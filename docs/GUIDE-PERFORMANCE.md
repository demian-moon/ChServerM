# 성능 튜닝 가이드 — 측정 근거와 함께

이 문서는 [BENCHMARKS.md](BENCHMARKS.md)(정본 수치)와 [PROFILING.md](PROFILING.md)(측정
방법)를 **결정 순서**로 재구성한 것이다. 여기 나오는 모든 수치는 BENCHMARKS.md 의 해당
절에서 왔고, 절 제목을 함께 적었다 — 수치가 의심되면 원문을 본다.

**읽기 전 규칙 (BENCHMARKS.md 「규칙」 절)**
- 수치 없는 성능 주장은 하지 않는다. 측정은 Release + 디버거 미연결.
- GC 모드는 선언이 아니라 **`*.runtimeconfig.json` 산출물**로 확인한다 — 프로퍼티 오타
  하나로 3개월간 Workstation GC 로 돈 실사례가 있다(ADR-0031).
- 레이턴시는 평균이 아니라 **p50/p99/p999** 로 읽는다.
- 종단 부하 수치는 전부 **루프백 단일 머신**(서버·부하 생성기가 코어를 공유)이다 —
  지연은 낙관치이고, 실 NIC·다중 머신 수치는 아직 없다.

## 0. 기준선 — 튜닝 전에 이것과 비교한다

「성능 기준선 (실측, 2026-08-08 확정)」:

| 항목 | 수치 | 조건 |
|---|---|---|
| TCP 에코 처리량 | **169,180 RPS** (p50 1.39ms · p99 3.53ms) | ENV-A, 1만 접속 |
| 동시 접속 | 10,000/10,000, 실패 0 | |
| 커넥션당 메모리 | ~8 KB | GC 모드에 좌우 |
| 프레임당 힙 할당 | 0 B | in-flight 얕을 때 |
| 디스패치 라우팅 | 0.69 ns (프로덕션 경로 7.63 ns) | |
| 코어 확장성 | **14.67×/16코어 (효율 91.7%)** — ALU 천장의 99.0% | ENV-B |
| 프레임워크 세금 (vs raw Kestrel) | 저부하 −13.5% RPS · 고동시성 −3.3% RPS 에 **p99 −34%** | |

파생 예산: 169k RPS/코어 ≈ **메시지당 6 µs**. 어떤 기능의 비용을 판단할 때 이 분모로
나눠 본다(예: 메트릭 72ns/프레임 = 예산의 1.2%).

부하별 형태(「Phase 5 게이트」): 16 활성 p50 **104µs** → 10k 접속 p50 1.39ms.
처리량은 150~170k 로 수렴하고, **동시성이 늘면 처리량이 아니라 대기 지연이 는다.**

## 1. 튜닝 순서 — 효과가 큰 것부터

### 1.1 파티션 수 (`PartitionedExecutionOptions.PartitionCount`)

**물리 코어 수와 같거나 정수배로.** 어중간한 비율이 최악이다 — 8코어에 12파티션은
24파티션보다 느리고(61.7 vs 46.8ms), 16코어에 24파티션은 −30%다.
(「ADR-0005 재검증: 실제 코어 제한 확장성 곡선」 §초과 구독, 2026-08-07)

### 1.2 전송 선택 — 동시성 프로필이 결정한다

「HTTP 전송 세금」(2026-08-11, ADR-0057):

| 시나리오 | TCP | HTTP/2 (h2c) |
|---|---|---|
| 16 활성 (지연 민감) | 기준 | −6.1% RPS, p50 +8~9µs |
| 512 활성 | 149,304 RPS | **882,931 RPS (5.9×)** |
| 10k+256 활성 | 154,104 RPS | **764,062 RPS (5.0×)** |

**상시 연결 소수·지연 민감 = TCP, 대규모 동시 스트림·처리량 = HTTP/2.** 역전의 원인은
스트림 다중화로 syscall 이 줄어서다. WebSocket·QUIC 성능은 **미측정**이다 — 단정하지 않는다.

### 1.3 직렬화기 선택 (「4자 직렬화 벤치마크」, 2026-08-05)

왕복 최속 = **MemoryPack**(small 104.4ns / large 1,916ns, 기본값 ADR-0013).
와이어 최소·크로스 언어 = **Protobuf**(직렬화 33.0ns / 71B). FlatSharp 156.8ns,
MessagePack 181.4ns. 네 후보 모두 직렬화 할당 0 — 선택 기준은 속도보다
**상호운용·랜덤 접근 요구**다 ([GUIDE-CHOOSING-AXES.md](GUIDE-CHOOSING-AXES.md) 3절).

### 1.4 버퍼 — 응답 스크래치는 재사용한다

`ArrayBufferWriter` 매 요청 생성 → `PooledBufferWriter` 재사용: **619.1ns·8,056B →
50.3ns·0B (12.3×)**. 1만 커넥션이 동시에 붙들어도 정상 상태 0 B.
(「버퍼: 응답 직렬화 스크래치」 2026-08-05 · 「PooledBufferWriter 1만 커넥션」 2026-08-11)

단, **파티션 실행 모델에서만** 커넥션당 재사용 버퍼가 합법이다 — 무상태(병렬) 프로필에서
공유 가변 버퍼는 데이터 경합이다(`StatelessWeb` 샘플의 핸들러 주석 참조).

깊은 큐 경로(in-flight 1만)는 `ArrayPool.Shared` 가 빗나간다: 전용 풀이 **33% 빠르고
무할당**(514.0ns·274B → 342.9ns·0B). 대가는 트리밍 없음 — 보유 상한을
`2 × maxArrayLength(2^올림) × maxArraysPerBucket` 로 직접 계산하고, 보관 개수는
"큐 깊이"가 아니라 **큐 깊이 × 피어 수**다.
(「전용 풀이 깊은 큐에서 무할당을 회복한다」 2026-08-10)

### 1.5 수용 제어 — 꼬리를 지키는 장치다

접속 스파이크에 `PermitsPerSecond`/`BurstCapacity` 를 걸면 기존 커넥션 **p99 −41%**
(27.20→16.00ms). 대신 신규 3,000 중 1,975 거부, p50 은 오히려 악화. **평균이 아니라
꼬리를 지키는 장치**임을 알고 켠다. (「스파이크 시나리오」 2026-08-08)

### 1.6 GC — 처리량이 아니라 p99 와 메모리의 트레이드오프

세 모드의 처리량 차이는 ±2% 안(무할당 설계의 증거). 결정 지점은 DATAS:
켜짐 = p99 +46~85%, 끄면 p99 회복하지만 **워킹셋 62→624 MB(10배)**.
(「GC 모드 A/B」 2026-08-08, ADR-0031 — 기본값은 잠정이다)

### 1.7 그 외 노브 요약

| 노브 | 실측 | 판단 |
|---|---|---|
| TLS 1.3 | −2.5% RPS, p50 +~50µs | 공인망이면 그냥 켠다 — 병목 아님 (2026-08-05) |
| 압축 LZ4 (`MinCompressLength` 1024) | 인코드 582~935ns/1KB, 할당 0. Brotli 는 비압축성에서 11~35배 | 코덱은 LZ4, 문턱을 함부로 낮추지 않는다 (2026-08-06) |
| 메트릭/추적 | 메트릭 ~72ns/프레임·0B. 추적 리스너 없으면 +2ns, 붙으면 170.6ns·560B | 메트릭은 상시, 추적은 샘플링 (2026-08-06·07) |
| 틱 지터 (`SpinWaitWindow`) | 1ms 스핀은 효과 없음(OS 해상도 ≈15.6ms 미만이라). **16ms 스핀 → p99 0µs**, 대가 = 50ms 틱에서 코어 최대 32% | 저지터가 정말 필요할 때만 (2026-08-11) |
| Native AOT | 기동 2.8×, 워킹셋 2.8× 개선. **정상 상태 처리량 미측정** | 콜드스타트·풋프린트용 (2026-08-08) |
| 원격 세션 저장소 | Redis 읽기 452µs, PG 쓰기 2,250µs = 에코 왕복의 4~5배 | **메시지마다 원격 세션 읽기는 성립하지 않는다** — 캐시 전제(ADR-0039, 2026-08-10) |
| 룸 브로드캐스트 | 멤버당 384~433ns 일정·0B. 100명 룸 60Hz ≈ 코어 25% | 규모 산정에 이 상수를 쓴다 (2026-08-11) |

## 2. 하지 말 것 — 측정으로 기각된 최적화

전부 "해 봤는데 효과가 없거나 역효과"로 판정된 것들이다. 다시 시도하려면 기각 근거부터 읽는다.

1. **파티션 대기 스핀 제거** — CPU 프로파일 1위(25.32%)라서 없앴더니 −4.7% RPS. 그 25%는
   낭비가 아니라 커널 전이 회피 비용이다 (2026-08-09, PROFILING.md 2.4)
2. **벡터드 send** — RPS +0.3%, burst p99 악화, 힙 3→9MB. 기본 false 유지 (2026-08-05)
3. **디스패치 switch 직생성** — 배열 인덱싱(0.69ns)이 이미 더 빠르다 (2026-08-05)
4. **Kestrel Socket Transport 교체** — 유리하게 기운 비교에서도 동률, p99 는 순수 소켓 승 (ADR-0001)
5. **전역 락 실행 모델** — 직렬 실행보다도 느리다. 순서 보장 비용은 파티션 모델로 3.9%면 충분 (2026-08-03)
6. **GC 튜닝으로 처리량 개선** — ±2% 안. 무할당 설계에서 GC 는 처리량 병목이 아니다 (2026-08-08)
7. **대량 접속 해제 대응** — 비용은 해제(0B·2.04ms)가 아니라 **재접속 폭풍**(커넥션당
   ~7.4KiB 신규 할당)에서 난다. "결함이 아니라 예산" — 실 워크로드에서 관측되면 대응 (2026-08-11)
8. **조각 재조립 최적화** — 16조각이 단일 대비 +1.3%, 양쪽 다 0B (2026-08-11)

## 3. 측정하는 법 — 주장 전에 이것부터

```bash
# 마이크로 벤치마크 (BenchmarkDotNet)
dotnet run -c Release --project Bench/ChServerM.Bench -- --filter "*PartitionScaling*"

# 종단 부하 (자체 클라이언트, ADR-0009)
dotnet run -c Release --project Bench/ChServerM.Bench.LoadRunner -- server --partitions 12
dotnet run -c Release --project Bench/ChServerM.Bench.LoadRunner -- client --connections 10000 --active 256
```

- LoadRunner 출력의 **생성기 CPU%** 를 본다 — 100% 근처면 병목은 서버가 아니라 생성기다.
- 확장성 판정은 **물리 코어까지만**(SMT 구간을 넣으면 멀쩡한 설계를 오판). 어피니티
  마스크는 SMT 형제가 인접 쌍이라 한 칸 건너뛴 비트다(`0x5`, `0x55`, …).
- 회귀 게이트: `eng/bench-gate.ps1`(CI, 비율 기반 — 두 팔이 함께 느려지는 회귀는 원리상
  못 잡는다, ADR-0032) · `eng/scaling-gate.ps1`(측정 머신 전용, 하한 효율 70%).
- 프로파일링 절차와 함정(리프 의사 프레임 귀속, 정상 상태 진입 대기)은
  [PROFILING.md](PROFILING.md). **"프로파일해 봤더니 문제가 아니었다"도 결과다** —
  고치지 않기로 한 결정을 근거와 함께 남긴다.
- 정상 상태 참고값(512 커넥션 ~156k RPS): 할당 37.3MB/s, gen0 5/s, **gen1·gen2 = 0**.
  누수 신호는 할당량이 아니라 **gen2 승격과 워킹셋 추세**다.

## 4. 아직 없는 수치 (단정 금지 목록)

WS·QUIC 전송 성능 · 실 NIC 다중 머신 · NUMA · AOT 정상 상태 처리량 · 리눅스 틱 지터 ·
주소별 연결 제한(루프백으로 검증 불가). 이 목록의 무언가가 필요해지면 측정이 먼저다.
