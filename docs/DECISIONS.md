# 설계 결정 기록 (ADR)

라이브러리 선택과 아키텍처 결정을 여기에 남긴다. **추가 전용** — 결정을 뒤집을 때는 기존 ADR을 수정하지 말고 새 ADR을 추가해 `Superseded by ADR-XXXX`로 표시한다.

## 작성 규칙
- 번호는 4자리 연번(`ADR-0001`)
- **대안과 탈락 이유를 반드시 적는다.** 이것이 ADR의 존재 이유다
- 성능이 근거라면 `docs/BENCHMARKS.md`의 수치를 링크한다
- 상태: `제안` / `채택` / `보류` / `폐기(Superseded by ADR-XXXX)`

## 템플릿

```markdown
## ADR-XXXX: {제목}

- **날짜**: YYYY-MM-DD
- **상태**: 채택
- **영향 범위**: {어셈블리 / 축}

### 배경
{어떤 문제를 풀어야 했는가}

### 결정
{무엇을 선택했는가}

### 대안과 탈락 이유
| 대안 | 탈락 이유 |
|---|---|
| {A} | {이유} |

### 결과
- 긍정: {얻은 것}
- 부정: {감수한 비용, 되돌리기 난이도}
```

## ADR-0000: 아키텍처 기본 원칙

- **날짜**: 2026-07-30
- **상태**: 채택
- **영향 범위**: 전체

### 배경
단일 서버가 아니라 기능을 조립해 서버를 구성하는 상업용 프레임워크가 목표다. 성능이 최우선이면서 동시에 구현체 교체가 가능해야 한다 — 이 둘은 보통 상충한다(추상화는 간접 호출 비용을 낳는다).

### 결정
1. `ChServerM.Core`는 서드파티 의존 0. 추상화·인터페이스·값 타입만 담는다.
2. 모든 벤더 통합은 `ChServerM.<축>.<벤더>` 어댑터 어셈블리로 격리한다.
3. 리플렉션 대신 소스 제너레이터. 전 어셈블리 `IsAotCompatible=true`.
4. 조립 비용은 **시작 시점**에 지불한다 — 빌더가 파이프라인을 델리게이트 체인으로 컴파일하고, 핫패스에는 동적 결정을 남기지 않는다.

### 대안과 탈락 이유
| 대안 | 탈락 이유 |
|---|---|
| 단일 어셈블리 + 조건부 컴파일 심볼 | 소비자가 필요 없는 벤더 의존까지 끌고 감. NuGet 배포 단위를 쪼갤 수 없다 |
| 런타임 리플렉션 기반 플러그인 로딩 | Native AOT 불가, 콜드스타트 비용, 트리밍 불가 |
| 제네릭 특수화로만 축 교체 (인터페이스 없음) | 최고 성능이지만 사용자 코드 전체에 타입 인자가 전파돼 API가 못 쓸 수준으로 복잡해진다. 향후 핫패스 국소 적용은 검토 |

### 결과
- 긍정: 축 교체가 패키지 참조 교체로 끝난다. Core만 보면 프레임워크 전체 계약을 읽을 수 있다.
- 부정: 어셈블리 수가 많아져 빌드·버전 관리 비용이 늘어난다. 축 하나를 추가할 때 Core 인터페이스부터 손대야 해서 초기 속도가 느리다.

## ADR-0001: raw TCP 전송 구현 방식

- **날짜**: — (2026-07-30 근거 보강, **2026-08-05 확정**)
- **상태**: **채택 — 순수 `Socket`+Pipelines 유지** (아래 2026-08-05 절)
- **영향 범위**: `ChServerM.Transport.Tcp`

### 배경
raw TCP 서버의 소켓 계층을 직접 만들 것인지, 검증된 엔진을 재사용할 것인지.

### 후보
| 후보 | 장점 | 우려 |
|---|---|---|
| Kestrel Socket Transport (`Microsoft.AspNetCore.Connections.Abstractions`) | 프로덕션 검증된 소켓 엔진, `SocketAsyncEventArgs` 풀링 + 전용 IO 스케줄러, Pipelines 통합 완료, 유지보수 무료 | ASP.NET Core 의존 유입, 커넥션 추상화가 우리 것과 겹침 |
| 순수 `Socket` + `SocketAsyncEventArgs` + Pipelines | 완전한 제어, 최소 의존, 스레드-퍼-코어 직접 구현 가능 | 엣지 케이스(half-open, 리눅스/윈도우 차이) 전부 직접 처리 |

### 2026-07-30 추가된 근거
레거시 `LegacyServer/IoPipelineSrvM.cs`를 정독한 결과, 기존 구현은 `TcpClient.GetStream()` →
`NetworkStream.ReadAsync` 노선이다. Kestrel Socket Transport에는 이 `NetworkStream` 계층이 없다.
즉 **레거시 노선은 성능 상한이 더 낮다.** 이것이 Kestrel 재사용 쪽으로 기운 이유다.

다만 레거시 자산 승계 비용이 있으므로, Phase 5 진입 전 양쪽 프로토타입 벤치마크로 확정한다.
참고: Bedrock Framework(Kestrel 전송을 비HTTP 프로토콜에 쓰는 실험적 구현).

### 2026-08-03 — 순수 `Socket` 쪽 프로토타입 완성

`ChServerM.Transport.Tcp` 를 raw `Socket` + `System.IO.Pipelines` 로 구현했다.
**결정은 여전히 열려 있다** — 비교 대상 하나가 생겼을 뿐이다. Kestrel 버전을 만들어
벤치마크로 붙여야 확정된다. `IServerTransport` 가 중립이므로 두 구현이 공존할 수 있다.

구현하면서 확정한 것들:

- **`TcpClient`/`NetworkStream` 을 쓰지 않는다.** `Socket` 의 `Memory<byte>` 오버로드를
  직접 쓴다. 레거시 노선(`TcpClient.GetStream()`)보다 계층이 하나 적다
- **소켓 작업에 `CancellationToken` 을 넘기지 않는다.** 플랫폼마다 실제 취소 가능 여부가
  다르고 등록 비용이 작업마다 든다. 중단은 `Socket.Dispose()` 로 한다 — Kestrel 과 같은 방식
- **0바이트 수신으로 대기한다**(`WaitForDataBeforeAllocating`, 기본 켬). 유휴 커넥션이
  수신 버퍼를 붙들지 않는다. 1만 유휴 접속 × 4KB = 40MB 를 아낀다.
  레거시는 커넥션당 64KB 를 상수로 붙들었다(= 640MB)
- **부분 전송을 처리한다.** `SendAsync` 가 요청한 전부를 보낸다는 보장이 없다.
  처리하지 않으면 조용히 잘린 프레임이 나가고 수신 측 프레임 경계가 통째로 밀린다
- **이식 가능한 소켓 옵션만 쓴다.** 레거시의 `IOControlCode.KeepAliveValues` 는
  Windows 전용이라 리눅스에서 던진다 — 크로스 플랫폼 차단 요인이었다.
  세밀한 keep-alive 제어가 필요하면 애플리케이션 레벨 하트비트를 쓴다

**검증**: `CrossTransportTests` 가 같은 핸들러 코드를 InMemory 와 TCP 양쪽에서 돌린다.
14개 항목 × 2 전송이 전부 통과한다 — ADR-0004 의 조립 가능성 합격 기준.

### 2026-08-05 — 확정: 순수 `Socket`+Pipelines 를 유지한다

Kestrel 쪽 프로토타입(`SocketTransportFactory` 를 `IServerTransport` 로 감싼
`KestrelSocketServerTransport`, `Bench/ChServerM.Bench.LoadRunner` 소재)을 만들어
동일 상위 계층으로 3개 시나리오(16/512 활성, 1만 접속+256 활성)를 대결시켰다.
수치는 `BENCHMARKS.md` 2026-08-05 절.

**결과는 통계적 동률(전 항목 ±3.2%, 방향 혼재)이고, p99 는 순수 소켓이 두 부하
시나리오 모두 낮았다.** 프로토타입에는 idle 스윕·거부 통지·상한 판정 등 프로덕션
기능이 없어 비교가 Kestrel 에 유리하게 기울어 있었는데도 그렇다. 이 워크로드의
병목은 전송이 아니라 상위 파이프라인이다.

**따라서 순수 `Socket`+Pipelines(`ChServerM.Transport.Tcp`)를 유지한다.** 2026-07-30 의
"Kestrel 쪽으로 기울었음"은 실측으로 뒤집혔다 — 그 추정은 레거시(`NetworkStream` 노선)
대비였고, 우리 구현이 이미 같은 계층 수(소켓 직결)에 도달했기 때문이다.

| 대안 | 탈락 이유 |
|---|---|
| Kestrel Socket Transport 채택 | 성능 이득 없음(동률). `Microsoft.AspNetCore.App` FrameworkReference 유입 — 어댑터 무의존 규약·Native AOT 배포 크기와 충돌. 이미 구현·검증된 프로덕션 기능(idle 스윕, 거부 통지 40004, MaxConnections, ConnectionId 세대, 종료 상한)을 어댑터 위에 재구현해야 한다 |
| 양쪽 유지(전송 어댑터 2종) | 기능 동등성 유지 비용 이중화. 이득이 없는 중복이다. 프로토타입은 벤치 도구에 남겨 재현·재검만 가능하게 한다 |

부수 이득: 이 대결로 `IServerTransport` 계약의 세 번째 실증(InMemory·Tcp·Kestrel)이
생겼다 — HTTP 전송(Phase 16)도 같은 모양으로 들어올 수 있다는 근거다.

재검토 조건: 워크로드가 바뀌어 전송이 병목으로 관측되거나(Phase 11 메트릭),
Kestrel 전송에 우리가 재현할 수 없는 기능(예: io_uring 지원)이 들어올 때.

## ADR-0002: 프레임 헤더에 직렬화 포맷을 쓰지 않는다

- **날짜**: 2026-07-30
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(`IFrameDecoder`/`IFrameEncoder`), `ChServerM.Transport.*`

### 배경
레거시 `LegacyServer/FlatbufferM/PacketM.fbs`는 프레임 헤더 3종(`FbsPkHeadM`,
`FbsContentHeadM`, `FbsEncryptHeadM`)을 모두 FlatBuffers `table`로 정의했다.
스키마 주석이 문제를 자백하고 있다:

```
byteCheckSum : byte = -1;   // 0을 쓰면 안된다. 헤더 길이 달라짐
packetType : ushort;        // 디폴트 값은 저장이 안되니까(패킷 사이즈가 달라짐)해서 1부터 쓴다
conDataLen : int = -1;      // 0은 저장이 안되니까 -1로 설정 (헤더값 달라짐)
gage : ushort = 65535;      // 65535는 변경이 없다는 의미
```

원인은 명확하다. **FlatBuffers는 기본값과 같은 필드를 직렬화하지 않는다.** 그래서 헤더가
가변 길이가 되고, 고정 길이를 전제로 하는 프레이밍이 깨진다. 이를 `-1`, `65535` 같은
sentinel 값으로 우회하고 있어 값 공간이 오염되고 새 필드를 추가할 때마다 같은 함정을 밟는다.

### 결정
**프레임 헤더는 직렬화 라이브러리를 거치지 않는다.** 고정 크기 `struct` +
`MemoryMarshal`/`BinaryPrimitives`로 직접 읽고 쓴다. 헤더 크기는 컴파일 타임에 확정된다.

직렬화 라이브러리는 **페이로드에만** 적용한다. `docs/ARCHITECTURE.md`의
"프레이밍과 직렬화를 분리한다" 원칙이 정확히 이 문제를 해결한다.

### 대안과 탈락 이유
| 대안 | 탈락 이유 |
|---|---|
| FlatBuffers 헤더 + sentinel 값 유지 (레거시 방식) | 가변 길이 헤더. 값 공간 오염. 필드 추가마다 재발. 파싱 비용도 불필요하게 발생 |
| Protobuf 헤더 | 동일 문제. varint + 기본값 생략으로 길이가 가변 |
| FlatBuffers를 페이로드에서도 배제 | 과잉 대응. 역직렬화 없는 랜덤 접근은 게임 패킷에 실익이 있다. 문제는 포맷이 아니라 용도 오배치였다 |

### 결과
- 긍정: 헤더 파싱 비용 0. 프레이밍과 직렬화 축을 독립적으로 교체 가능. sentinel 규약 소멸
- 부정: 헤더 레이아웃 변경이 와이어 호환성을 직접 깬다. 버전 필드를 헤더에 미리 넣어야 한다

### 2026-08-03 확정 — 레이아웃

`ChServerM.Core/Framing/FrameHeader.cs`에 **16바이트 고정, 리틀 엔디안**으로 굳혔다.

```
offset size 필드            비고
  0     2   Version         이게 없으면 프로토콜을 영원히 못 바꾼다
  2     2   MessageId
  4     4   PayloadLength   디코더가 상한과 대조한 뒤에만 신뢰한다
  8     2   Flags           Compressed / Encrypted / Fragmented / EndOfMessage
 10     2   Reserved        0으로 채운다
 12     4   Sequence        순서 진단 + Phase 9 리플레이 방지
       ────
       16
```

배경에서 계산한 레거시 헤더는 **52바이트**(실제 데이터 13바이트)였다.
초당 10만 프레임 기준 헤더 오버헤드가 5.2MB/s → 1.6MB/s로 줄어든다.

두 가지를 배경 시점의 서술에서 바꿨다.

- **`MemoryMarshal`을 쓰지 않는다.** `BinaryPrimitives` + 명시적 리틀 엔디안만 쓴다.
  구조체 정렬·패딩·호스트 엔디안에 와이어 포맷이 끌려가지 않는다. 그래서
  `FrameHeader`에는 `[StructLayout]`이 없고 코덱은 별도 어셈블리(`ChServerM.Framing`)에 있다
- **체크섬 필드를 두지 않는다.** 무결성은 Phase 9의 AEAD 태그가 담당한다.
  레거시의 체크섬 검증 함수는 본문이 `return true`였다 — 있는 척하는 필드보다 없는 편이 정직하다

### 남은 미결
**페이로드 직렬화 기본값은 확정하지 않았다.** MemoryPack / FlatSharp /
Google.Protobuf·protobuf-net / MessagePack-CSharp 4자 벤치마크(Phase 6)로 결정한다.
레거시가 FlatBuffers 스키마와 생성 코드를 이미 운영 중이므로 승계 비용이 변수다.
크로스 언어 클라이언트가 요구사항에 들어오면 결론이 바뀐다.

## ADR-0003: 목표 워크로드 — 실시간 게임 서버

- **날짜**: 2026-07-30
- **상태**: **폐기 (Superseded by ADR-0004)** — 2026-07-31
- **영향 범위**: ROADMAP Phase 순서, `IExecutionModel`, 전송 축 우선순위

> **폐기 사유 (2026-07-31)**
> 이 ADR은 프로젝트 목표를 잘못 읽었다. ChServerM은 특정 워크로드용 서버가 아니라
> **워크로드를 조립해내는 프레임워크**다. "TCP 커넥션 서버로 할 수도 있고 stateless
> 웹서버로 할 수도 있다"가 최초 요구사항이었다. 워크로드는 산출물이지 전제가 아니다.
>
> 아래 "근거"에 모은 레거시 증거 자체는 유효하다. 다만 그것이 증명하는 것은
> "이 제품은 게임 서버다"가 아니라 **"프레임워크가 표현할 수 있어야 하는 능력들"**이다.
> 그 해석으로 다시 쓴 것이 ADR-0004다.

### 배경
"고성능 서버 프레임워크"만으로는 전송·동시성 모델의 우선순위를 정할 수 없다. 실시간 게임과
일반 API 서버는 요구가 다르다 — 전자는 상시 연결·틱·순서 보장, 후자는 무상태·수평 확장.

### 근거 (레거시 구성에서 도출)
| 자산 | 시사점 |
|---|---|
| `RatingSystem/GlickoM.cs`, `WengLinM.cs` | Glicko / Weng-Lin 레이팅 → 매치메이킹 |
| `QuadTreeM.cs`, `BoxColliderM.cs`, `HierachyM.cs` | 공간 분할·충돌·씬 계층 → 실시간 시뮬레이션 |

| `UserM.MemPkActionBlock` | 유저별 순서 보장 |

### 제안했던 결정 (폐기됨)

→ **ADR-0004로 대체.**

## ADR-0004: 워크로드는 전제가 아니라 프로필이다

- **날짜**: 2026-07-31
- **상태**: 채택
- **영향 범위**: 전체 (ROADMAP 구조, Part V 위상, 검증 전략)
- **관계**: Supersedes ADR-0003

### 배경
ADR-0003은 레거시 코드에서 워크로드를 역추론해 "이 프레임워크는 실시간 게임 서버용"이라고
전제했다. 이는 프로젝트 목표와 충돌한다. ChServerM의 존재 이유는 **워크로드를 옵션과
빌더로 골라 조립하는 것**이다 — TCP 상시 연결도, stateless 웹서버도 같은 Core 위에서
조립되어야 한다.

동시에 반대 방향의 실패도 있다. 검증 대상 없이 추상화만 그으면 **쓸 수 없는 추상화**가
나온다. 추상화의 정당성은 서로 다른 구현이 실제로 끼워지는 것으로만 증명된다.

### 결정

**1. 프레임워크에 목표 워크로드는 없다.** 축 구현체의 조합이 워크로드를 만든다.
Phase 순서는 워크로드가 아니라 **"무엇이 추상화를 먼저 증명하는가"**로 정한다.

**2. 대신 검증용 참조 프로필을 둔다.** 프로필은 축 조합의 이름이고, `Samples/`의 산출물이며,
추상화가 실제로 조립 가능한지 증명하는 장치다. 최소 2개를 유지한다:

| 프로필 | 축 조합 | 이 프로필이 증명하는 것 |
|---|---|---|
| `realtime-stateful` | TCP + 고정 헤더 프레이밍 + 유저별 순서 보장 실행 모델 + 인메모리 세션 | 상시 연결, 순서 보장, 커넥션 생명주기 |
| `stateless-web` | HTTP/Kestrel + 무상태 + 외부 세션 저장소 + 병렬 실행 모델 | 세션 외부화, 수평 확장, 전송 교체 |

**3. 두 프로필이 같은 핸들러 코드로 동작해야 한다.** 이것이 조립 가능성의 합격 기준이다.
한쪽만 도는 추상화는 추상화가 아니다.

**4. 워크로드 특화 기능은 선택 축(별도 패키지)으로 격리한다.** 틱 루프·룸/AOI·매치메이킹은
`ChServerM.RealTime.*`로 분리해, 쓰지 않는 사용자가 의존을 끌고 오지 않게 한다.
Core는 이들의 존재를 알지 않는다.

### 레거시 증거의 올바른 해석
ADR-0003이 모은 증거는 유효하다. 결론만 틀렸다. 재해석:

| 레거시 증거 | 잘못된 해석 (ADR-0003) | 올바른 해석 |
|---|---|---|
| `UserM.MemPkActionBlock` | 게임 서버가 목표다 | `IExecutionModel`이 **유저별 순서 보장을 표현할 수 있어야** 한다. 무상태 프로필은 이 전략을 쓰지 않는다 |
| `FbsServerTick`, `serverFrequency` | 틱이 프레임워크 핵심이다 | 틱은 **선택 축**이다. 없이도 서버가 성립해야 한다 |
| `QuadTreeM`, `BoxColliderM` | 공간 분할이 필수다 | 선택 패키지. 프레임워크가 아니라 도메인 계층 |
| `GlickoM`, `WengLinM` | 매치메이킹이 필수다 | 선택 패키지. 샘플로도 충분할 수 있다 |

### 대안과 탈락 이유
| 대안 | 탈락 이유 |
|---|---|
| 워크로드를 게임 서버로 고정 (ADR-0003) | 프로젝트 목표와 충돌. 축 교체 가능성이라는 존재 이유를 스스로 부정한다 |
| 워크로드를 완전히 불특정하고 프로필도 두지 않음 | 검증 대상이 없어 "조립 가능한 것처럼 보이는" 추상화가 나온다. 두 번째 구현체가 나올 때까지 추상화는 가설이라는 원칙(ADR-0000)과도 모순 |
| 프로필을 3개 이상 (게임/웹/IoT/배치…) | 초기 비용 과다. 2개로 축 교체가 증명되면 3번째는 사용자가 만들 수 있다 |

### 결과
- 긍정: 로드맵이 특정 도메인에 종속되지 않는다. Part V를 빼도 프레임워크가 성립한다.
  "두 프로필이 같은 핸들러로 동작"이라는 **객관적 합격 기준**이 생겼다
- 부정: 프로필 2개를 상시 유지해야 하므로 샘플·통합 테스트 비용이 두 배다.
  전송·실행 모델 축의 인터페이스가 양쪽을 모두 수용해야 해서 설계가 더 어렵다

### 열린 항목
어느 프로필을 먼저 구현할지는 **선호가 아니라 검증 효율**로 정한다.
`realtime-stateful`이 프레이밍·순서 보장·커넥션 생명주기를 모두 통과해야 하므로
추상화를 더 강하게 압박한다. `stateless-web`은 상당 부분 그 부분집합이다.
따라서 `realtime-stateful`을 먼저 세우고 `stateless-web`으로 교체 가능성을 증명한다.

## ADR-0005: `IExecutionModel`의 기본 전략은 키 기반 샤딩이다

- **날짜**: 2026-07-31
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(`IExecutionModel`), `ChServerM.Concurrency`, 전 축의 스레드 안전성 계약

### 배경

멀티코어를 최대한 활용하면서 **유저별 처리 순서를 보장**해야 한다. 이 둘은 보통 상충한다 —
순서를 보장하려면 직렬화가 필요하고, 직렬화는 병렬성을 죽인다.

`docs/legacy/` 전수 분석에서 레거시가 이 문제를 **송신·수신·스케줄러 3곳에서 독립적으로
같은 방식으로 해결**한 것을 확인했다([01-network-transport](legacy/01-network-transport.md#sendpacketgroupm),
[04-concurrency](legacy/04-concurrency.md#이-계층의-핵심--샤딩이-아키텍처의-중심-아이디어다)).
같은 발상이 세 번 재발명됐다는 것은 그것이 이 문제의 자연스러운 해답이라는 뜻이다.

### 결정

**`IExecutionModel`의 기본 전략을 키 기반 샤딩(partition-by-key)으로 한다.**

```
파티션 키(SessionId 등)의 안정 해시(XxHash3) → 샤드 선택
같은 키의 작업은 항상 같은 샤드 → 단일 소비자 → 순서 보장 + 동기화 불필요
다른 키는 완전 독립 → 코어 수만큼 선형 확장
```

부수 결정:

1. **샤드 내부는 동기화가 불필요하다는 것을 계약으로 표현한다.** 그 안의 자료구조는 락도
   `Concurrent*`도 쓰지 않는다. 레거시는 이 보장에 **암묵적으로** 의존해 `PkObjM`의 락을
   제거했다가, 계약이 코드에 없어 앱 코드가 깰 수 있는 상태가 됐다
2. **파티션 키는 강타입 ID의 안정 해시**로 구한다. 레거시의 `oid % n`은 음수·오버플로·
   분포 편향 문제가 있다
3. **샤드 수는 옵션 + 시작 시점 검증.** static 초기자로 다른 static을 읽지 않는다
   (레거시는 이 때문에 `DivideByZeroException` 가능 상태였다)
4. 이것은 **기본 전략이지 유일 전략이 아니다.** `stateless-web` 프로필은 병렬 실행을
   선택한다 — 하나의 계약이 양쪽을 수용해야 한다(ADR-0004)

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| **전역 락 / `Concurrent*` 자료구조** | 코어 수가 늘어도 경합 지점이 하나라 확장되지 않는다. 락-프리 CAS도 같은 캐시 라인을 다투면 락보다 느려질 수 있다 |
| **액터 모델 (Orleans / Proto.Actor)** | 개념은 유사하지만 프레임워크 전체를 특정 런타임에 묶는다. Core 무의존 원칙 위반이고, 액터당 오버헤드가 커넥션 수만큼 곱해진다. **어댑터로는 계속 검토**(Phase 8) |
| **스레드-퍼-코어 + CPU 어피니티만** | 코어 배정은 해결하지만 **"같은 유저의 작업이 같은 스레드로 간다"는 보장이 없다.** 샤딩과 배타적이지 않으므로 **병행 적용**한다 |
| **순서 보장 포기 (완전 병렬)** | 게임 서버·상시 연결 워크로드에서 유저 메시지 순서가 뒤바뀌면 상태가 깨진다. `stateless-web` 프로필에서만 선택지다 |
| **메시지마다 시퀀스 번호로 재정렬** | 레거시가 시도했다가 접었다(`ConcurSeqTaskExecM.cs`에 약 430줄 주석으로 잔존). 재정렬 버퍼와 지연이 생기고, 샤딩이 같은 결과를 공짜로 준다 |

### 결과

- 긍정: **락 없이 순서 보장 + 코어 수 선형 확장.** 샤드 내부 코드가 단순해진다(동기화 코드 불필요).
  경합 자체가 없으므로 false sharing·CAS 경합 문제가 대부분 소멸한다
- 부정: **파티션 키 선택이 부하 분포를 결정한다.** 한 유저가 과도한 트래픽을 내면 그 샤드만
  포화된다(hot partition). → 샤드별 큐 깊이를 메트릭으로 노출하고 rate limiting을 유저 단위로
  적용한다(Phase 10·11)
- 부정: 유저 간 상호작용(같은 룸의 두 유저)은 **샤드를 넘는 통신**이 필요하다. 룸 단위 파티셔닝을
  별도 축으로 둘지 Phase 18에서 결정한다
- 부정: 샤드 수를 런타임에 바꾸기 어렵다(키→샤드 매핑이 변한다). 재해싱 전략은 Phase 15에서

### 검증

**"코어 수 대비 처리량이 선형에 근접"을 벤치마크로 증명한다** (1·2·4·8·16코어).
증명되지 않으면 이 결정은 무효다 — Phase 8 게이트이자 Phase 12의 회귀 게이트 대상이다.
구현 규약은 `CLAUDE.md` 9절(병렬성 규약).

### 2026-08-03 — 구현 완료, 확장성 증명은 미완

`ChServerM.Concurrency` 에 파티션당 전용 스레드 + 단일 FIFO 큐로 구현했다.
`PartitionedConnectionHandler` 가 커넥션의 읽기 루프를 파티션 스케줄러에 고정한다 —
그러면 그 루프와 모든 `await` 연속이 같은 스레드에서 이어지고, **프레임당 큐 비용이 0**이 된다.

기능적 성질은 테스트로 확인했다(같은 키 → 같은 스레드, 순서 보존, `await` 너머 스레드 고정,
파티션 간 스레드 분리, 큐 포화 시 거부, 작업 예외 후 생존). 다만 이것은 "동작한다"의 증명이지
"선형 확장한다"의 증명이 아니다 — 그쪽은 아래에서 따로 측정했다.

구현하면서 확정한 설계:

- **큐는 하나다.** 스케줄러 연속과 `TryPost` 외부 작업이 같은 FIFO 를 공유해야
  둘 사이의 순서도 보장된다. 나누면 "타이머 작업이 진행 중인 메시지보다 먼저 실행"된다
- **유계 규약(9.6)은 유입 지점에서만 적용한다.** 채널 자체는 무제한이고
  외부 유입만 카운터로 막는다. 스케줄된 `Task` 를 거부하면 그것을 `await` 하던 코드가
  **영원히 깨어나지 못한다** — 커넥션 하나가 조용히 멈춘다.
  연속은 이미 승인된 작업의 결과이지 새로운 유입이 아니다
- **전용 스레드에서 블로킹한다.** 9.5 가 금지하는 것은 스레드풀 고갈이다.
  이 스레드는 이 파티션만을 위해 존재하므로 큐가 빌 때 여기서 대기하는 것이 의도된 동작이다
- **`TryExecuteTaskInline` 은 파티션 스레드에서만 허용한다.** 다른 스레드에서 인라인 실행하면
  "같은 키는 같은 스레드"가 그 자리에서 깨진다. 순서 보장의 마지막 방어선이다
- **구조체 작업은 풀링된 상자에 담아 큐에 넣는다.** `TryPost` 가 `struct` 로 제약된 이유가
  박싱 회피인데 채널에 그대로 넣으면 게시마다 박싱된다. 상자를 풀링해 정상 상태 할당 0
- **대기 카운터에 캐시 라인 패딩(128B)을 둔다** (9.4)
- **종료는 "전부에게 알린 뒤 함께 대기"다.** 파티션마다 순차로 알리고 기다리면
  최악의 종료 시간이 `파티션 수 × 제한 시간`이 된다 (64 × 5초 = 5분 20초)

락 획득 비용만 추가된다.

**남은 검증 두 가지.** 이 결정은 유효하지만 완전히 증명된 것은 아니다.

1. **파티션 수 스윕은 코어 수 제한의 근사다.** OS 는 여전히 모든 코어를 쓸 수 있다.
   `Process.ProcessorAffinity` 가 리눅스 미지원이라 프로세스 안에서 줄일 수 없으므로,
   `taskset`/`start /affinity` 로 감싼 재측정이 남아 있다
2. **단일 소켓 머신 한 대의 측정이다.** NUMA 노드가 여럿인 서버에서는 파티션-코어 배치가
   결과를 바꿀 수 있다 (Phase 8 의 CPU 어피니티 항목과 연결된다)

### ⚠ 2026-08-04 — 주 경로 구현 서술이 ADR-0008 로 대체됐다

위의 "읽기 루프를 파티션에 고정하면 모든 `await` 연속이 같은 스레드에서 이어지고
프레임당 큐 비용이 0" 서술은 **실전 경로에서 반증됐다** — 파이프 연속이 스레드풀로
이탈해 같은 파티션의 작업이 병렬 실행될 수 있었다. 배타성은 이제 완료 대기로 보장한다.
반증 경위·새 계약·비용은 [ADR-0008](#adr-0008-파티션-배타성은-스레드-어피니티가-아니라-완료-대기로-보장한다).
**이 ADR 의 결정(키 기반 샤딩)과 확장성 검증 조건 자체는 유지된다** — 위 확장성 곡선은
"실행 모델의 상한" 측정으로 재해석한다(메시지 단위 실측은 ADR-0008 벤치마크).

## ADR-0006: `System.IO.Pipelines`를 Core의 바이트 경로 추상으로 채택한다

- **날짜**: 2026-08-03
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(`IConnection`), 모든 `ChServerM.Transport.*`

### 배경

`IConnection`이 바이트를 어떤 타입으로 노출할지 정해야 했다. 이것은 되돌리기 비용이
가장 큰 결정 중 하나다 — 모든 전송 구현과 프레이밍 코드가 여기에 매인다.

동시에 CLAUDE.md의 하드 룰이 있다: **Core는 서드파티 의존을 가질 수 없다.**
`ChServerM.Core.csproj`의 `CHSM0001` 타깃과 `CoreDependencyTests`가 이를 강제한다.

### 검증한 사실

`System.IO.Pipelines`는 **net10.0 공유 프레임워크에 포함된다.** `PackageReference` 없이
`PipeReader`/`PipeWriter`를 쓸 수 있다. `System.Threading.Channels`도 마찬가지다.

반면 `System.IO.Hashing`(`XxHash3`)은 **별도 패키지**다. 그래서 파티션 해시를 Core에서
`XxHash3`로 구현할 수 없고, 피보나치 해싱을 쓴다(ADR-0005 / `PartitionKey`).

### 결정

`IConnection`은 `PipeReader Input` / `PipeWriter Output`을 노출한다.
프레임 디코더는 `ReadOnlySequence<byte>`를 받는다.

무의존 하드 룰과 충돌하지 않는다 — 공유 프레임워크는 서드파티가 아니다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| `Stream` | 부분 읽기를 호출자가 매번 처리해야 하고, 백프레셔 개념이 없다. 버퍼 재사용도 직접 관리해야 한다 — 레거시가 정확히 이 지점에서 커넥션당 64KB 고정 버퍼(1만 접속 = 640MB)를 잡았다 |
| 자체 `IByteChannel` 추상 정의 | 백프레셔·버퍼 풀링·세그먼트 관리를 처음부터 다시 만들게 된다. Pipelines가 이미 검증된 답이고, 새 추상은 결국 그것을 재발명한 열등한 사본이 된다 |
| `IDuplexPipe`(BCL) 노출 | Kestrel의 선택. 나쁘지 않지만 `IConnection`이 이미 `Id`·`Features`·`Abort`를 갖는 마당에 파이프만 별도 객체로 감싸면 간접 참조만 한 겹 는다 |
| `Memory<byte>` 직접 노출 | 소유권과 수명이 타입에 드러나지 않는다. 레거시 결함 원인 (A) "리소스 소유권이 주석에만 있다"의 재발 |

### 결과

- 긍정: 백프레셔·버퍼 재사용·세그먼트 경계 처리가 전송마다 재구현되지 않는다.
  TCP·인메모리·WebSocket·QUIC이 같은 계약에 들어온다
- 긍정: Core 무의존 유지. `CHSM0001` 가드가 계속 통과한다
- 부정: `ReadOnlySequence<byte>`는 연속 메모리가 아니다. **프레임 디코더가 세그먼트
  경계를 넘는 헤더를 반드시 처리해야 한다** — Stage 3의 퍼징 테스트 대상이다
- 부정: `PipeWriter`는 동시 쓰기를 허용하지 않는다. 다중 생산자 송신은 상위에서
  직렬화해야 한다(CLAUDE.md 9장 "공유하지 않는 것이 1순위")

## ADR-0007: 최대 프레임 크기는 전송 버퍼 한계 안에 들어가야 한다

- **날짜**: 2026-08-03
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(`ITransportBufferLimits`), `ChServerM.Hosting`(조립 검사), 모든 전송

### 배경

Stage 6 통합 테스트에서 **200KB 페이로드 왕복이 인메모리 전송에서 영구 교착**했다.
같은 테스트가 TCP 에서는 통과했다. 원인을 좁혀보니 축 두 개의 성질이 충돌하고 있었다.

| 축 | 성질 |
|---|---|
| 프레이밍 | 디코더는 **완전한 프레임이 오기 전에 아무것도 소비할 수 없다.** 부분 프레임을 소비하면 경계를 잃는다 |
| 전송 | 수신 버퍼는 **소비되지 않은 바이트가 임계값에 닿으면 쓰기를 멈춘다**(백프레셔) |

```
프레임 크기 > 전송 버퍼 임계값
  → 프레임이 다 오기 전에 버퍼가 참
  → 쓰기 정지, 그런데 디코더는 소비할 수 없음
  → 영구 교착
```

실측(인메모리, 임계값 64KiB):

| 임계값 | 페이로드 | 결과 |
|---|---|---|
| 64 KiB | 200 KB | **교착** |
| 64 KiB | 40 KB | 정상 |
| 512 KiB | 200 KB | 정상 |

**TCP 가 통과한 것은 운이었다.** 커널 소켓 버퍼가 초과분을 흡수했을 뿐이고,
페이로드가 더 컸다면 똑같이 교착한다.

**증상이 최악인 종류다.** 작은 프레임은 멀쩡히 오가다가 큰 메시지 하나에서만 멈추고,
예외도 로그도 없다. 커넥션이 그냥 응답하지 않는다 — 레거시 결함 유형 (C) "조용한 실패"와 같다.

**기본값 조합부터 어긋나 있었다.** `FramingOptions` 기본 1 MiB, 전송 기본 64 KiB.

### 결정

**조용한 교착을 조립 시점 예외로 바꾼다.**

1. Core 에 `ITransportBufferLimits`(`MaxBufferedBytesPerConnection`)를 둔다. 선택 구현이다
2. 네 전송(In-Memory·TCP × 서버·클라이언트)이 자기 `PauseWriterThreshold` 를 보고한다
3. `ServerBuilder`/`ClientBuilder` 가 `Build()` 에서 검사한다 —
   `헤더 + MaxPayloadLength > MaxBufferedBytesPerConnection` 이면 예외.
   메시지에 원인과 해결책 세 가지(임계값 상향 / 페이로드 상한 하향 / 조각화)를 담는다

**기본값은 맞추지 않는다.** 전송 기본을 1 MiB 로 올리면 커넥션당 방향당 1 MiB가 되어
1만 접속에 20 GB다. 프레이밍 기본을 64 KiB 로 낮추면 정당한 워크로드를 막는다.
어느 쪽도 옳지 않으므로 **조합하는 사람이 정하게 하고, 틀리면 시작 시점에 알린다.**

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 문서로만 경고 | 이 프로젝트가 레거시에서 배운 것과 정반대다. 규약을 주석에만 적으면 반드시 샌다(CLAUDE.md 9.7) |
| 전송 기본 임계값을 프레이밍 기본(1 MiB)에 맞춤 | 커넥션당 방향당 1 MiB. 1만 접속 = 20 GB. 레거시의 "커넥션당 64KB 고정 버퍼"(640 MB) 문제를 30배로 재현하는 셈 |
| 프레이밍 기본을 64 KiB 로 낮춤 | 64 KiB 넘는 메시지가 정당한 워크로드를 막는다. 그리고 사용자가 임계값을 낮추면 같은 문제가 되돌아온다 |
| 디코더가 부분 프레임을 소비하고 자체 버퍼에 모음 | 프레임당 복사가 생기고, 그 버퍼가 결국 상한 없는 큐가 된다. 지금 구조의 제로 카피가 무너진다 |
| 전송이 프레이밍을 알게 함 | 축 독립성이 깨진다. 전송은 바이트만 다뤄야 한다 |

### 결과

- 긍정: **조용한 교착이 시작 시점 예외가 된다.** 메시지가 원인과 해결책을 함께 알려준다
- 긍정: 축 독립성 유지. 전송은 프레이밍을 모르고, 프레이밍은 전송을 모른다.
  둘을 아는 조립 계층에서만 검사한다
- 부정: 기본값끼리 조합하면 실패한다. **의도된 것이지만 첫 사용자는 놀란다** —
  예외 메시지가 그만큼 친절해야 하는 이유다
- 부정: `ITransportBufferLimits` 를 구현하지 않는 전송은 검사되지 않는다.
  버퍼 개념이 없는 전송까지 강제할 수 없어 선택 구현으로 뒀다
- **미해결**: 조각화(`FrameFlags.Fragmented`)가 구현되면 임계값보다 큰 논리 메시지를
  보낼 수 있게 된다. 그때 이 검사는 "프레임 하나"에만 적용된다 — 재조립 버퍼의 상한은
  별도로 필요하다(Phase 9)

## ADR-0008: 파티션 배타성은 스레드 어피니티가 아니라 완료 대기로 보장한다

- **날짜**: 2026-08-04
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(`IExecutionPartition`, `IPartitionExclusiveWork`),
  `ChServerM.Concurrency`, `ChServerM.Hosting`
- **관계**: ADR-0005 의 **주 경로 구현 서술**("읽기 루프를 파티션 스케줄러에 고정하면
  모든 `await` 연속이 같은 스레드에서 이어진다 — 프레임당 큐 비용 0")을 **supersede** 한다.
  ADR-0005 의 결정 자체(키 기반 파티션 샤딩)와 확장성 검증 조건은 유지된다.

### 배경 — 주 경로가 반증됐다

2026-08-04 정밀 감사에서 네 가지 독립 발견이 하나로 수렴했다.

1. **구현**: 전송이 만드는 `Pipe` 가 `ReaderScheduler` 를 지정하지 않아(기본값 스레드풀)
   읽기 루프의 첫 미완료 `await` 연속이 스레드풀로 갔고, `ConfigureAwait(false)`(라이브러리
   규약, CLAUDE.md 8절)가 스케줄러 재캡처를 막아 **복귀 경로가 없었다**
2. **테스트**: 고정을 검증하던 단위 테스트는 `Task.Yield()` + `ConfigureAwait(true)` —
   스케줄러를 캡처하는, 실전과 정반대의 await 조합 — 으로만 검증했다
3. **통합**: 통합 하네스가 `ServerBuilder` 를 우회해 `PartitionedConnectionHandler` 를
   실행하는 테스트가 0개였다
4. **벤치마크**: 확장성 곡선이 청크 단위 실행이라 이 결함을 감지할 수 없는 측정이었다

프로덕션 조립 경로를 그대로 타는 반증 테스트로 고정한 결과: 핸들러 실행이 파티션
스레드를 이탈하고, **같은 파티션의 두 커넥션 핸들러가 병렬로 실행**됐다(동기 구간 겹침
실측). 더 나쁘게, 실행 위치가 프레임 도착 타이밍에 따라 비결정적이었다 — 데이터가 루프의
첫 `ReadAsync` 보다 먼저 오면 파티션 스레드에서, 늦게 오면 스레드풀에서 돌았다.

**근본 원인은 타이밍이 아니라 접근법이다.** 스레드 어피니티로 배타성을 얻는 설계는
`ConfigureAwait(false)` 를 쓰는 모든 코드(프레임워크 자신 포함)와 구조적으로 충돌한다.
사용자 핸들러의 어떤 `await` 든 스레드를 이탈시킬 수 있으므로, 완전한 어피니티는
사용자 코드까지 통제해야 성립한다 — 그것은 계약이 아니라 희망이다.

### 결정

**배타성의 정의를 바꾼다: "같은 스레드"가 아니라 "완료까지 다음 작업을 시작하지 않음".**

1. Core 에 `IPartitionExclusiveWork`(`ValueTask ExecuteAsync()`)와
   `IExecutionPartition.TryEnqueueExclusive` 를 추가한다. 파티션 소비 루프는 배타 작업이
   반환한 `ValueTask` 가 **완료될 때까지 다음 큐 항목을 시작하지 않는다**(전용 스레드
   블로킹 — 이 스레드의 존재 이유가 배타성 강제다)
2. 읽기 루프(`FramedConnectionHandler`)는 실행 모델이 있으면 프레임마다
   `PartitionDispatchGate`(커넥션당 1개 재사용, `IValueTaskSource` 기반)를 게시하고
   완료를 기다린다. 커넥션당 in-flight 1건이므로 자연 백프레셔이고 프레임당 할당 0이다
   (동기 완료 핸들러 기준 — 비동기 핸들러는 기존과 같은 상태 머신 예외)
3. `PartitionedConnectionHandler`(루프 시작 고정 데코레이터)는 삭제한다. 루프 시작
   지점 고정은 배타성에 아무 기여도 하지 않았다
4. `IExecutionPartition.Scheduler` 는 배타성 수단에서 **동기 구간 고정 수단**으로 강등하고
   문서에 명시한다
5. 보장 내용: 같은 파티션의 배타 작업은 **동시에 실행되지 않고**(await 걸침 포함),
   **게시 순서(FIFO)대로 시작**되며, **동기 구간은 파티션 전용 스레드에서** 실행된다

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| **파이프 스케줄러 주입** (전송의 `Pipe` 에 파티션 스케줄러를 `ReaderScheduler` 로) | 파이프 연속은 복귀시키지만 **핸들러 안의 비-파이프 `await` 는 여전히 이탈한다** — 계약에 예외 조항이 필요해지고, 그 예외가 곧 사용자가 밟을 지뢰다. 커넥션→파티션 배정을 파이프 생성 전으로 옮겨야 해 전송 축이 실행 모델을 알게 된다(축 결합) |
| **계약 축소** ("커넥션당 순차 실행"만 보장) | 코드 변경 0으로 현실과 문서를 일치시키지만, **샤드 상태를 락 없이 만진다는 ADR-0005 의 존재 이유를 포기**한다. Phase 13(세션)에서 같은 문제가 그대로 재부상한다 |
| **현상 유지** | 계약이 반증된 상태로 방치 — 사용자가 문서를 믿는 순간 조용한 데이터 레이스다. 레거시 `PkObjM` 과 동일한 실패 양식의 재현 |
| **완전 액터 런타임 도입** (Orleans / Proto.Actor) | ADR-0005 에서 탈락한 이유 그대로 — Core 무의존 위반, 런타임 종속. 어댑터 검토는 Phase 8 항목으로 유지 |

### 결과

- 긍정: **배타성이 사용자 코드의 await 방식과 무관하게 성립한다.** 계약 테스트 3종이
  프로덕션 조립 경로(`ServerBuilder` + 실제 `Pipe`)에서 고정한다
  (`PartitionExclusivityContractTests` — 반증 테스트를 계약 방향으로 뒤집은 것)
- 긍정: 실행 위치의 비결정성이 사라진다. 동기 구간은 항상 파티션 스레드다
- 부정: **프레임당 게시+완료 신호 왕복 비용이 생긴다 — 실측 +0.70µs/프레임 (ENV-B, P=1),
  약 1µs 작업 기준 총비용 1.94×.** 파티션당 커넥션 1개짜리 핑퐁 구조에서는 파티션을 늘리면
  깨우기 비용이 지배해 오히려 악화된다(P=8 에서 역확장 실측). 또한 이 측정이
  **프레임당 할당 ~170-184 B** 를 드러냈다 — 완료 신호의 스레드풀 큐 항목과 소비 루프
  대기의 `AsTask()` 가 원인이고, 후자는 구 설계에도 있었으나 청크 벤치마크가 가려왔다.
  상세와 교정 후보는 [BENCHMARKS.md](BENCHMARKS.md#2026-08-04--%EF%B8%8F-adr-0008-검증-프레임-단위-배타-왕복-메시지-단위-측정).
  구 설계의 "프레임당 큐 비용 0"은 애초에 실전에서 성립하지 않았으므로(매 프레임이
  스레드풀 큐를 경유) 이 수치는 회귀가 아니라 **처음 보이게 된 비용**이다
- 부정: **head-of-line blocking** — 비동기 핸들러가 완료될 때까지 같은 파티션의 다른
  커넥션이 대기한다. 이것은 액터 모델의 본질적 비용이다. 긴 I/O 를 하는 핸들러는
  파티션 실행 모델이 맞지 않는다(무상태 프로필을 쓰거나, 파티션 밖에서 처리 후
  `TryPost` 로 결과만 주입). 가이드는 Phase 20 문서화 항목으로
- **⚠ 교착 규약**: 배타 작업 안에서 **같은 파티션의** `Scheduler` 로 스케줄한 태스크를
  `await` 하면 교착한다(파티션이 그 작업의 완료를 기다리는 중이다). `IPartitionExclusiveWork`
  와 `ExecutionPartition` 문서에 명시했다. 컴파일 타임 검출은 Phase 20 진단 분석기 후보

### 검증

- 계약 테스트: 동기 구간 파티션 스레드 고정 / 같은 파티션 동기 핸들러 비중첩 /
  **await 를 걸치는 비동기 핸들러의 배타성** — 전부 프로덕션 조립 경로에서
- 메시지 단위 벤치마크: 프레임당 배타 왕복 비용과 파티션 수 스윕. 청크 단위 곡선
  (ADR-0005 검증)은 "실행 모델의 상한" 측정으로 재해석해 유지한다

## ADR-0009: Phase 5 부하 생성은 자체 부하 클라이언트로 한다

- **날짜**: 2026-08-04
- **상태**: 채택
- **영향 범위**: `Bench/`(부하 러너), Phase 5 게이트 측정, Phase 12 회귀 게이트

### 배경

Phase 5 게이트(1만 동시 접속 안정 동작 + p99 레이턴시 기준선)에는 종단 부하 생성이
필요하다. CLAUDE.md 기술 스택은 NBomber 를 후보로 명시했으나, 이 프레임워크의 전송은
커스텀 TCP 프레이밍이라 어떤 도구를 쓰든 와이어 포맷을 아는 클라이언트 코드는
직접 작성해야 한다.

### 결정

`Bench/` 에 **자체 부하 러너**를 만든다. `TcpClientTransport` + `ChServerM.Framing` 을
그대로 쓴다 — 부하 측정이 곧 클라이언트 경로의 검증이 된다. 레이턴시는 p50/p99/p999
분위수로 기록한다(BENCHMARKS.md 규칙).

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| NBomber 도입 | 커스텀 TCP 프레이밍에는 어차피 자체 클라이언트 팩토리가 필요해 기성품의 이점(시나리오·리포트)이 절반이다. Bench 외부 의존 +1, 상용 라이선스 확인 필요 |
| 둘 다(교차 검증) | 비용 두 배. Phase 12 회귀 게이트 설계 시 재검토 가능성은 열어 둔다 |

### 결과

- 긍정: 의존 0, 클라이언트 경로 동시 검증, 측정 코드가 프레임워크와 함께 진화
- 부정: 램프업·분위수 집계·리포트를 직접 구현한다. **부하 생성기 자체가 병목이면
  서버가 아니라 생성기를 재는 것이 된다** — 생성기 CPU 사용률을 결과와 함께 기록한다

## ADR-0010: 프레이밍 계약을 논리 엔벨로프와 와이어 헤더로 분리한다

- **날짜**: 2026-08-04
- **상태**: 채택
- **영향 범위**: `ChServerM.Core`(Framing·Dispatch), `ChServerM.Framing`, `ChServerM.Hosting`
- **관계**: 2026-08-04 정밀 감사 발견 **H4** 의 해소. ADR-0002(프레이밍·직렬화 분리)를
  한 단계 더 밀고 나간 것 — 이제 프레이밍 축 안에서도 "논리 계약"과 "와이어 포맷"이 분리된다

### 배경 — Core 가 특정 와이어 포맷에 결박돼 있었다

감사 발견 H4: 구체 와이어 포맷인 `FrameHeader`(16B 고정, 오프셋 상수, `CurrentVersion`)가
Core 에 있고, 계약 세 곳이 그것에 결박돼 있었다.

| 결박 지점 | 문제 |
|---|---|
| `IFrameEncoder.HeaderSize` | 헤더 크기가 상수라는 전제 — varint(가변 길이) 인코더가 구현 불가 |
| `FrameDecodeResult.Header` | 디코더가 16B 레이아웃 타입을 반환해야 함 — 다른 프레이밍은 없는 필드를 위조해야 함 |
| `MessageContext.Header` | 디스패치·미들웨어에 와이어 포맷이 노출 — HTTP 전송(`stateless-web`)은 `FrameHeader` 를 합성해야 함 |

이대로면 Phase 4 의 varint 디코더("두 번째 구현 전까지 `IFrameDecoder` 는 가설")와
Phase 16 의 `stateless-web` 프로필이 구조적으로 막힌다. **한쪽만 도는 추상화는
추상화가 아니다**(ADR-0004).

수정 시점이 지금인 이유: 결박된 API 전부가 `PublicAPI.Unshipped.txt` 에 있다.
Shipped 승격 후에는 파괴적 변경이다.

### 소비자 분석 — 무엇이 실제로 필요한가

- **디스패치가 소비하는 것은 `Header.MessageId` 하나뿐이다** (디스패처 라우팅 3곳 + 로깅 1곳)
- `Flags` 는 Phase 9 `IPayloadCodec`(압축·암호화 변환 표시), `Sequence` 는 리플레이 방지가
  소비할 예정 — 둘 다 **횡단 축이라 개념이 Core 에 있어야 한다**
- `Version`·오프셋 상수·`Size` 는 순수한 와이어 포맷 소유물 — Core 의 어떤 소비자도 쓰지 않는다
- `IFrameEncoder.HeaderSize` 의 유일한 소비자는 `CompositionGuard` 의 상한 계산 — 정확한
  크기가 아니라 **상한**이면 충분하다

### 결정

**Core 는 논리 엔벨로프만 알고, 와이어 헤더는 프레이밍 어댑터가 소유한다.**

1. Core 에 `MessageEnvelope`(readonly struct: `MessageId` + `FrameFlags` + `Sequence`)를
   신설한다. 디스패치·미들웨어가 소비하는 논리 메타데이터의 전부다
2. `FrameHeader`(레이아웃·오프셋·`CurrentVersion`)는 `ChServerM.Framing` 으로 옮긴다 —
   `FrameHeaderCodec` 옆, 원래 있어야 할 곳
3. `IFrameEncoder` 는 `WriteHeader(IBufferWriter<byte>, in MessageEnvelope, int payloadLength)`
   로 바꾼다. `IBufferWriter` 라 가변 크기 헤더가 자연 수용된다.
   `HeaderSize` 는 `MaxHeaderSize`(상한)로 교체 — `CompositionGuard` 는 상한으로 충분하다
4. `FrameDecodeResult.Header` / `MessageContext.Header` → `Envelope`
5. **표현 불가 값은 거부한다** — 와이어에 해당 필드가 없는 프레이밍(varint 등)의 인코더는
   기본값이 아닌 `Flags`/`Sequence` 를 받으면 예외를 던진다. 조용히 버리면 레거시의
   "압축이 한 번도 실행되지 않음"(FrameWriter 참조)과 같은 조용한 실패가 된다.
   반대로 디코더가 채우는 `Flags=None`/`Sequence=0` 은 "그 와이어에 그 개념이 없다"는
   사실의 표현이라 위조가 아니다

버전 협상(Phase 9 로드맵)과의 정합: 버전이 어댑터 소유가 되므로 협상된 버전은
커넥션 단위 상태로 어댑터가 관리한다. Core 상수였다면 협상 자체가 성립하지 않았다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| **최소 계약 + Features** — Core 는 `MessageId`+`Payload` 만, `Flags`·`Sequence` 는 `IFeatureCollection` 경유 | 압축·리플레이 미들웨어가 **프레임마다 feature 조회**(딕셔너리 + 캐스팅) — 핫패스 무할당·저비용 원칙과 충돌. `FrameFlags` 타입은 `IPayloadCodec` 계약 때문에 어차피 Core 에 남아 개념 제거 효과도 반감. 디코더 반환 경로까지 feature 로 옮기면 `FrameDecodeResult` 구조가 흐려진다 |
| **보류 — varint 프로토타입을 먼저 만들어 부딪히는 지점을 실측** | 부딪히는 지점은 이미 코드 조사로 특정됐다(위 표 3곳). 프로토타입이 추가로 알려줄 것이 없고, 그 사이 Shipped 승격이 일어나면 수정 비용이 파괴적 변경으로 뛴다 |
| **현상 유지** — varint 도 16B 헤더의 부분집합으로 우겨 넣음 | 없는 필드를 위조한 `FrameHeader` 를 만들게 된다 — 레거시의 "있는 척하는 헤더 필드"(체크섬 `return true`) 재현. `stateless-web` 은 여전히 막힌다 |

### 결과

- 긍정: varint·델리미터·HTTP 프레이밍이 계약 변경 없이 구현 가능해진다.
  `stateless-web` 프로필의 구조적 차단이 풀린다
- 긍정: 핫패스 비용 불변 — 엔벨로프는 struct 필드 접근이라 기존 `Header.MessageId` 와
  동일 비용. 할당 0 유지
- 긍정: 전부 Unshipped 단계라 파괴적 변경 비용 0
- 부정: `MessageEnvelope` ↔ `FrameHeader` 변환 지점이 어댑터에 생긴다(디코더가 헤더를
  읽고 엔벨로프로 투영). 비용은 필드 복사 수준이지만 개념이 하나 늘었다
- 부정: 표현 불가 값 거부가 **런타임 예외**다 — 압축 축을 varint 프레이밍과 조합하면
  첫 압축 프레임에서 터진다. 조립 시점 검출(인코더가 지원 능력을 보고하고
  `CompositionGuard` 가 대조)은 `IPayloadCodec` 이 실물이 되는 Phase 9 에서 재검토
- 부정: `FrameDecodeStatus.VersionMismatch` 등 버전 관련 상태는 Core 에 남는다 —
  버전 개념이 있는 프레이밍이 공통으로 쓰는 실패 분류라 일반적이다. 버전 "값"만
  어댑터로 내려간다

## ADR-0011: 직렬화 축 첫 어댑터로 MemoryPack 을 도입한다

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `ChServerM.Serialization.MemoryPack`(신설), `Directory.Packages.props`
- **관계**: ADR-0002 의 미결 항목(페이로드 직렬화 기본값)은 **이 ADR 이 결정하지 않는다.**
  이것은 "첫 구현" 선택이지 "기본값" 확정이 아니다 — 기본값은 Phase 6 의 4자 벤치마크
  (MemoryPack / FlatSharp / Protobuf 계열 / MessagePack-CSharp) 후 별도 ADR 로 확정한다

### 배경

Phase 6 진입. 직렬화 축은 `IMessageSerializer<T>` 계약과 테스트 전용
`Utf8StringSerializer` 만 있고 실동 어댑터가 없다. 축 증명(DoD-5)에는 두 번째 구현이
필요하므로 어느 쪽이든 "첫 번째"를 골라야 하고, 첫 구현은 계약의 압박 테스트를 겸한다.

### 결정

**MemoryPack 1.21.4 를 첫 어댑터로 도입한다.** 선택 기준은 셋이다.

1. **C#↔C# 최속 가설의 검증 대상** (CLAUDE.md 6절 초기 가설 1위) — zero-encoding 설계라
   "직렬화 비용 자체가 없는 쪽에 가까운" 상한을 먼저 세워야 4자 벤치마크의 기준선이 생긴다
2. **소스 제너레이터 기반** — "리플렉션 대신 소스 제너레이터" 하드 룰과 Native AOT
   게이트(CI)에 그대로 부합한다. 런타임 코드 생성이 전혀 없다
3. **계약 정합** — `IBufferWriter<byte>` 쓰기 / `ReadOnlySequence<byte>` 읽기 네이티브
   오버로드가 있어 Core 계약에 무변환 직결된다. 중간 배열이 구조적으로 생기지 않는다

구현에서 굳힌 계약 두 가지 (코드가 아니라 규약이므로 여기 기록한다):

- **엄격 소비** — 역직렬화가 페이로드를 끝까지 소비하지 않으면 실패. 프레이밍이 길이를
  정확히 주므로 잔여 바이트는 스키마 불일치이거나 조작이다
- **null 메시지 불허** — 인코더는 예외로 거부(조용한 유실 금지, ADR-0010 원칙),
  디코더는 null 로 풀리는 페이로드를 실패로 판정한다

### 구현 중 발견 — `IsRegistered` 의 거짓 음성

`[MemoryPackable]` 생성 코드는 포매터 등록을 **타입 정적 생성자**에 넣는데,
`MemoryPackFormatterProvider.IsRegistered<T>()` 는 수동 조회라 그 실행을 보장하지 않는다.
한 번도 만진 적 없는 타입이 "미등록"으로 오판되는 것을 테스트로 재현했다
(`Find_ColdPackableType_ReturnsSerializer`). 제공자가 미등록 판정 전에
`RuntimeHelpers.RunClassConstructor` 로 정적 생성자를 강제 실행해 해소했다 —
조립 시점 1회 경로라 비용은 없다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| Google.Protobuf / protobuf-net 을 먼저 | 크로스 언어 상호운용이 강점이나 그 요구가 아직 확정되지 않았다(ADR-0002). varint 인코딩 비용으로 속도 상한 기준선 역할을 못 한다. **두 번째 어댑터 1순위 후보로 유지** — 성질이 정반대(스키마 파일, 필드 태그, 가변 인코딩)라 계약 검증력이 가장 크다 |
| FlatSharp(FlatBuffers) 을 먼저 | 역직렬화 없는 랜덤 접근이 강점이지만 `TryDeserialize`→객체 모델에 얹으면 그 강점이 죽는다. 접근 패턴 축(lazy 접근)을 계약에 반영할지가 먼저 — 4자 벤치마크 시점에 판단 |
| MessagePack-CSharp 을 먼저 | 균형형이라 "가장 빠른 상한"도 "가장 이질적인 검증"도 아니다. 첫 구현의 목적 어느 쪽에도 최적이 아니다 |
| 테스트 전용 직렬화기로 버티고 Phase 6 전체를 벤치마크로 시작 | 실동 어댑터 없이 4자 벤치마크를 만들 수 없다. 순서가 역전된다 |

### 결과

- 긍정: 직렬화 축에 실동 구현 1호. 교체 테스트(`SerializerSwapTests`)로 같은 핸들러가
  직렬화기 교체만으로 동작함을 통합 수준에서 고정
- 긍정: 어댑터 격리 규약 준수 — MemoryPack 타입은 public 표면에 노출되지 않고,
  이 어셈블리를 지워도 Core 는 컴파일된다
- 부정: 트리밍 분석 억제 2건(IL2091·IL2059)이 어댑터에 생겼다. 근거는 코드 주석에
  기록했고, AOT 검증(CI)이 전제("생성 포매터만 사용")를 지킨다
- 부정: 스키마 진화·크로스 언어 검증은 미착수 — Phase 6 잔여 항목으로 남는다

## ADR-0012: Phase 6 잔여 직렬화 어댑터 — Google.Protobuf 와 FlatSharp 을 도입한다

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `ChServerM.Serialization.Protobuf`(신설), `ChServerM.Serialization.FlatBuffers`(신설),
  `Directory.Packages.props`, `eng/build.ps1`, `Bench/ChServerM.Bench`
- **관계**: ADR-0011 의 후속. 페이로드 기본값은 여전히 미결 — 4자 벤치마크 수치로
  별도 ADR 에서 확정한다

### 결정 1 — protobuf 는 Google.Protobuf 로 (protobuf-net 탈락)

두 번째 어댑터의 목적은 계약 중립성 증명(DoD-5)이다. MemoryPack 과 성질이 정반대인
protobuf 를 두 번째로 택했고, 구현체 두 후보 중 **Google.Protobuf 3.35.1** 을 채택했다.

| 대안 | 탈락 이유 |
|---|---|
| protobuf-net | POCO + 어트리뷰트가 장점이나 런타임 메타프로그래밍(IL emit) 기반 — "리플렉션 대신 소스 제너레이터" 하드 룰과 충돌. `ReadOnlySequence` 파싱·`IBufferWriter` 쓰기의 네이티브 지원도 Google.Protobuf 쪽이 정합 |
| Google.Protobuf | ✅ protoc 빌드 타임 생성, `ParseFrom(ReadOnlySequence)`/`WriteTo(IBufferWriter)` 직결, 공식 구현이라 크로스 언어 보증이 가장 강함 |

제공자는 **조립 시점 명시 등록**(`Register<T>()`) 방식이다 — 제약 없는 `Find<T>()` 안에서
`IMessage<T>` 제약이 걸린 직렬화기를 만들려면 `MakeGenericType` 리플렉션이 필요해
AOT 게이트와 충돌한다. MemoryPack 제공자(전역 판정)와 모양이 다른 것은 결함이 아니라
포맷 성질(스키마 생성 타입 전제)의 반영이다.

### 결정 2 — FlatSharp 어댑터는 Greedy 전용

`IMessageSerializer` 계약은 "호출이 끝나면 페이로드 무효"다. FlatSharp 의 Lazy/Progressive
역직렬화는 반환 객체가 버퍼를 계속 참조하므로 이 계약과 양립할 수 없다 —
**생성자가 Greedy 계열이 아닌 직렬화기를 조립 시점에 거부한다**(use-after-free 류 버그를
런타임이 아니라 조립에서 잡는다). 이 결정은 FlatBuffers 의 간판 기능(역직렬화 없는
랜덤 접근)을 버리는 것이다. 그 기능을 살리는 lazy 접근 축(페이로드 뷰 노출)은 계약
변경이 필요하므로, 벤치마크에서 Greedy 가 열세로 확인되고 실사용 요구가 생길 때
별도 ADR 로 다룬다.

부수 결정: FlatSharp.Compiler 는 net9.0 도구라 .NET 10 SDK 단독 환경에서 실행이
거부된다. `eng/build.ps1` 이 `DOTNET_ROLL_FORWARD=LatestMajor` 를 설정해 로컬·CI 가
같은 조건으로 재현되게 했다(수동 실행으로 도구가 10.0 런타임에서 정상 동작함을 확인).

### 결정 3 — MessagePack 은 벤치마크 비교군 전용, 어댑터를 만들지 않는다

4자 벤치마크(ADR-0002 잔여)에는 MessagePack 수치가 필요하지만, 어댑터 어셈블리는
만들지 않는다. 근거: MessagePack 의 포지션(균형형)은 MemoryPack(속도 상한)과
protobuf(크로스 언어)가 이미 덮는 구간과 겹쳐 **제품으로서의 세 번째 어댑터가
증명하는 것이 없다**. 벤치에는 `Bench` 내부의 최소 래퍼(표준 리졸버, IL emit)로 충분하며
JIT 전용 수치임을 명기한다. 실사용 요구가 생기면 그때 어댑터로 승격한다 —
어댑터 수 자체가 유지 비용이다.

### 스키마 진화 — 테스트로 고정한 포맷별 성질 (Phase 6 항목)

| 포맷 | 필드 추가(끝) | 비고 |
|---|---|---|
| protobuf | **양방향 호환** + 모르는 필드 왕복 보존 | 중계 시나리오까지 안전. 구버전 공존의 기본 후보 |
| FlatBuffers | 양방향 호환, 보존은 없음 | V1 리더가 다시 쓰면 V2 필드 소실 |
| MemoryPack 기본 | **단방향**: 구데이터→신리더만 허용 | 신데이터→구리더는 실패. 롤링 배포에서 반드시 발생하는 방향이라, 그 경계에는 `VersionTolerant` 명시 필요. 처음 가정(양방향 비호환)은 실측으로 정정했다 |
| MemoryPack VersionTolerant | 양방향 호환 | 멤버별 길이가 붙어 와이어가 커진다 |

### 결과

- 긍정: **직렬화 축 DoD-5 완성** — 실동 어댑터 3종. `SerializerSwapTests` 가 같은 핸들러
  코드를 Utf8/MemoryPack/Protobuf/FlatSharp 4직렬화기 × 교체로 고정
- 긍정: 명시 등록형 제공자라는 두 번째 제공자 형태가 나오면서
  `IMessageSerializerProvider` 계약 자체도 두 구현으로 증명됐다
- 부정: 코드 생성 도구 3종(protoc·FlatSharp.Compiler·MemoryPack 생성기)이 빌드에
  들어왔다. 전부 빌드 타임이고 런타임 의존은 각 포맷 런타임 dll 뿐이다
- 부정: 롤포워드 환경 변수는 빌드 스크립트 밖(IDE 단독 빌드)에서는 수동 설정이
  필요하다 — 해당 csproj 에 주석으로 남겼다

## ADR-0013: 페이로드 직렬화 기본값은 MemoryPack — ADR-0002 잔여 해소

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `Samples/`, 참조 프로필(ADR-0004), 문서의 기본 예시
- **관계**: ADR-0002 의 미결 항목("페이로드 직렬화 기본값") 해소.
  근거 수치: `BENCHMARKS.md` 2026-08-05 4자 벤치마크(ENV-B)

### 결정

**프레임워크의 기본 권장 직렬화기는 MemoryPack 이다.** 샘플·참조 프로필·문서의 기본
예시가 이것을 쓴다. "기본값"의 의미는 그것뿐이다 — 축이므로 조립에서 언제든 교체된다
(ADR-0004: 워크로드는 전제가 아니라 프로필이다).

### 근거 (2026-08-05 실측, ENV-B)

1. **왕복 최속** — small 왕복 104ns 로 2위(Protobuf 134ns) 대비 22%, 서버의 지배
   경로인 역직렬화 단독으로는 61.7ns vs 101.1ns (**39% 차이**). large 에서도 왕복 최속
2. **소스 제너레이터 + AOT** — 하드 룰과 게이트에 무조건 부합
3. 직렬화 경로 할당 0 이 어댑터 경유로 실측 확인됨

**초기 가설의 정정**: "MemoryPack 이 전 항목 최속"(CLAUDE.md 6절)은 부분 기각됐다.
소형 메시지의 직렬화 단독(33ns vs 43ns)과 와이어 크기(71B vs 85B)는 Protobuf 가 이긴다.
그래도 기본값이 MemoryPack 인 이유는 서버 워크로드의 지배 경로(수신·역직렬화)와
왕복 합 기준이기 때문이다.

### 크로스 언어 상호운용 — Phase 6 항목의 결론

**"클라이언트는 C#" 을 Core 의 전제로 넣지 않는다.** 비-C# 클라이언트 요구가 생기면
답은 어댑터 교체이고, 그 경로는 이미 실동한다 — Google.Protobuf 어댑터가 같은 핸들러
코드로 동작함을 `SerializerSwapTests` 가 고정하고 있고, 스키마 진화(양방향 + 모르는
필드 보존)도 protobuf 가 가장 강하다. 즉:

| 상황 | 권장 |
|---|---|
| C#↔C#, 성능 우선 (realtime-stateful 계열) | **MemoryPack** (기본값) |
| 비-C# 클라이언트, 공개 API, 구버전 장기 공존 | **Google.Protobuf** |
| 레거시 FlatBuffers 스키마 승계 구간 | FlatSharp (Greedy 제약 인지, ADR-0012) |

MemoryPack 채택 시 주의 계약 두 가지를 기본값의 조건으로 문서화한다:
(1) 롤링 배포로 신-구 버전이 공존하는 메시지는 `VersionTolerant` 를 명시한다 —
기본 모드는 신데이터→구리더 방향이 실패한다(스키마 진화 테스트로 고정).
(2) 스키마 불일치 감지는 포맷이 아니라 프레임워크 몫이다(Phase 9 버전 협상).

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| Protobuf 를 기본값으로 | 역직렬화가 39~64% 느리다. 크로스 언어는 "필요할 때 켜는 프로필"이지 기본 비용으로 지불할 전제가 아니다(ADR-0004) |
| FlatSharp 를 기본값으로 | Greedy 강제 상태에서 왕복·와이어 모두 우위 없음. lazy 축이 계약에 들어오면 재평가(ADR-0012) |
| MessagePack 을 기본값으로 | 왕복 최하위. 어댑터도 없다(ADR-0012 결정 3) |
| 기본값을 정하지 않음 | 샘플·문서·프로필이 매번 선택을 강요받는다. "기본값 없음"은 사용자에게 벤치마크를 떠넘기는 것이다 |

### 결과

- 긍정: Phase 6 게이트 조건("두 개 이상 어댑터 + 기본값 ADR") 충족
- 긍정: 선택 기준이 수치와 함께 문서화돼, 요구가 바뀌면(비-C# 클라이언트 확정 등)
  어느 지점에서 결론이 뒤집히는지 명확하다
- 부정: 기본값 주의 계약(VersionTolerant)은 사용자가 어길 수 있는 규약이다 —
  Phase 7 소스 제너레이터에서 진단으로 승격할 후보

## ADR-0014: 디스패치 소스 제너레이터 — 발견·검증·등록 생성의 1차 형태

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `ChServerM.SourceGen`(신설), `ChServerM.Core`(`MessageHandlerAttribute`),
  진단 대역 `CHSM1xxx`(docs/DIAGNOSTICS.md)
- **관계**: "리플렉션 대신 소스 제너레이터" 하드 룰의 디스패치 축 적용.
  ROADMAP Phase 7 의 1차 증분 — 스위치 테이블 직생성·폴백 디스패처·벤치마크는 후속

### 배경

수동 `Map<T>` 등록의 실패 — 중복 메시지 ID, 계약 미구현, 센티넬 ID 0 — 는 전부
런타임 조립 예외로만 드러난다. 상업용 프레임워크에서 "빌드는 됐는데 서버가 안 뜬다"는
사용자 경험 결함이고, 컴파일 타임으로 당길 수 있는 실패다.

### 결정

1. **발견은 어트리뷰트로** — Core 에 `[MessageHandler(ushort)]` 마커를 둔다(무의존이라
   비용 0, 핸들러 어셈블리는 제너레이터 없이도 컴파일된다)
2. **검증은 진단으로** — `CHSM1001~1007`(정본: docs/DIAGNOSTICS.md). 런타임이었다면
   조립 예외인 것은 전부 Error 다. 릴리스 추적(RS2008)은 AnalyzerReleases.*.md 로 —
   PublicAPI 승인 파일과 같은 "diff 를 리뷰에 노출" 게이트
3. **등록 생성은 인스턴스 매개변수 방식** — `MapGeneratedHandlers(builder, serializers,
   handler100, handler200, …)` 확장 메서드를 생성한다. 핸들러 인스턴스는 사용자가 만들고,
   직렬화기는 `IMessageSerializerProvider` 에서 조립 시점에 해석한다(누락 = 예외)
4. **Hosting 미참조 어셈블리에서도 검증은 돈다** — 핸들러 전용 라이브러리는 생성만
   건너뛰고(CHSM1007 경고) 진단은 그대로 적용된다
5. **Roslyn 4.14.0 고정** — 생성기는 호스트 컴파일러에 로드되므로 호스트보다 새
   Roslyn API 를 참조하면 로드 실패한다. SDK 10.0.1xx 호스트(5.x)보다 낮은 4.14 가 안전선
6. **증분 생성** — `ForAttributeWithMetadataName` + 값 동등성 record 모델.
   `Location` 은 값 표현(`LocationModel`)으로 바꿔 캐시를 깨지 않는다

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 핸들러 자동 인스턴스화 (`new()` 제약) | 의존(인코더·저장소) 있는 핸들러가 배제되거나 서비스 로케이터가 강요된다. DI 통합은 호스팅 계층의 축이지 제너레이터의 결정이 아니다 |
| DI 컨테이너 해석 코드 생성 | Phase 2 의 DI 축(MEDI vs Pure.DI/Jab)이 미결이다. 지금 굳히면 그 결정을 제너레이터가 선점한다 |
| `IMessageDispatcher` 스위치 문 직생성 | 현 라우팅(배열 인덱싱)과의 성능 차이가 미측정이다. "측정 없는 최적화 금지" — Phase 7 벤치마크(생성 vs 딕셔너리 vs 배열) 후 2차 증분에서 판단 |
| 리플렉션 스캔 등록 (어트리뷰트 + 런타임 발견) | 하드 룰 위반. AOT 에서 죽거나 트리밍으로 조용히 빠진다 — 개발 편의 폴백(Phase 7 잔여)으로만, AOT 비활성 조건부 |

### 결과

- 긍정: 중복 ID·계약 위반·센티넬이 **빌드 실패**가 됐다. 드라이버 테스트 9종이 진단을,
  스냅샷 테스트가 생성 코드 전문을, 통합 테스트가 종단(생성 코드 → 실제 파이프라인
  에코)을 고정한다
- 긍정: 소비자는 제너레이터를 분석기로만 참조한다(`ReferenceOutputAssembly=false`) —
  런타임 의존 0
- 부정: 생성 메서드 시그니처가 핸들러 수에 비례해 길어진다. DI 축이 확정되면
  오버로드 추가로 해소한다(그때 이 ADR 을 잇는다)
- 부정: 어트리뷰트 상수(`FrameworkRangeStart=40001`)가 생성기에 복제된다 —
  생성기는 Core 를 참조하지 않기 때문이다. 값 변경 시 두 곳을 고쳐야 한다(주석으로 결박)

### 2026-08-05 (2차) — 미결 질문 종결: switch 문 직생성은 하지 않는다

`DispatchBenchmarks`(ENV-B, BENCHMARKS.md 해당 절) 결과, 순수 라우팅에서 **배열
인덱싱 0.69ns vs switch 문 0.88ns** — 빌더가 시작 시점에 만드는 배열 테이블이 이미
switch 직생성보다 빠르다. 연속 ID 는 jump table 로도 인덱싱을 못 이기고, 희소 ID 는
이진 탐색으로 더 나빠진다. 따라서 제너레이터의 역할은 현행(검증 + 등록 생성)으로
확정하고, 디스패처 본체 생성은 하지 않는다.

부수 확정: Phase 7 게이트의 측정 조건("딕셔너리보다 빠름")은 배열 0.69ns vs
Dictionary 1.93ns(2.8×)로 충족. 리플렉션 폴백의 가격(20.5ns + 32B/호출)도 이때 함께
측정돼 "프로덕션 비권장" 근거가 수치로 남았다. AOT 실증은 EchoServer 샘플이
`[MessageHandler]` 생성 경로(+MemoryPack 어댑터)를 태우고 Native AOT publish 를
통과하는 것으로 완료 — ADR-0011 의 트리밍 억제 전제("생성 포매터만 사용")도 이
publish 가 함께 검증한다.

## ADR-0015: 조각 재조립은 연속성 계약 + 크기 상한으로, 타이머 없이

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `ChServerM.Hosting`(`FragmentAssembler`, `FramedConnectionHandler`,
  `FramedConnectionOptions.MaxAssembledMessageLength`, `FrameWriter.WriteFragmentedFrameAsync`)
- **관계**: ADR-0007 의 미해결 항목("조각 재조립 버퍼 상한") 해소. Phase 4 마지막 항목

### 배경

프레임 페이로드에는 상한이 있다(`MaxPayloadLength` — 없으면 길이 필드가 곧 메모리 할당
지시가 된다). 그보다 큰 논리 메시지는 `Fragmented`/`EndOfMessage` 조각으로 나뉘어야
하는데, 재조립에는 두 가지 위험이 있다: (1) 마지막 조각이 오지 않는 부분 메시지를
무한정 들고 있으면 메모리 고갈 공격 경로다, (2) 조각 상태가 어긋난 채 계속하면 재조립
결과가 조용히 오염된다(레거시 desync 와 같은 부류).

### 결정

**재조립은 커넥션 소유의 읽기 루프에서, 다음 계약으로 한다.**

1. **연속성** — 조각 메시지가 진행 중일 때 그 커넥션에는 같은 `MessageId` 의 조각만
   올 수 있다. 사이에 낀 비조각 프레임·다른 ID 는 프로토콜 오류로 커넥션을 닫는다
2. **상한** — 누적 길이가 `MaxAssembledMessageLength`(기본 1 MiB, 0 = 재조립 거부)를
   넘으면 즉시 닫는다. 최악 재조립 메모리는 `MaxConnections × 상한`으로 계산 가능하다
3. **미완성 만료는 전용 타이머 없이** — 연속성 계약 덕분에 "재조립이 멈춘 커넥션"은
   "아무것도 보내지 않는 커넥션"과 동치이고, 그것은 전송의 idle timeout(전송당 스윕
   타이머 하나)이 이미 끊는다. 무한 조각 공급은 상한이 끊는다. 커넥션당·메시지당
   타이머를 만들지 않는다(CLAUDE.md 9.5)
4. **조각은 도착 즉시 복사** — 파이프 버퍼는 `AdvanceTo` 로 반납되므로 참조를 들 수
   없다. 버퍼는 `ArrayPool` 대여 + 2배 성장이며, 메시지 완성 즉시 반납한다(유휴
   커넥션의 재조립 메모리 0). 반납 책임은 `FragmentAssembler.Reset` 하나로 모으고
   읽기 루프의 `finally` 가 종료 경로를 보장한다
5. **핸들러는 조각을 모른다** — 재조립분의 엔벨로프에서 조각 플래그를 걷어내고
   전달한다. `Compressed`/`Encrypted` 는 남는다(논리 메시지 전체에 적용된 사실의 기록,
   Phase 9). 송신은 `FrameWriter.WriteFragmentedFrameAsync` 가 분할·플래그를 맡는다 —
   플래그를 손으로 붙이다 생기는 중복·누락을 구조적으로 없앤다

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 조각 인터리브 허용(메시지 다중화) | 메시지별 재조립 맵 + 스트림 ID 가 필요해 HTTP/2 수준 복잡도가 된다. 커넥션의 프레임은 이미 전순서라 단일 진행 계약으로 충분하고, 진짜 다중화가 필요하면 그것은 프레이밍 축의 별도 구현이다 |
| 조각 인덱스/총개수를 와이어에 추가 | 헤더 확장(와이어 호환성 파괴) 대가로 얻는 것이 순서 검증뿐인데, TCP + 연속성 계약이 이미 그것을 보장한다 |
| 미완성 조각 전용 만료 타이머 | 커넥션당 타이머 금지(9.5) 위반. 연속성 계약 아래에서 idle timeout 과 완전히 중복된다 |
| 디코더가 재조립 | 디코더는 무상태·공유 인스턴스라는 Phase 4 결정과 충돌. 상태가 생기는 순간 커넥션마다 디코더를 만들어야 한다 |

### 결과

- 긍정: ADR-0007 의 마지막 미해결 항목이 닫혔다 — 큰 메시지는 이제 "임계값을 올린다"
  가 아니라 "조각화한다"가 정답이다. Phase 4 전 항목 완결
- 긍정: 위반 8경로가 통합 테스트로 고정됐다(`FragmentReassemblyTests`)
- 부정: 재조립은 복사다 — 조각당 1회, 성장 시 추가 복사. 큰 메시지가 핫패스라면
  그 프로토콜 설계가 문제다(스트리밍 축 후보). 무할당 목표의 예외 지점으로 기록한다
- 부정: 조각 프레임의 `Sequence` 는 첫 조각 것만 남는다 — 조각별 시퀀스 검증은
  Phase 9 리플레이 방지 설계에서 다시 본다

## ADR-0016: 버퍼 풀링 정책 — `ArrayPool.Shared` 래핑, 반납은 Dispose, 누수는 파이널라이저 관측

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: `ChServerM.Buffers`(신설, 무의존), 응답 직렬화 경로 전반
- **관계**: Phase 3 착수. 레거시에는 승계할 풀 구현이 없다(전부 참조 0 또는 검사 없는
  32줄 — [12-domain-util-discarded]) — 처음부터 설계한다

### 배경 — 지금 실제로 새는 곳이 어디인가

커넥션 수신·송신 버퍼는 `Pipe` 가 이미 풀링한다(블록 재사용). 프레이밍은 무할당,
디스패치도 무할당이다. 현재 요청당 할당이 실제로 남아 있는 곳은 **응답 직렬화
스크래치**다 — 헤더에 페이로드 길이가 먼저 필요하므로 직렬화기는 어딘가에 먼저 써야
하고, 예제·테스트가 쓰는 `ArrayBufferWriter` 는 그 "어딘가"를 매번 힙에 만든다.
레거시의 실패는 풀이 없어서가 아니라 **반납이 새는데 아무도 관측하지 못한 것**이었다.

### 결정

1. **풀은 `ArrayPool<byte>.Shared` 를 쓴다. 커스텀 슬랩 할당기는 지금 만들지 않는다** —
   커넥션 버퍼는 `Pipe` 가 풀링하고, 남은 수요(직렬화 스크래치)는 공유 풀로 충분하다.
   슬랩이 이기려면 공유 풀의 경합·단편화가 관측돼야 한다("측정 없는 최적화 금지").
   그 측정은 Phase 12 회귀 게이트·프로파일링에서 나온다
2. **대여 단위는 `PooledBufferWriter`** — `IBufferWriter<byte>` 계약의 풀 기반 구현.
   커넥션당 하나를 만들어 `Clear()` 재사용이 의도된 사용법이다(정착 상태 할당 0 —
   게이트 테스트로 고정)
3. **반납 책임은 소유자의 `Dispose()` 하나로 모은다.** 초과 크기는 2배 대여-복사-반납
4. **반납 누락은 조용히 사라지지 않는다** — 파이널라이저가 누수를
   `BufferPoolDiagnostics.LeakedBuffers` 로 계수하고 버퍼를 회수한다. 정상 경로는
   `GC.SuppressFinalize` 라 비용 0. ROADMAP 의 "DEBUG 빌드에서 추적"보다 강한 형태다 —
   Release 에서도 관측되고, 게이트 테스트가 의도적 누수로 검증하며, Phase 11 이
   이 카운터를 메트릭·경보로 승격한다

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| `ref struct` 스코프 가드로 반납 강제 | 컴파일 타임 보장은 가장 강하지만 **`async` 핸들러에서 쓸 수 없다**(`await` 경계를 못 넘는다). 응답 직렬화가 정확히 그 자리에 있다 |
| `IMemoryOwner<T>` 반환형 | Dispose 계약은 동일한데 쓰기 커서(`IBufferWriter`)가 없어 결국 래퍼가 하나 더 필요하다. 인터페이스 경유 비용만 늘어난다 |
| 커스텀 슬랩 할당기 선행 구현 | 수요의 근거가 없다(위 배경). 만들면 그것이 관측·튜닝 대상이 되어 유지 비용이 먼저 온다 |
| DEBUG 전용 누수 추적(ROADMAP 원안) | Release CI·프로덕션에서 눈이 먼다. 파이널라이저-온-리크는 정상 경로 비용 0으로 같은 것을 상시 제공한다 |

### 결과

- 긍정: Phase 3 게이트 충족 — 정착 왕복 할당 0(테스트), 의도적 누수 검출(테스트),
  요청당 비용은 BENCHMARKS.md 버퍼 절
- 긍정: 어셈블리가 무의존이다(Core 조차 참조 없음) — 어디서든 끌어다 쓸 수 있다
- 부정: 파이널라이저 기반 관측은 "언젠가"만 보장한다(GC 시점). 실시간 잔량은
  `RentedBuffers - ReturnedBuffers` 로 본다
- 부정: 슬랩 할당기 항목은 열려 있다 — 공유 풀 경합이 관측되면 재개한다

## ADR-0017: 전송 보안은 TLS 1.3 위임, 버전 협상은 보안 채널 안의 프레임워크 핸드셰이크

- **날짜**: 2026-08-05
- **상태**: 채택
- **영향 범위**: Core(`ITransportSecurity` 계약 + 핸드셰이크 메시지) / `ChServerM.Security.Tls`(신설 예정) / Hosting(조립 순서) / Framing(협상 후 버전 판정)

### 배경

- `docs/THREAT-MODEL.md` 가 요구를 고정했다: 키 교환·기밀성·무결성(T-01·04·08·09·10)과
  버전 협상 요구사항 R-1~R-5. 레거시 자체 암호 계층은 전량 폐기 판정이다
  ([legacy/07-security](legacy/07-security.md) — XOR, 고정 IV CBC, 미인증 RSA, 커넥션당 키쌍 생성).
- `ITransportSecurity` 는 Phase 1 잔여로 계약이 아직 없다 — 이 결정이 계약의 형태를 정한다.
- 현행 유일 버전 정책 "프레임 버전 불일치 = 종료"는 무중단 롤링 배포와 구조적으로 충돌한다
  (2026-08-04 감사).

### 결정

1. **전송 보안의 기본 구현은 TLS 1.3(`SslStream`)이다. 자체 암호 프로토콜을 만들지 않는다.**
   서버 인증서가 T-01(MITM)을, AEAD 레코드가 T-04·T-08 을, 레코드 계층 nonce 관리가 T-09 를,
   Finished 의 transcript 검증이 T-02(다운그레이드)를 담당한다 — 전부 검증된 구현으로.
   레거시가 전멸한 지점(키 교환·nonce·무결성)을 직접 다시 설계하지 않는 것 자체가 1차 완화책이다.
2. **`ITransportSecurity` 계약은 "커넥션 수립 직후 양방향 바이트 경로를 감싸는 데코레이터"다.**
   전송 중립 — TCP·InMemory 어디에나 같은 방식으로 끼운다(소켓 없이 TLS 경로를 통합 테스트
   가능). Core 에는 계약만 두고(무의존 유지) `SslStream` 은 `ChServerM.Security.Tls` 에 격리한다.
   "없음"(내부망·개발)도 유효한 조립이다 — 이것은 축이다. QUIC 처럼 TLS 를 내장한 전송은
   이 축이 "이미 적용됨"을 선언하는 특례로 수용한다(이중 암호화 금지).
3. **버전 협상은 보안 채널 확립 후 프레임워크 핸드셰이크 1왕복이다.**
   `ClientHello`(지원 `[min, max]`) → `ServerHello`(교집합 최고 버전 확정) 또는
   `ConnectionRejected`(40004, 지원 범위 포함) 후 종료. 협상이 TLS **안**에서 일어나므로
   R-4(다운그레이드 방지)는 별도 transcript 재검증 없이 구조적으로 충족된다.
   협상 후 프레임 버전 불일치는 그때부터 종료 사유다 — 현행 정책은 폐기가 아니라
   "협상 후 단계"로 자리를 옮긴다(R-1: 핫패스 무분기 유지).
   핸드셰이크 프레임 자체는 **헤더 v1 + 고정 바이너리 레이아웃으로 영구 동결**하고
   직렬화 축에 의존하지 않는다 — 교체 가능한 축 위에 부트스트랩을 얹으면
   축 교체가 와이어 호환성을 깨는 모순이 생긴다(R-2).
4. **리플레이 방어(T-05)를 재배치한다.** 커넥션 내 와이어 리플레이·재정렬은 TLS 레코드 계층이
   이미 차단한다 — 앱 계층 시퀀스 검증을 중복 구현하지 않는다(레거시 `pid` 개념은 승계하지 않음).
   크로스 커넥션 리플레이(캡처한 토큰 재사용)는 인증 계층의 몫이다(1회용·만료 토큰, Phase 9
   `IAuthenticator`). 보안 축 "없음" 조립은 이 보호가 없음을 계약 문서에 명시한다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 자체 ECDHE + AEAD 핸드셰이크 | 감사받지 않은 자체 설계를 프로덕션에 두는 위험. PFS·세션 재개·인증서 회전·다운그레이드 방지 전부 재발명 대상이 된다. 레거시가 정확히 이 길(자체 프로토콜)에서 전량 폐기됐다 |
| Noise Protocol Framework | 프로토콜 자체는 건전하나 .NET 성숙 구현·운영 생태계(인증서 발급·회전 도구)가 없다. AOT 호환 검증 부담까지 지면서 TLS 1.3 대비 얻는 것이 없다 |
| TLS 밖(평문) 협상 + 키 확립 후 transcript 재검증 | TLS Finished 가 이미 하는 일을 앱 계층에서 재구현한다. 코드와 실수 표면만 는다. 협상을 채널 안으로 넣으면 통째로 사라지는 비용이다 |
| 다중 버전 상시 병행 수용(협상 없음) | 프레임마다 버전 분기가 핫패스에 들어오고(R-1 위반) 다운그레이드 방지 지점이 없다(R-4 위반) — THREAT-MODEL 5절에서 기각 |
| 전송마다 TLS 내장 구현 | 전송 축 × 보안 축 조합이 곱으로 폭발한다. 데코레이터면 합이다 |

### 결과

- 긍정: T-01·02·04·05(와이어)·08·09·10 이 검증된 구현 하나로 완화된다. Phase 9 에 남는
  앱 계층 작업이 명확해진다 — 상태별 화이트리스트(T-19)·인증(T-20)·인가(T-21)·압축 정책(T-11·18)
- 긍정: 버전 협상이 암호 설계와 분리된다 — 보안 축 "없음" 조립에서도 협상은 동일하게 동작한다
- 부정: `SslStream` 은 `Stream` 기반이라 Pipelines 경로(ADR-0006)와 어댑터가 필요하다.
  이 비용은 **측정으로 방어한다** — TLS on/off 의 RPS·p99·할당 비교가 Phase 9 게이트 벤치에
  포함된다(측정 없는 최적화 금지의 역방향 적용: 측정 없는 "느릴 것" 추정으로 자체 구현을
  정당화하지 않는다)
- 부정: 인증서 운영(로딩·검증·회전) 부담이 생긴다 — 옵션·문서가 제품의 일부가 된다.
  개발·테스트 경로는 자가서명 헬퍼로 낮춘다
- 부정: 핸드셰이크 1왕복만큼 접속 지연이 는다(TLS 1.3 1-RTT + 협상 1-RTT).
  0-RTT(early data)는 리플레이 표면을 여는 기능이라 채택하지 않는다

## ADR-0018: 비밀번호 해싱은 ASP.NET Core Identity PasswordHasher 위임

- **날짜**: 2026-08-06
- **상태**: 채택
- **영향 범위**: Core(`IPasswordHasher` 계약) / `ChServerM.Security.AspNetIdentity`(신설 어댑터) / 신규 의존 `Microsoft.Extensions.Identity.Core`

### 배경

- Phase 9 인증 축(`IAuthenticator`, T-20)의 구현 재료로 비밀번호 해싱이 필요하다.
- 레거시 판정([legacy/07-security](legacy/07-security.md))이 `AuthM` 의 `PasswordHasher<T>`
  채택을 **레거시 보안 코드 중 유일한 승계 자산(🟢 Phase 9)**으로 지정했다.
  단, 네 가지 결함과 함께다: 호출마다 해셔 생성(#2), 파라미터 미명시(#4),
  `internal` 격리(#3), 그리고 호출부의 결과 무시(#1 — 이것은 T-20 으로 미들웨어가 해소).

### 결정

1. **Core 에 `IPasswordHasher` 계약**(무의존), 구현은 신설 어댑터
   `ChServerM.Security.AspNetIdentity` 에 격리한다 — 벤더(`Microsoft.Extensions.Identity.Core`)는
   이 어셈블리에만 존재하고, 삭제해도 Core 는 컴파일된다.
2. **구현은 `PasswordHasher<T>`(V3) 위임.** PBKDF2-HMAC-SHA256 + 비밀번호별 랜덤 솔트 +
   반복 횟수·버전 태그 내장 형식 — 검증된 구현을 위임하는 것이 1차 완화책이다(ADR-0017 과
   같은 원칙). **레거시와 같은 라이브러리·형식이므로 기존 계정 해시가 그대로 검증된다** —
   계정 이전 경로가 살아 있고, 이것이 직접 구현 대비 결정적 이점이다.
3. **레거시 결함을 계약으로 해소한다.** 해셔는 1회 생성 재사용(#2), 반복 횟수는 생성자
   명시 + 기본값 OWASP 600,000(#4 — 라이브러리 기본 100,000 은 정책 부재의 연장이다),
   재해싱 신호(`SuccessRehashNeeded`)를 enum 으로 표면화. 손상 해시의 `FormatException` 은
   어댑터가 `Failed` 값으로 변환한다(저장소 오염이 인증 경로의 예외 비용으로 증폭되지 않게, T-16).

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| BCL `Rfc2898DeriveBytes` 로 직접 형식 정의 | PBKDF2 자체는 같지만 솔트·반복 횟수·버전을 담는 저장 형식과 업그레이드 경로를 재발명해야 한다. 레거시 해시 형식 호환도 잃는다 — 얻는 것은 의존 하나 줄이는 것뿐 |
| Argon2id (권장 최신 KDF) | .NET 표준 구현이 없어 서드파티(Konscious 등) 검증 부담 + 레거시 해시 이전 시 전 계정 강제 재설정. 형식에 버전 태그가 있으므로 필요 시 어댑터 추가로 점진 전환 가능 — 지금 문을 닫는 결정이 아니다 |
| `Microsoft.AspNetCore.Cryptography.KeyDerivation` 직접 사용 | `PasswordHasher` 가 그 위에 얹은 형식·버저닝이 정확히 우리가 필요한 부분이다. 아래 계층으로 내려가면 형식 재발명(첫 번째 대안과 동일) |
| Core 에 구현까지 포함 | Core 무의존 하드 룰 위반. 논외 |

### 결과

- 긍정: 레거시 계정 DB 이전 경로 유지(형식 호환 테스트로 고정). 반복 횟수 상향이
  기존 해시를 깨지 않고 재해싱 신호로 흡수된다
- 긍정: T-20 완화가 완결된다 — 검증(이 ADR) + 결과 강제(`AuthenticationMiddleware`)
- 부정: Microsoft.Extensions 계열 신규 의존 1개. 단 어댑터에 격리되어 있어 계약만 두고
  구현을 교체(Argon2id 등)하는 비용이 낮다
- 부정: 기본 600,000 회는 로그인당 수십 ms CPU 다 — 의도된 비용이며, 워크로드별 조정은
  생성자 인자로 열려 있다(값은 항상 코드에 드러난다)

## ADR-0019: 압축 축 첫 어댑터는 LZ4(K4os), 블롭은 자기서술 + 해제 상한 강제

- **날짜**: 2026-08-06
- **상태**: 채택
- **영향 범위**: Core(`IPayloadCodec` 계약) / `ChServerM.Compression.LZ4`(신설 어댑터, 신규 의존 `K4os.Compression.LZ4`) / Hosting(송신 정책 + 수신 해제 통합)

### 배경

- Phase 9 항목 + Phase 1 잔여 계약. 위협 모델이 계약 요구를 고정했다:
  압축→암호화 순서(T-11, CRIME 류)와 해제 출력 상한(T-18, 압축 폭탄).
- 레거시는 LZ4 를 의도했으나 `maxLength >= originDataLen` 이 항상 참이라 **한 번도
  실행되지 않았고**, 해제는 와이어 길이 값으로 곧장 할당해 메모리 고갈 경로였다
  ([legacy/07-security](legacy/07-security.md) 결함 #1·#6, T-12).

### 결정

1. **계약 형태가 위협 완화를 강제한다.** `TryDecode` 의 `maxDecodedLength` 는 필수
   인자다 — 구현체가 상한 검사를 생략할 수 없다(T-18). 블롭은 자기서술(원본 길이
   접두)이라 **버퍼를 잡기 전에** 선언 길이를 검증한다(T-12 의 역). 해제 실패는
   값(T-16). 압축→암호화 순서는 구조가 보장한다 — 압축은 페이로드 수준, TLS 는
   그 바깥의 스트림 수준이라 뒤집힐 방법이 없다(T-11 잔여인 비밀 문맥 혼합은
   `PayloadCompressionOptions.DoNotCompress` 제외 목록).
2. **첫 어댑터는 LZ4(`K4os.Compression.LZ4`, FAST 레벨 고정).** 실시간 메시지 압축의
   정석 — 압축률보다 속도. 관리형 구현이라 AOT 호환. 레벨 옵션은 벤치 수치와 함께만
   추가한다(측정 없는 옵션 표면 금지).
3. **송신 정책은 조립에 있다.** 문턱(기본 1024B, 레거시 정책 승계) / 제외 목록 /
   압축 이득 없으면 평문 — 전부 `WriteCompressedFrameAsync` 가 판정하고
   `Compressed` 플래그를 스스로 붙인다(플래그·변환 불일치가 구조적으로 불가능).
4. **알고리즘은 조립 수준 합의다.** 와이어의 `Compressed` 플래그는 알고리즘을 말하지
   않는다 — 양쪽이 같은 코덱을 조립하며, 불일치는 해제 실패 = 종료. 코덱 미조립 +
   압축 프레임 수신도 종료다(압축 바이트가 조용히 핸들러에 가는 것이 레거시형 조용한 실패).
5. **무결성은 이 축의 몫이 아니다.** LZ4 블록에는 무결성 검사가 없고 추가하지도
   않는다 — 가짜 무결성 장치는 레거시 가짜 체크섬의 재판이다. 무결성은 전송 보안
   축의 AEAD 가 담당한다(T-04).

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| BCL Brotli 첫 어댑터 (의존 0) | 실시간 메시지엔 인코딩이 느리다 — 벤치 비교군으로 세워 수치로 확인(BENCHMARKS.md 압축 절). 의존 하나 아끼자고 기본 경로가 느려지는 선택 |
| Zstd (ZstdSharp 등) | 압축률·속도 균형은 우수하나 첫 어댑터 자리는 최속이 맞다. 축 규칙대로 두 번째 어댑터 후보 — 벤치 후 판단 |
| LZ4 프레임 형식(자체 길이·체크섬 내장) | 블록 형식 + 4B 접두 대비 오버헤드·구현 표면만 는다. 체크섬은 AEAD 와 중복(결정 5) |
| varint 길이 접두 | 접두는 코덱 내부 형식이라 프레이밍 축의 varint 코덱을 참조할 수 없다(어댑터 간 의존). 4바이트 절약보다 고정 형식의 단순성 |
| 해제 상한을 옵션 문서로만 요구 | "문서로만 적은 규약은 반드시 샌다"(레거시 반복 패턴). 계약 인자로 박아 생략 불가로 |

### 결과

- 긍정: T-11·T-18 완화가 계약 표면에 고정된다. "압축이 실제로 실행됨"이 테스트로
  고정된다(레거시 무동작의 역)
- 긍정: 조각화와 직교 조합된다 — 압축 전체 메시지 → 조각화, 재조립 → 해제
  (`FragmentAssembler` 의 플래그 보존이 설계 시점부터 이것을 예비했다)
- 부정: 신규 의존 1개(K4os). 어댑터 격리로 교체 비용 낮음
- 부정: 해제 경로에 커넥션당 해제 버퍼 상한(`MaxDecompressedMessageLength`, 기본 1MiB)
  만큼의 최악 메모리가 추가된다 — `MaxConnections × 상한` 계산은 옵션 문서에 명시

## ADR-0020: 관측 축 첫 어댑터는 `System.Diagnostics.Metrics`(BCL Meter), 계측은 데코레이터

- **날짜**: 2026-08-06
- **상태**: 채택
- **영향 범위**: Core(`IMetricsSink`·`MetricTag` 계약) / `ChServerM.Observability`(신설 어댑터, BCL 전용 — 새 의존 0) / Hosting(데코레이터 배선)

### 배경

- Phase 11 목표는 "**실패가 관측되는가**"다. 레거시는 메트릭이 하나도 없어 조용한 실패
  (압축 미실행·재시도 무효·만료 미동작)를 아무도 몰랐다([09-observability](legacy/09-observability.md)).
- 메트릭 **이름 계약**은 이미 있다(`DiagnosticNames`/`MetricNames`/`TagNames` — 2026-08-04
  정비). 없던 것은 축 계약(`IMetricsSink`)과 어댑터.
- Phase 9 가 조용한 실패 지점마다 `EventId` 로그 이벤트를 이미 깔아뒀다(리플레이·인증
  실패·포화·압축 위반·인증서 재적재). 관측 루프를 닫는 한계 비용이 낮은 시점이다.

### 결정

1. **Core 에 `IMetricsSink` 계약**(무의존): `Count`(카운터)/`Record`(히스토그램)/
   `AdjustGauge`(up-down). 태그는 중립 `MetricTag`(문자열 값 전용 — 값 타입 박싱과
   커넥션 ID 카디널리티 사고를 타입이 막는다)의 `ReadOnlySpan` 으로 받아 핫패스 무할당.
   기본은 `NullMetricsSink`(로거와 같은 null 없는 구조).
2. **첫 어댑터는 `System.Diagnostics.Metrics`(BCL `Meter`).** `dotnet-counters`/
   `dotnet-monitor` 가 즉시 읽고, **OpenTelemetry 메트릭 SDK 는 이 `Meter` 를 구독**하는
   얇은 설정 계층이라 나중에 OTel 을 얹어도 재계측이 아니라 배선만 추가하면 된다.
   새 패키지 의존이 0인 것도 이 선택의 몫이다. `Counter.Add` 는 구독자가 없으면 거의
   무비용이라 게이트에도 유리하다.
3. **계측은 데코레이터로**(CLAUDE.md 4 — 횡단 관심사는 코어 로직을 오염시키지 않는다).
   커넥션 생명주기는 `MetricsConnectionHandler`(가장 바깥 — TLS·협상 실패도 "수락됐다"는
   세고 활성 게이지가 전 생애를 덮는다, 감소는 `finally`), 디스패치 지연·처리량·실패는
   `MetricsMiddleware`(파이프라인 가장 바깥 — 지연이 전체를 감싼다). `UseMetrics()` 한
   번이 둘을 올바른 순서로 배선한다.
4. **첫 증분은 좁게.** 축 계약 + Meter 어댑터 + 커넥션·디스패치 데코레이터 + 오버헤드
   벤치(게이트). 트레이싱(`ActivitySource`)·헬스체크·ZLogger·런타임 로그 레벨·프레임당
   바이트 카운터(읽기 루프 계측)는 후속 증분 — "Core 인터페이스 → 참조 구현 → 벤치" 규칙.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| OpenTelemetry SDK 직접 첫 어댑터 | OTLP 익스포터까지 한 번에 가지만 새 패키지 의존 여럿 + 핵심 계측과 익스포트 설정이 한 증분에 섞여 벤치 게이트가 복잡해진다. OTel 이 어차피 `Meter` 를 구독하므로 BCL 을 먼저 깔면 OTel 은 나중에 배선만 |
| `IMetricsSink` 없이 `Meter` 직접 사용 | 관측은 교체 가능한 축(축 표 "관측")이다. Core 에 BCL 계측 타입을 노출하면 무의존·교체 가능성이 깨진다 |
| 태그를 `object?` 값으로 | 값 타입 태그가 프레임마다 박싱된다. 문자열 전용 + 스팬 전달로 핫패스 할당 0 |
| 프레임당 바이트 카운터를 이번에 | 읽기 루프 직접 계측이라 데코레이터로 안 된다 — 코어 로직 오염. 좁은 첫 증분에서 제외, 후속 |
| 계측을 읽기 루프·핸들러에 직접 | 코어 로직이 관측 코드로 오염된다(레거시가 `Debug.WriteLine` 을 곳곳에 흩뿌린 것과 같은 부류) |

### 결과

- 긍정: `UseMetrics(new MeterMetricsSink())` 한 줄로 `dotnet-counters` 가 즉시 읽는다.
  OTel·Prometheus 는 나중에 `MeterProvider` 구독 설정만 추가(재계측 없음)
- 긍정: 관측 없는 조립(`NullMetricsSink` 기본)의 핫패스 비용이 0에 가깝다(벤치로 방어)
- 부정: 트레이싱·헬스체크·바이트 카운터가 아직 없다 — 후속 증분. Phase 11 은 다증분이다
- 부정: 데코레이터는 커넥션·디스패치 경계의 신호만 본다. 프레이밍 내부(바이트·프레임
  드롭)는 읽기 루프 계측이 필요해 다음 증분으로 미뤘다

## ADR-0021: 과부하 제어 축 — `IAdmissionControl`(전송 주입) + 신규 연결 토큰 버킷 첫 구현

- **날짜**: 2026-08-06
- **상태**: 채택
- **영향 범위**: Core(`IAdmissionControl`·`AdmissionDecision` 계약) / Hosting(참조 구현
  `ConnectionRateAdmissionControl`·`CompositeAdmissionControl`) / 전송 어댑터 2종(옵션 주입·거부 배선)

### 배경

- Phase 10 게이트: "과부하에서 거부하며 살아남고, 24h soak 에서 메모리가 평탄"할 때.
  전반부("거부하며 생존")의 핵심이 신규 연결 수용 제어다.
- 정적 상한(`MaxConnections`)과 거부 통지(`RejectionNotice`)는 Phase 5 에 이미 있다(T-14
  절반). 없던 것은 **동적** 판정 — 상한 <b>안</b>에서 일어나는 연결 폭주(SYN 폭주·재접속
  스톰)는 정적 상한을 통과해 accept·핸드셰이크 CPU 를 그대로 때린다(T-16).
- Phase 11 메트릭에 `ConnectionsRejected` 이름이 이미 있다 — 거부를 관측으로 잇기만 하면 된다.

### 결정

1. **Core 에 `IAdmissionControl` 계약**(무의존): `AdmissionDecision TryAdmit(EndPoint?)`.
   실패는 값(거부는 정상 동작 — 판정마다 예외를 던지면 그것이 자원 소모 경로). `AdmissionDecision`
   은 `default = 거부`(가장 제한적 기본값). `Try` 는 소비형 부수효과(토큰 소비)를 알린다.
2. **삽입 지점은 전송 계층이다.** 판정에 필요한 원격 주소·수락 시점은 전송만 안다.
   계약은 Core 에 두고 구현을 전송 옵션(`AdmissionControl`)으로 주입한다 — `RejectionNotice`
   와 같은 주입 패턴. 정적 상한 통과 후에만 물어보고, 거부하면 기존 거부 경로를 재사용한다.
3. **첫 참조 구현은 신규 연결 토큰 버킷**(`ConnectionRateAdmissionControl`, 전역 속도).
   정적 상한이 못 막는 연결 폭주를 신규 연결 <b>속도</b>에 상한을 둬 막는다. 버스트 용량이
   정상 러시를 흡수하고 지속 속도가 폭주를 막는다. **`System.Threading.RateLimiting` 을
   쓰지 않고 손수 만든다** — 커넥션 수용은 커넥션당 1회(프레임당이 아님) 저빈도라 락 기반
   토큰 버킷이 명백히 정확하고 무의존이다. RateLimiting 의 슬라이딩 윈도우·파티션 정교함은
   메시지 수준 `IRateLimiter`(증분 2)에서 값을 한다.
4. **거부는 전송이 메트릭으로 방출**한다. 거부된 커넥션은 핸들러에 닿지 않아
   `UseMetrics` 의 핸들러 데코레이터가 못 본다 — 전송 옵션에 `IMetricsSink` 를 주입해
   `ConnectionsRejected`(저카디널리티 사유 태그: `connection_limit`/`admission`)를 방출한다.
   정적 상한 거부와 동적 수용 거부가 같은 `RejectConnection` 경로를 공유한다.
5. **첫 증분은 좁게** — `IAdmissionControl` 만. `IRateLimiter`(메시지 수준, RateLimiting +
   ADR), 백프레셔 생산 배선, 서킷 브레이커·Bulkhead, 24h soak 하네스는 후속 증분.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| `System.Threading.RateLimiting` 을 수용 제어에 | 커넥션 수용은 저빈도(커넥션당 1회)라 손수 토큰 버킷이 정확·무의존. 패키지의 정교함은 메시지 수준(고빈도·파티션별)에서 값을 한다 — 거기서 도입(증분 2) |
| 정적 `MaxConnections` 만으로 충분 | 상한 안의 연결 폭주(SYN·재접속 스톰)를 못 막는다 — accept·핸드셰이크 CPU 소진(T-16) |
| 동시 접속 소프트 상한 + 히스테리시스 | 정적 하드 상한과 역할이 겹치고, 새 연결 폭주(빠른 연결·해제 반복)를 못 막는다 |
| 메모리 워터마크 | 현실적이나 테스트 결정성이 낮고(GC 시점 의존) 신호가 느리다 — 후속 구현 후보 |
| 호스팅 계층에 삽입 | 판정에 필요한 원격 주소를 호스팅이 모른다. 전송만 안다 |
| 거부를 admission control 이 자기 sink 로 | 정적 상한 거부(전송 내부)는 여전히 미관측으로 남는다. 전송이 두 거부를 한 지점에서 방출해야 일관 |

### 결과

- 긍정: T-14(연결 폭주)의 동적 제어 절반과 T-16(핸드셰이크 CPU 소진)의 연결 속도 방어가
  구현된다. 거부가 `ConnectionsRejected` 로 관측된다(Phase 11 토대 활용)
- 긍정: 컴포지트로 축이 조합 가능 — 전역 속도 + (후속) IP별 + 워터마크를 AND 로 건다
- 부정: 첫 구현은 전역 속도라 단일 악성 IP 를 구분하지 못한다 — IP별 제한은 상태·정리
  정책이 필요한 별도 구현(후속). 전역 속도가 프로세스 CPU 를 지키는 1차 방어다
- 부정: `IRateLimiter`·백프레셔 생산·24h soak 는 아직 없다 — Phase 10 은 다증분이다

## ADR-0022: 분산 추적은 `ActivitySource` 를 Hosting 에서 직접 방출 (Core 중립 인터페이스 없음)

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: Hosting(`TracingMiddleware`·`ServerBuilder.UseTracing`) / Core(태그 이름
  `TagNames.ConnectionId` 만 추가 — 계약 상수). Core 는 트레이스 API 를 참조하지 않는다.

### 배경

- Phase 11 관측의 세 축(메트릭·로그·추적) 중 추적만 비어 있었다. 이름 계약
  (`ActivityNames.Connection`·`ActivityNames.Dispatch`, `DiagnosticNames.ActivitySourceName`)은
  2026-08-04 에 이미 정의돼 있었다 — 방출만 배선하면 되는 상태.
- 메트릭은 `IMetricsSink`(Core 중립 인터페이스) + `MeterMetricsSink`(어댑터)로 감쌌다(ADR-0020).
  추적도 대칭으로 `ITraceSink` 를 둘지가 갈림길이었다.

### 결정

1. **추적은 `System.Diagnostics.ActivitySource` 를 Hosting 에서 직접 방출한다.** Core 에 중립
   `ITraceSink` 를 두지 않는다.
2. **이유 — 추적의 교체 지점은 방출자가 아니라 구독자다.** OpenTelemetry·Jaeger·Application
   Insights 는 전부 `Activity` 를 이름으로 **구독**(`ActivityListener`)하지 방출 API 를 바꾸지
   않는다. 방출자는 하나뿐이고 대안 구현이 없으므로, Core 인터페이스는 "두 번째 구현이
   오기 전의 가설"(CLAUDE.md 3)이고 프레임당 span 핸들 할당이라는 비용만 남긴다.
3. **Core 무의존은 유지된다.** `ActivitySource`/`Activity` 는 공유 프레임워크(`Microsoft.NETCore.App`)라
   패키지 참조가 없고(메트릭 `Meter` 와 동일), Core 는 이 API 를 참조하지 않는다 — span 은
   Hosting 두 데코레이터에서만 난다.
4. **fast-path — 리스너 없으면 데코레이터가 사라진다.** `TracingMiddleware` 는
   `ActivitySource.HasListeners()` 가 false 면 `next` 를 **async 래퍼 없이 그대로 반환**한다.
   이는 2026-08-06 관측 벤치가 남긴 "데코레이터 async 비용(Null 싱크에서도 6→43ns)"의 해법이다 —
   추적에는 켜짐/꺼짐을 구분하는 값싼 신호가 있어 가능했다(측정: 리스너 없음 8ns/0B vs 기준선 6ns).
5. **이번 증분은 디스패치 span 만.** `ActivityNames.Connection`(커넥션 전 생애) span 은 연기.
   실행 모델(ADR-0008)에서 디스패치는 파티션 스레드에서 돌고 `Activity.Current` 는 AsyncLocal 이라
   채널 핸드오프를 넘지 못한다 — 부모 연결은 커넥션의 `ActivityContext` 를 `MessageContext` 로
   실어 명시적으로 넘기는 별도 배선이 필요하다. 지금은 `connection_id` span 속성으로 상관시킨다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| Core `ITraceSink` 중립 인터페이스(메트릭과 대칭) | 추적의 교체 지점은 구독자(ActivityListener)라 방출자 추상화는 두 번째 구현이 없다. 프레임당 span 핸들 할당(래퍼 객체) 또는 struct 핸들 API 확장 비용만 생긴다 |
| 커넥션 span 을 이번에 함께 | 파티션 스레드 크로스로 `Activity.Current` 가 안 흘러 부모 배선이 별도 필요. 장수명 span·export 시점 문제도 별도 판단이 낫다 |
| `UseTracing(sink)` 로 싱크 주입(메트릭처럼) | 방출자가 하나뿐이라 주입할 대상이 없다. 구독은 프로세스 밖 `ActivityListener` 가 한다 |
| 항상 배선(opt-in 아님) | 관측은 조립 선택이어야 한다(축 규약). fast-path 로 비용이 낮아도 opt-in 을 유지 |

### 결과

- 긍정: 관측 3축(메트릭·로그·추적) 완성. 커넥션·메시지 종류별 트레이스 상관이
  `connection_id`·`message_id` span 속성으로 가능하다
- 긍정: fast-path 로 리스너 없는 조립이 8ns/0B — 메트릭 미들웨어의 async 래퍼 비용(43ns)을
  추적에서는 회피했다. 이 패턴은 켜짐/꺼짐 신호가 있는 다른 데코레이터에도 적용 후보다
- 부정: 커넥션 span·부모-자식 트리는 아직 없다 — 크로스 스레드 부모 배선이 후속(→ 후속 완료)
- 부정: 추적은 Hosting 에 `ActivitySource` 를 직접 묶는다(메트릭보다 결합이 강함). 그러나
  이는 표준 .NET 추적 계약이고 벤더 패키지가 아니므로 어댑터 격리가 불필요하다

### 후속 (2026-08-07): 커넥션 span + 크로스 스레드 부모 전파 완료

위 "부정"의 첫 항목(커넥션 span·부모-자식 트리)을 완성했다. correlation ID 전파가 이로써
닫힌다.

- **메커니즘**: `TracingConnectionHandler`(가장 바깥 데코레이터)가 커넥션 수립 시
  `ActivityNames.Connection` span 을 열고, 그 `ActivityContext` 를 `ConnectionTraceFeature`
  로 커넥션 기능에 1회 싣는다. `TracingMiddleware` 는 파티션 스레드에서 이 컨텍스트를 읽어
  디스패치 span 의 **명시적 부모**로 넘긴다.
- **왜 `Activity.Current` 가 아니라 명시적 전파인가**: 실행 모델(ADR-0008)에서 디스패치는
  파티션 스레드에서 돌고 `Activity.Current`(AsyncLocal)는 채널 핸드오프를 넘지 못한다.
  커넥션 기능은 "수립 시 1회 Set, 그 뒤 읽기만" 규약이라 락 없이 안전하고(Set 이 첫 디스패치보다
  앞서고 채널 게시-소비가 가시성 보장), 커넥션 GC 가 정리를 공짜로 한다.
- **결정 — 전 생애 부모 span**(사용자 승인): 커넥션 span 하나가 수립~종료까지 열려 그 커넥션의
  모든 디스패치 span 의 부모가 된다. 제대로 된 부모-자식 트리. **트레이드오프**: 장수명 커넥션은
  종료 시 export 라 trace 가 늦게 보이고 자식이 많이 쌓인다 — 볼륨은 리스너 `Sample`(head
  샘플링)으로 조절(표준 운영). 탈락: 짧은 커넥션 span + 공유 컨텍스트만(자식이 부모보다 늦게
  시작하는 시간 역전) / 현재 유지 + 인바운드 W3C traceparent(프레임에 필드 없음, 프로토콜 변경 필요).
- **fast-path 보존**: 부모 조회(커넥션 기능 Get)는 `HasListeners()` 게이트 뒤에서만 일어난다 —
  리스너 없는 조립의 핫패스는 여전히 8ns/0B(feature 접근조차 없음).
- **결과**: 실행 모델(파티션 스레드) 아래에서도 디스패치 span 이 커넥션 span 의 자식(같은
  TraceId·부모 SpanId)이 됨을 종단 테스트로 고정. 새 public 표면 없음(전 타입 internal).

## ADR-0023: 헬스 체크 축 — Core 최소 계약 + 프로그래밍 우선, HTTP 노출은 후속

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: Core(`IHealthCheck`·`HealthStatus`·`HealthCheckResult`·`HealthReport` 계약) /
  Hosting(`HealthCheckService`·`HealthProbe`·내장 체크·`ServerLifecycleState`) /
  Concurrency(`PartitionedExecutionModel` 이 `IHealthCheck` 구현)

### 배경

- Phase 11: "헬스체크 / 라이브 진단 엔드포인트 — liveness / readiness 구분". 오케스트레이터
  (k8s 등)가 "프로세스가 살아 동작하는가(liveness)"·"트래픽 받을 준비가 됐는가(readiness)"를
  물을 수 있어야 한다.
- 조사로 확정한 전제 둘: (1) **HTTP 전송이 없다** — 데이터 평면은 raw TCP + 커스텀 프레이밍,
  헬스를 얹을 기존 HTTP 서버가 없다. (2) **생명주기가 이미 readiness 전이를 모델링한다** —
  `StartAsync`(수용) → `UnbindAsync`(드레이닝) → `StopAsync`(정리).

### 결정

1. **Core 에 최소 헬스 계약**(무의존): `IHealthCheck`(`ValueTask<HealthCheckResult> CheckAsync`),
   `HealthStatus`(Unhealthy=0 최악=기본값), `HealthCheckResult`, `HealthReport`. ASP.NET Core 가
   검증한 형태라 "두 번째 구현 없는 가설"이 아니다. `Microsoft.Extensions.Diagnostics.HealthChecks`
   (패키지)를 Core 가 참조할 수 없어 최소 계약을 직접 둔다.
2. **프로브 소속은 계약이 아니라 등록에 둔다**(`HealthProbe` [Flags], Hosting). liveness·readiness 는
   같은 체크를 다르게 쓰는 것이라 체크 자신이 아는 것이 아니다 — Core 계약을 최소로 유지.
3. **집계는 "가장 나쁜 것이 이긴다"** + **항목별 try/catch**. 한 체크의 예외가 전체 헬스
   조회를 깨지 않는다(소비 루프 항목 격리와 같은 원칙, 9.2). 헬스가 예외로 터지면
   오케스트레이터가 프로세스를 오판한다.
4. **내장 readiness = 생명주기.** `ServerLifecycleState`(Created→Accepting→Draining→Stopped)를
   `ChServerMServer` 가 갱신하고 `AcceptanceReadinessCheck` 가 읽는다 — 생명주기와 readiness 가
   한 진실을 공유. `UnbindAsync` 즉시 Draining 으로 전이해 무중단 배포 때 로드밸런서가 트래픽을 뺀다.
5. **내장 liveness = 실행 모델이 `IHealthCheck` 를 구현.** `PartitionedExecutionModel` 이 파티션
   스레드 생존을 보고한다. 호스팅은 `_executionModel is IHealthCheck` 면 liveness 로 자동 등록 —
   **Core 실행 모델 계약(`IExecutionModel`)에 진단 멤버를 얹지 않고, 호스팅이 Concurrency 를
   참조하지 않고도 배선**되는 접점이다. liveness 는 확정적 고장(스레드 사망)만 본다 — 교착
   감지(진행도 하트비트)는 후속.
6. **이번 증분은 프로그래밍 API 까지**(`server.Health.CheckHealthAsync(probe)`). HTTP 노출
   (`/healthz`·`/readyz`)은 별도 어댑터 몫 — HTTP 관리 서버는 별개 축(HttpListener vs Kestrel
   ADR·별도 어셈블리)이라 "먼저 경계를 긋고 하나씩"(CLAUDE.md 1.4) 원칙으로 분리한다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| `Microsoft.Extensions.Diagnostics.HealthChecks` 채택 | 패키지 의존 — Core 무의존 위반. 최소 계약이면 충분하다 |
| 이번 증분에 HTTP 엔드포인트 포함 | HTTP 호스팅은 별개 축(전송 미구현). 헬스 생산을 먼저 올바로 긋고 노출은 후속(요청 범위를 임의로 넓히지 않는다) |
| liveness 를 `IExecutionModel` 에 멤버로 | 실행 모델 축 계약에 진단 관심사를 얹는다. `IHealthCheck` 옵트인 구현이 계약을 오염 안 시키고 배선을 준다 |
| readiness 상태를 헬스가 따로 관리 | 생명주기와 두 진실이 어긋난다. 서버가 이미 아는 상태를 공유하는 것이 옳다 |
| 프로브 소속을 `IHealthCheck` 에 | 같은 체크가 두 프로브에 쓰일 수 있다 — 등록의 몫이 맞다 |

### 결과

- 긍정: readiness 가 무중단 배포(`UnbindAsync`)에 즉시 반응, liveness 가 실행 모델 스레드
  사망을 잡는다. 프로그래밍으로 완전 조회·테스트 가능(9종 테스트). 무의존·새 라이브러리 0.
- 긍정: 실행 모델이 `IHealthCheck` 를 구현하는 패턴은 세션 저장소·전송 등 다른 어댑터도
  같은 방식으로 헬스에 기여할 수 있는 확장 접점이다.
- 부정: HTTP 엔드포인트가 없어 k8s 프로브가 아직 직접 못 쓴다 — 관리 HTTP 어댑터가 후속.
- 부정: liveness 는 스레드 사망만 본다(교착 미감지). 진행도 하트비트 기반 liveness 는 후속.

## ADR-0024: HTTP 헬스 노출은 `System.Net.HttpListener` + 프로브 델리게이트(Core 만 참조)

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: 신규 어셈블리 `ChServerM.Diagnostics.Http`(`HealthHttpEndpoint`·`HealthHttpOptions`) /
  Core(`HealthProbe` 를 Hosting 에서 이동)

### 배경

- ADR-0023 에서 헬스 생산·집계·프로그래밍 API 를 만들되 HTTP 노출은 후속으로 미뤘다.
  k8s liveness/readiness 프로브는 HTTP GET 이므로, 오케스트레이터가 직접 쓰려면 엔드포인트가 필요하다.
- 이 프레임워크엔 HTTP 전송이 없다(데이터 평면 raw TCP) — 헬스 HTTP 는 별도 admin 서버여야 한다.

### 결정

1. **HTTP 스택은 `System.Net.HttpListener`.** 2라우트 GET 헬스 엔드포인트에 Kestrel(ASP.NET Core
   호스팅 모델)은 과하다. HttpListener 는 BCL 공유 프레임워크라 패키지 의존이 0이고, AOT 분석기도
   깨끗하다(clean 빌드 경고 0). 응답 본문은 <b>평문</b> — 프로브는 상태코드만 보므로 JSON(과 그
   직렬화·AOT 비용)을 들이지 않는다. 상태 매핑: 정상·저하 → <c>200</c>, 비정상 → <c>503</c>
   (저하는 경고이지 프로브 실패가 아니다).
2. **어댑터는 Core 만 참조하고, 헬스 소스를 델리게이트로 받는다**
   (`Func<HealthProbe, CancellationToken, ValueTask<HealthReport>>`). 그러려면 `HealthProbe` 를
   Hosting → Core 로 옮긴다 — `HealthStatus`·`HealthReport` 와 같은 헬스 값 타입 계열이다.
   그 결과 일방 의존(어댑터 → Core)이 유지되고("Server 어셈블리가 Hosting 참조"라는 첫 사례를
   만들지 않는다), 엔드포인트가 임의의 헬스 소스에 재사용된다. 표준 사용법은
   `new HealthHttpEndpoint(server.Health.CheckHealthAsync, options)`.
3. **별도 어셈블리로 격리.** HTTP 헬스 노출을 안 쓰는 소비자(프로그래밍 API 로 충분·사이드카가
   노출을 대신하는 배포)가 HttpListener 표면을 프로세스에 끌고 가지 않아야 한다(Observability 가
   Meter 를, Security.Tls 가 SslStream 을 격리하는 규율).
4. **항목별 격리.** 한 요청의 예외(프로브 실패·연결 끊김)가 accept 루프를 죽이지 않는다 —
   500 으로 응답하고 계속(소비 루프 항목 격리, 9.2). 프로브는 순차 처리(저빈도라 동시성 불필요).

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| Kestrel | 2라우트 헬스엔 과함 + ASP.NET Core 호스팅 모델을 헬스 어댑터에 끌어들임. HttpListener 로 충분 |
| 어댑터가 Hosting 참조(HealthCheckService 직접) | "Server 어셈블리 → Hosting" 첫 사례로 일방 의존을 흐린다. 델리게이트면 Core 로 족하다 |
| JSON 응답 본문 | 프로브는 상태코드만 본다. STJ 직렬화·AOT 비용을 헬스 어댑터에 들일 이유가 없다(본문은 curl 디버그용 평문) |
| 데이터 평면 프로토콜에 헬스 메시지 | k8s 프로브는 HTTP 다. 커스텀 TCP 메시지는 그 용도를 못 채운다 |

### 결과

- 긍정: k8s 등이 `/healthz`·`/readyz` 를 직접 프로브할 수 있다(200/503). 무의존·AOT 클린.
  엔드포인트가 헬스 소스와 분리돼 테스트가 스텁 델리게이트로 Core 만으로 완결된다(6종).
- 긍정: `HealthProbe` 가 Core 로 가며 헬스 값 타입이 한곳에 모였다(HealthStatus·HealthReport·HealthProbe).
- 부정: HttpListener 는 일부 환경에서 URL ACL(Windows netsh)·방화벽 설정이 필요하다 —
  기본 루프백은 사이드카·같은 파드 안에서만 닿는다. 외부 인터페이스 노출은 운영이 함께 본다.
- 부정: TLS·인증이 없는 평문 admin 엔드포인트다 — admin 포트를 외부에 노출하지 않는 전제다(관례).

## ADR-0025: 바이트는 전송이 push, 풀 카운터는 pull(`ObserveCounter`) — 배선은 관측 어셈블리가 가져간다

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: Core(`IMetricsSink.ObserveCounter` 기본 메서드 추가, 풀 메트릭 이름 3종) /
  Observability(`ObserveCounter` 구현 + `BufferPoolMetrics` + Buffers 참조) / Transport.Tcp(바이트 계측)

### 배경

- Phase 11 의 남은 메트릭은 "프레임당 바이트·큐 깊이·풀 카운터"였다. 큐 깊이는 2026-08-07
  백프레셔 증분에서 끝났고, 바이트와 풀이 남았다.
- 조사에서 셋의 성격이 전혀 다름이 드러났다.
  - **바이트**: 전송이 정확한 값을 안다(`SocketConnection` 수신 루프의 소켓 반환값). TCP·InMemory
    옵션에 `MetricsSink` 가 이미 배선돼 있다(Phase 10).
  - **풀**: `BufferPoolDiagnostics` 가 rented/returned/leaked 를 **이미 세고 있다**(정적·누적).
    문제는 (a) `IMetricsSink` 가 push 전용이고 (b) `ChServerM.Buffers` 는 **"Core 조차 참조하지
    않는다"가 의도된 결정**이라(csproj 주석) `IMetricsSink` 를 볼 수 없다는 것.
  - **`FramesSent`**: `FrameWriter` 가 static 확장 메서드라 싱크를 주입할 수 없다 — 이번 범위 밖.

### 결정

1. **바이트는 전송 계층이 push 한다.** 소켓 경계가 `bytes.received`/`bytes.sent` 의 정의(실제로
   회선을 건넌 바이트)와 일치하는 유일한 지점이다. 계측 호출이 **소켓 연산당 1회**라(프레임당이
   아니다 — 한 번의 read 가 여러 프레임을 실어온다) syscall 비용에 묻힌다. 전송 실패한 바이트는
   세지 않는다(`finally` 뒤에서 센다).
2. **회선이 없는 전송은 이 메트릭을 내지 않는다.** 인메모리 전송은 파이프를 직접 건네므로
   "회선을 건넌 바이트"가 존재하지 않는다 — 없는 개념을 억지로 만드는 대신(PipeReader/Writer
   래핑은 핫패스에 가상 호출을 더한다) 내지 않고 계약에 명시했다. 그 조립에서 0인 것은 정상이다.
3. **풀 카운터는 pull 이다.** `IMetricsSink.ObserveCounter(name, Func<long>, tags)` 를 추가하되
   **기본 구현을 무동작으로 둔다**(default interface method) — 기존 구현체가 깨지지 않고,
   pull 을 지원하지 않는 싱크는 그 메트릭이 안 나올 뿐이다. 어댑터는 BCL
   `Meter.CreateObservableCounter` 로 위임하므로 pull 의미가 그대로 성립한다(중간 저장·타이머 불필요).
   **push 였다면 대여·반납마다 메트릭 호출이 붙는데, 그 지점은 가장 뜨거운 경로 중 하나다.**
4. **풀 배선은 관측 어셈블리가 가져간다.** `ChServerM.Observability` 가 Buffers 를 참조하고
   `BufferPoolMetrics.Register(sink)` 를 둔다. 풀은 카운터를 노출만 하고, 그것을 메트릭 이름
   계약에 잇는 책임은 관측 쪽이다 — **Buffers 의 무의존 결정을 깨지 않는다.** 일방 의존
   (Observability → Buffers·Core)이라 순환이 없다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 바이트를 커넥션 데코레이터(PipeReader/Writer 래핑)로 | 핫패스 읽기·쓰기마다 가상 호출이 붙고, 소비 위치 계산(SequencePosition 산술)이 까다롭다. 전송이 이미 정확한 값을 안다 |
| 바이트를 디스패치 미들웨어에서(payload 길이) | 페이로드는 회선 바이트가 아니다(헤더 제외·압축 해제 후). 송신은 아예 못 본다(FrameWriter static) |
| 풀 카운터를 push(대여·반납 시) | 가장 뜨거운 경로에 메트릭 호출. 이미 세어진 값을 다시 push 할 이유가 없다 |
| `Buffers → Core` 참조 후 풀이 직접 배선 | csproj 에 명시된 "의존 0" 결정을 깬다 — superseding ADR 이 필요한 변경인데 얻는 것이 배선 위치뿐이다 |
| 앱이 직접 배선 | 새 엣지는 0이지만 자동이 아니라 빠뜨리기 쉽다. 관측 배선은 관측 어셈블리의 몫이 일관적이다 |
| `IMetricsSink` 에 메서드 추가 대신 별도 인터페이스 | 싱크 하나가 두 계약을 갖게 되고 어댑터가 캐스팅을 해야 한다. 기본 메서드가 더 단순하다 |

### 결과

- 긍정: `bytes.received`/`bytes.sent` 가 TCP 에서 실물로 나온다(회선 기준, 보안 축이 있으면 암호문 기준).
  풀 카운터 3종이 `dotnet-counters` 에 즉시 보이고, **`pool.buffers.leaked != 0` 이 경보 대상**이 된다.
- 긍정: pull 개념이 생겨, 앞으로 "이미 세어지고 있는 값"(세션 수·캐시 항목 등)을 핫패스 비용 0으로
  내보낼 수 있다.
- 부정: `FramesSent` 는 여전히 생산자가 없다 — `FrameWriter` 가 static 확장이라 싱크 주입 지점이
  없다. 별도 판단이 필요한 API 문제로 남긴다.
- 부정: 인메모리 조립에서는 바이트 메트릭이 0이다(설계상 정상이나, 대시보드를 두 전송에 공유하면
  혼동할 수 있어 계약 문서에 명시했다).

## ADR-0026: 주소별 연결 속도 제한 — 고정 슬롯 배열(축출 없음) + IPv6 프리픽스 집계

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: Hosting(`PerAddressConnectionRateAdmissionControl`·`PerAddressConnectionRateOptions`).
  Core 계약·전송 배선은 그대로 재사용 — 새 축이 아니라 `IAdmissionControl` 의 두 번째 구현이다.

### 배경

- ADR-0021 이 명시적으로 미뤄둔 항목이다: "첫 구현은 전역 속도라 **단일 악성 IP 를 구분하지
  못한다** — IP별 제한은 **상태·정리 정책이 필요한 별도 구현**(후속)".
- 전역 제한만 있으면 악성 IP 하나가 전역 예산을 빨아들여 **정상 사용자가 함께 거부된다** —
  공격자가 원하는 결과다(T-14·T-16).

### 결정

1. **상태는 시작 시 고정 크기 슬롯 배열이다 — 축출 메커니즘이 없다.**
   주소→버킷을 `Dictionary` 에 담으면 공격자가 소스 주소를 바꿔가며 접속하는 것만으로 맵이
   무한히 자라 **OOM 으로 죽는다** — 방어하려던 자원 고갈을 방어 코드가 대신 일으킨다.
   고정 배열은 **구조적으로 유계**라 스윕 타이머·항목당 할당·락 경합이 아예 존재하지 않는다
   ("무제한 큐 금지"의 같은 원리, CLAUDE.md 9.6). 구조체 배열이라 런타임 할당 0.
2. **대가는 해시 충돌이다(수용).** 두 주소가 한 슬롯을 공유하면 한쪽이 다른 쪽을 제한할 수
   있다. 슬롯 수를 활성 주소 수보다 넉넉히 잡아 확률을 낮추고, 충돌해도 리필이 수 초 안에
   회복시킨다. 정확한 계정이 필요하면 축출 정책이 있는 다른 구현을 쓴다 — 그 교환을 옵션이
   아니라 **타입으로 갈랐다**.
3. **표적 충돌 공격은 프로세스별 랜덤 시드로 막는다.** 해시가 고정이면 공격자가 피해자와 같은
   슬롯에 떨어지는 주소를 계산해 그 슬롯을 고갈시키는 표적 DoS 가 가능하다. `HashCode` 는
   프로세스마다 무작위 시드를 쓰므로(BCL 해시 플러딩 방어) 그 계산이 성립하지 않는다.
4. **IPv6 는 프리픽스로 집계한다(기본 `/64`).** 최종 사용자에게도 `/64` 이상이 통째로
   할당되므로 주소 하나 단위 제한은 공격자에게 **2^64 개의 우회로**를 준다 — 방어가 성립하지
   않는다. `/64` 를 하나의 주체로 센다. IPv4 는 /32, **IPv4 매핑 IPv6(`::ffff:a.b.c.d`)는
   IPv4 로 되돌린다**(듀얼스택 소켓이 그 형태로 넘기므로, 안 되돌리면 같은 클라이언트가 두
   주체로 갈려 제한이 두 배로 느슨해진다).
5. **주소를 모르면 판정하지 않고 통과시킨다.** 원격 종단이 IP 가 아니면(인메모리 전송 등)
   이 규칙은 할 말이 없다 — 거부가 아니다. 총량 방어는 컴포지트의 전역 규칙이 계속 맡는다.
6. **범위는 신규 연결 수용까지다.** 메시지 수준 속도는 `PerConnectionRateLimiter` 가 이미
   담당한다. 주소별 메시지 제한은 핫패스(프레임당)에서 주소 조회·공유 상태 경합이 생기므로
   별도 판단으로 남긴다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 유계 딕셔너리 + 유휴 축출 | 정확하지만 스윕 타이밍·락 경합·항목당 할당이 따라온다. 유계로 만드는 순간 "상한 도달 시 무엇을 버리나"라는 정책이 또 생긴다 |
| `System.Threading.RateLimiting` (`PartitionedRateLimiter`) | 새 패키지 의존 + 파티션당 할당·내부 타이머를 받아들여야 한다. ADR-0021 이 수용 제어에 이미 탈락시킨 이유(커넥션당 1회 저빈도)가 그대로 유효 |
| IPv6 를 /128 로 제한 | 공격자에게 2^64 우회로. 방어가 성립하지 않는다 |
| 주소를 거부 사유 문자열에 포함 | 그 문자열이 메트릭 태그로 흘러가면 카디널리티가 무한이라 시계열이 폭발한다(TagNames 규약) |
| 슬롯별 락 스트라이핑 | 경합이 측정되지 않았다. 이 규칙은 보통 전역 규칙과 함께 쓰이는데 그쪽이 이미 직렬화 지점이라 이득이 없다(측정 없는 최적화 금지) |
| 슬롯 구조체 캐시 라인 패딩 | 커넥션당 1회 저빈도이고 단일 락 뒤라 이득이 없다. 16,384 슬롯이면 패딩만 1MB |

### 결과

- 긍정: 악성 주소 하나가 전역 예산을 고갈시켜 정상 사용자를 함께 거부시키는 경로가 닫힌다.
  `CompositeAdmissionControl` 로 전역 규칙과 AND 결합 — 전역이 총량을, 주소별이 개별 학대자를.
- 긍정: 상태가 구조적으로 유계라 이 방어 장치 자체가 자원 고갈 벡터가 되지 않는다(테스트로 고정).
- 부정: 해시 충돌 시 무관한 두 주소가 예산을 공유한다 — 슬롯 수 설정에 의존한다.
- 부정: **NAT 뒤 다수 사용자가 한 주체로 보인다.** 회사·학교·모바일 캐리어 환경에서는 버스트·
  속도를 그만큼 키워야 정상 사용자가 거부되지 않는다(타입 문서에 경고).
- 부정: 거부 관측 태그는 전역 거부와 같은 `admission` 이다 — 사유 문자열로만 구분된다.
  태그를 나누려면 전송 배선 변경이 필요해 별도 판단으로 남긴다.

## ADR-0027: 서킷 브레이커는 대상이 생길 때까지 보류 — 대신 파티션 정지 감지를 만든다

- **날짜**: 2026-08-07
- **상태**: 채택
- **영향 범위**: Concurrency(`ExecutionPartition` 진행 표식, `PartitionedExecutionModel.CountStalledPartitions`,
  헬스 판정에 저하 추가, `PartitionedExecutionOptions.StallThreshold`)

### 배경

- Phase 10 잔여 항목 둘: "서킷 브레이커 / 재시도 미들웨어 — **외부 의존(DB/Redis) 장애 격리**" 와
  "Bulkhead — **한 기능의 장애가 전체를 마비시키지 않게 격리**".
- 조사 결과 **서킷 브레이커의 대상이 이 프레임워크에 아직 존재하지 않는다**: `Persistence.*`
  어셈블리도, `ISessionStore`·`IClusterMembership` 계약도 없다(Phase 13·15 에서 생긴다).
  `Core/Resilience` 에는 `IAdmissionControl`·`IRateLimiter` 뿐이고 **아웃바운드 호출 지점이 0** 이다.
- 반면 Bulkhead 항목이 가리키는 위험은 **이미 실재한다**: `ExecutionPartition` 은 배타 작업의
  완료를 <b>무기한</b> 기다린다(그 대기가 ADR-0008 배타성 보장의 실체다). 따라서 **완료하지
  않는 핸들러 하나가 파티션 전용 스레드를 영구 정지시키고, 그 파티션에 매핑된 모든 커넥션이
  함께 멈춘다.** 파티션마다 하나씩 걸리면 서버 전체가 마비된다.

### 결정

1. **서킷 브레이커는 보류한다.** 지금 만들면 **구현 0·호출 지점 0인 추상화**가 된다 —
   "두 번째 구현이 나오기 전까지 추상화는 가설"(CLAUDE.md 3), "추상화가 늘어나는 것 자체가
   비용"(2). 호출 지점 없이 정한 계약은 Redis 어댑터가 실제로 올 때 틀릴 위험이 크다.
   **세션 저장소(Phase 13)나 클러스터(Phase 15)에서 첫 아웃바운드 호출이 생길 때 그 실물에
   맞춰 만든다.** ROADMAP 항목에 이 근거를 남긴다.
2. **대신 파티션 정지를 감지한다.** 파티션이 진행 중인 항목의 시작 시각을 기록하고
   (<c>Environment.TickCount64</c>, 유휴는 <c>-1</c>), 밖에서 임계 초과 파티션 수를 질의한다.
   **프레임당 비용은 long 쓰기 2회**이고 할당은 0 이다 — 이미 하는 채널 읽기·Interlocked 증가에 묻힌다.
3. **관측이지 강제가 아니다.** 대안이던 핸들러 타임아웃(강제)은 (a) 협조적 취소라 CPU 무한루프·
   동기 블로킹은 못 막고 (b) 프레임당 `CancelAfter` 타이머 등록 비용이 붙는다. 정지의 진짜 문제는
   **아무도 모르는 것**이므로, 조용한 정지를 없애는 것이 1차 목표다.
4. **심각도는 저하(Degraded)이지 재시작(Unhealthy)이 아니다.** 정상적으로 오래 걸리는 작업도
   임계를 넘을 수 있는데, liveness 를 실패시키면 오케스트레이터가 프로세스를 재시작해
   **일시적 지연이 실제 장애로 승격된다**(`HealthProbe` 의 프로브 의미 규약). 저하는 프로브를
   통과시키되(HTTP 200) 헬스 보고서에 남는다. 스레드 사망만 Unhealthy 로 유지한다.
5. **표식 해제는 `finally` 에 둔다**(9.2). 빠뜨리면 예외 하나로 그 파티션이 영원히 "정지 중"
   으로 보고돼 진단이 거짓말을 한다 — 테스트로 고정했다.
6. **모든 항목 종류를 감싼다.** 배타 작업뿐 아니라 스케줄러 연속·외부 작업도 완료하지 않으면
   똑같이 스레드를 붙든다.

### 대안과 탈락 이유

| 대안 | 탈락 이유 |
|---|---|
| 지금 서킷 브레이커 계약을 만든다 | 대상(아웃바운드 호출)이 없다. 호출 지점 0인 계약은 실물이 올 때 틀린다 |
| 핸들러 타임아웃(강제 취소) | 협조적 취소라 CPU 무한루프·동기 블로킹은 못 막고, 프레임당 타이머 등록 비용이 붙는다. 정지의 진짜 문제는 "아무도 모르는 것"이다 |
| 파티션이 대기를 포기하게 한다 | 배타성 보장(ADR-0008)이 깨진다 — 같은 파티션 작업이 겹쳐 순서·배타 규약이 무너진다 |
| 정지를 Unhealthy 로 | 일시적 지연에도 재시작 루프에 빠진다. 오래 걸리는 정상 작업과 고장을 임계만으로 구분할 수 없다 |
| 별도 워치독 타이머·스레드 | 스레드를 늘리지 않는다(9.5). 헬스 프로브가 이미 주기적으로 폴링하므로 그것이 워치독이다 |
| 정지 수를 메트릭 게이지로 | 현재값 pull 게이지가 필요한데 `ObserveCounter`(누적)와 계약이 다르다. 헬스 보고서가 이미 관측 채널이고 HTTP 로도 노출된다 — 필요해지면 그때 추가 |

### 결과

- 긍정: "스레드는 살아 있는데 파티션이 멈춘" 사각지대가 드러난다 — 생존 신호로는 잡히지
  않던 상태다. 헬스 보고서 설명에 몇 개가 얼마나 붙들려 있는지 남고, `/healthz` 로 조회된다.
- 긍정: 프레임당 할당 0·long 쓰기 2회. 관측을 켜고 끄는 조립 선택조차 필요 없을 만큼 싸다.
- 부정: **감지일 뿐 강제가 아니다.** 정지한 파티션의 커넥션은 여전히 멈춰 있다 — 운영자가
  보고 조치해야 한다. 강제(타임아웃)는 위 근거로 별도 판단에 남긴다.
- 부정: 임계 설정에 의존한다. 배치성 핸들러를 파티션에서 돌리면 잡음이 생기므로 늘려 잡아야 한다.
- 부정: 서킷 브레이커·재시도는 여전히 미구현이다 — Phase 13/15 에서 첫 아웃바운드 호출과 함께 만든다.
