# 일관성 모델

무엇이 **강한 일관성**이고 무엇이 **최종 일관성**인가. 그리고 **무엇을 보장하지 않는가**.

> **이 문서의 존재 이유.** 분산 상태를 다루는 프레임워크가 보장 범위를 적어 두지 않으면,
> 앱은 자기가 가진 적 없는 보장을 가정한 채로 작성된다. 그 가정이 깨지는 것은 대개
> **장애 중**이고, 그때는 원인을 좁힐 시간이 없다.
> 여기 적히지 않은 것은 **보장되지 않는다**고 읽는다.

---

## 0. 한눈에

| 대상 | 보장 |
|---|---|
| **세션 한 키에 대한 읽기/쓰기** | **선형화 가능(linearizable)** — 단일 마스터 기준 |
| 세션 **여러 키에 걸친** 연산 | **보장 없음** — 다중 키 트랜잭션이 없다 |
| 세션 **만료 판정** | 즉시(읽으면 없는 것으로 보인다) |
| 세션 **저장 공간 회수** | 지연 — 인메모리·PostgreSQL 은 청소 주기, Redis 는 서버 정책 |
| **재개 시 좀비 차단** | 강함 — 단일 키 CAS 위에 세웠으므로 **다중 노드에서도 성립** |
| **서킷 브레이커 상태** | **노드 로컬** — 노드마다 다를 수 있다(의도된 설계) |
| Redis **복제** | **비동기** — 페일오버 시 확인된 쓰기가 유실될 수 있다 |
| **Redis Cluster** | ⚠ **미지원** (아래 4절). PostgreSQL 어댑터는 무관하다 |

## 1. 세션 저장소 — 키 하나에 대해서는 강하다

`ISessionStore`(ADR-0033)의 모든 변경 연산은 **낙관적 동시성(CAS)** 이다.
읽기가 버전을 함께 돌려주고, 쓰기·삭제·연장이 기대 버전을 받는다.

```
읽기      -> (상태, 버전 V)
쓰기(V)   -> 성공하면 새 버전 V'
쓰기(V)   -> 그 사이 남이 바꿨으면 Conflict
```

**보장**: 같은 키에 대한 연산들은 **하나의 전역 순서**로 관측된다. 두 주체가 같은 버전을
들고 동시에 쓰면 **정확히 하나만 성공**한다. 세 구현이 이것을 각자의 수단으로 만족시킨다.

| 구현 | 원자성의 근거 |
|---|---|
| `InMemorySessionStore` | `ConcurrentDictionary.TryUpdate` 의 참조 비교-교체. 항목은 불변이고 교체로만 갱신된다 |
| `RedisSessionStore` | **Lua 스크립트** — 서버에서 단일 원자 단위로 실행된다(ADR-0034). `WATCH/MULTI/EXEC` 는 커넥션에 묶이는데 멀티플렉서는 커넥션을 다중화하므로 쓸 수 없다. **Garnet 에서도 그대로 동작한다**(ADR-0038) — 단 Garnet 은 `--lua` 로 띄워야 한다 |
| `PostgresSessionStore` | **조건부 `UPDATE`** — `WHERE id=@id AND version=@expected` 가 그 자체로 원자적이고, 영향 행 0 이 곧 충돌이다(ADR-0037). 관계형은 Lua 가 필요 없다 |

**⚠ 이 보장은 "단일 마스터 기준" 이다.** Redis 복제는 비동기이므로, 마스터가 확인한 쓰기가
복제본에 도달하기 전에 페일오버가 나면 **그 쓰기는 사라진다**. 이것은 Redis 의 성질이지
어댑터의 결함이 아니며, 강한 내구성이 필요하면 다른 저장소를 고르는 문제다.

### 무엇이 보장되지 않는가

- **여러 세션에 걸친 원자성**. 세션 A 와 B 를 함께 바꾸는 연산은 없다. 필요하면 앱이
  보상 트랜잭션을 설계한다
- **읽기 사이의 일관된 스냅샷**. 두 번 읽으면 그 사이에 값이 바뀌었을 수 있다.
  읽고-고치고-쓰기 루프의 안전은 **CAS 가** 지키지, 읽기의 신선함이 지키지 않는다

## 2. 앱이 지켜야 할 규율 — 읽고·고치고·쓰기

CAS 는 **잘못된 쓰기를 막아 줄 뿐** 올바른 값을 만들어 주지는 않는다.

```csharp
while (true)
{
    var read = await store.TryReadAsync(id, buffer);      // 버전을 받는다
    var next = Modify(buffer.WrittenSpan);                // 읽은 값 위에서 고친다
    var write = await store.TryWriteAsync(id, next, read.Version);
    if (write.Succeeded) break;
    // ⚠ 충돌 = "남이 바꿨다". 재시도 전에 **반드시 다시 읽는다** —
    //    옛 값 위에서 만든 next 를 그대로 다시 쓰면 남의 변경을 덮는다.
    buffer.Clear();
}
```

**충돌은 오류가 아니라 정상적인 동시성 결과다.** 그래서 예외가 아니라 반환값이고
(`SessionWriteResult.Conflict`), 서킷 브레이커도 이것을 실패로 세지 않는다(ADR-0035) —
세면 경합이 곧 차단이 되어 부하를 견디라고 만든 장치가 부하 때문에 서비스를 끊는다.

**재시도 상한을 앱이 정한다.** 프레임워크는 무한 재시도를 하지 않는다 — 경합이 끝나지
않는 상황에서 무한 루프는 장애를 증폭시킨다.

## 3. 만료 — 판정은 즉시, 회수는 지연

| 질문 | 답 |
|---|---|
| 만료된 세션을 읽으면? | **없는 것으로 보인다**(즉시). 세 구현 모두 |
| 만료된 세션의 키에 첫 쓰기를 하면? | 기대 버전 `None` 으로 **성공한다**(계약) |
| 저장 공간은 언제 회수되나? | **지연**. 인메모리·PostgreSQL 은 청소 주기(`SweepInterval`), Redis 는 서버 정책 |

**지연 판정만으로는 새는 것을 막지 못한다.** 다시 조회되지 않는 세션 — 정확히 **끊긴
클라이언트의 상태** — 이 영원히 남기 때문이다. 그래서 인메모리와 PostgreSQL 은 주기적
청소를 함께 돌린다(타이머는 저장소당 하나, CLAUDE.md 9.5). Redis 는 서버가 회수하므로
어댑터에 청소가 없다. **같은 계약을 각자의 수단으로 만족시키는 것**이 축의 요점이다.

**⚠ PostgreSQL 의 청소는 배치 상한을 둔다.** 만료 행이 수백만 개 쌓인 상태에서 무제한
`DELETE` 는 긴 트랜잭션과 잠금으로 **서비스 쿼리를 막는다** — 청소가 장애를 만드는 것이
가장 나쁜 결말이다.

### ⚠ 시계는 저장소의 것이다

- `InMemorySessionStore` 의 만료 기준은 **그 프로세스의 시계**다
- `RedisSessionStore` 의 만료 기준은 **Redis 서버의 시계**다
- `PostgresSessionStore` 의 만료 기준은 **데이터베이스 서버의 `now()`** 다 — 만료 시각
  계산도 서버에서 하므로(`now() + @ttl`) 앱 노드의 시계가 어긋나도 판정이 갈리지 않는다

따라서 다중 노드에서 인메모리 저장소를 쓰면 노드마다 만료 시각이 다르다 — 그러나 애초에
인메모리 저장소는 **노드 로컬**이라 다중 노드에서 세션을 공유하지 못한다(6절).

## 4. ⚠ 알려진 한계 — Redis Cluster 미지원

`RedisSessionStore` 의 **쓰기 스크립트는 키를 둘 만진다**:

```
KEYS[1] = chsm:sess:<세션 식별자>    -- 세션 값
KEYS[2] = chsm:sess:__ver            -- 전역 버전 카운터
```

Redis Cluster 는 Lua 스크립트가 만지는 모든 키가 **같은 해시 슬롯**에 있어야 한다.
위 두 키는 서로 다른 슬롯에 떨어지므로 **`CROSSSLOT` 오류로 거부된다.**

**따라서 현재 어댑터는 단일 노드(또는 클러스터가 아닌 복제 구성)에서만 동작한다.**
읽기·삭제·연장 스크립트는 키를 하나만 만지므로 문제가 없고, **쓰기만 걸린다.**

> 전역 카운터를 쓰는 이유는 **ABA 방지**다 — 세션이 삭제·만료된 뒤 다시 만들어져도 이전
> 버전이 재사용되지 않아야 오래된 쓰기가 성공하지 않는다(ADR-0033). 키별 카운터는 세션이
> 사라질 때 함께 사라져 1 부터 다시 시작한다.

**이 한계를 푸는 선택지**(아직 결정하지 않았다 — 클러스터 지원은 Phase 17 의 몫이다):

| 방안 | 대가 |
|---|---|
| 해시 태그로 세션 키와 카운터를 같은 슬롯에 묶는다 (`chsm:sess:{<id>}` + `chsm:sess:{<id>}:v`) | 카운터가 **세션보다 오래 살아야** ABA 가 막힌다 → 세션당 영구 키 하나가 늘어난다 |
| 버전을 64비트 난수로 발급 | 카운터가 사라진다. 재사용 확률이 사실상 0(2⁻⁶⁴)이지만 계약의 "재사용하지 않는다" 가 **확률적 보장**으로 약해진다 |
| 클러스터를 지원하지 않는다고 명시 | 지금 상태. 단일 노드·복제 구성에서는 아무 문제가 없다 |

## 5. 재개와 좀비 차단 — 강한 보장이 CAS 에서 나온다

세션 재개(ADR-0036)는 **토큰 회전이라는 쓰기**를 유발한다. 그래서:

```
옛 커넥션: 버전 7 을 들고 있음
재접속:    토큰 회전 쓰기 -> 버전 8
옛 커넥션의 쓰기: TryWrite(expected=7) -> Conflict  (밀려났음을 안다)
```

**이 차단은 다중 노드에서도 성립한다.** 단일 키 CAS 위에 세웠기 때문이다 — 옛 커넥션이
다른 노드에 있어도 같은 저장소를 보므로 버전 비교가 그대로 작동한다.
능동적으로 옛 커넥션을 끊는 방식이었다면 **다른 노드의 커넥션에는 닿지 못했을 것**이다.

**⚠ 옛 커넥션은 쓰기를 시도해야 자신이 밀려난 것을 안다.** 읽기만 하는 좀비는 낡은 값을
계속 볼 수 있다. 앱이 그것을 문제로 본다면 주기적으로 쓰기(하트비트 연장이 아니라 상태
쓰기)를 하거나, 재개 시 앱 수준의 통지를 설계한다.

## 6. 무엇이 노드 로컬인가

| 대상 | 범위 |
|---|---|
| `InMemorySessionStore` | **프로세스 로컬**. 다중 노드에서 세션을 공유하지 못한다 — `stateless-web` 프로필이 외부 저장소를 요구하는 이유다(ADR-0004) |
| `RedisSessionStore`(Redis · **Garnet**) · `PostgresSessionStore` | **공유**. 다중 노드에서 같은 세션을 본다 |
| `CircuitBreaker` | **노드 로컬**. 각 노드가 자기가 본 실패로 판단한다 |
| 커넥션 바인딩(`ISessionFeature`) | **커넥션 로컬**. 그 커넥션의 디스패치 순차 컨텍스트 전용이다 |
| 속도 제한·수용 제어 | **노드 로컬**. 전역 상한이 필요하면 클러스터 축이 선행돼야 한다 |

**서킷 브레이커가 노드 로컬인 것은 의도된 설계다.** 노드마다 네트워크 경로와 부하가 다르니
한 노드가 관측한 장애가 다른 노드의 진실이 아닐 수 있다. 전역 합의는 그 자체로 또 하나의
분산 문제이며, 그것을 도입할 이유가 아직 없다(ADR-0035).

---

## 7. 이 문서를 갱신해야 할 때

- 새 `ISessionStore` 구현을 만들 때 — **적합성 스위트를 통과하는 것으로는 부족하다.**
  스위트는 계약을 검증하지만 **내구성·복제·클러스터 성질은 검증하지 않는다.**
  새 어댑터는 1·3·4·6절에 자기 줄을 추가한다
- 클러스터 축(Phase 17)이 생길 때 — 4절과 6절이 통째로 바뀐다
- 다중 키 연산이 필요해질 때 — 지금은 "보장 없음" 이고, 그것을 바꾸려면 ADR 이 선행된다
