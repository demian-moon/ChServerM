### ① 로그 레벨 런타임 변경 — 프레임워크 코드 0

- MEL 어댑터(ADR-0030)를 얹은 순간 **이미 성립**했다: 어댑터가 `IsEnabled` 를 **호출마다**
  MEL 로 위임하고(값을 캐시하지 않는다), MEL 은 필터 옵션이 바뀌면 규칙을 재구성한다.
  따라서 호스트가 `LoggerFilterOptions` 를 바꾸면 프레임워크 로그가 즉시 따라온다.
- **가정하지 않고 실제 `LoggerFactory` 로 검증했다** — 이 항목의 산출물은 코드가 아니라
  **증거**다: 필터 변경 반영 / 어댑터가 캐시하지 않음(질의 3회 = 위임 3회) / 범주
  (`ChServerM`)로 프레임워크 로그만 선택적으로 열기. 테스트 3종.
- 테스트 전용으로 `Microsoft.Extensions.Logging`(구현) 참조 — 필터를 바꿔 보려면 필요하다.
  **프로덕션 어댑터는 여전히 `Abstractions` 만** 참조한다.

### ② `LoadLevelAdmissionControl` — 메모리 워터마크를 수용 축에 연결

- 부하가 임계 이상이면 신규 연결을 거부해 **이미 붙은 커넥션을 보호**한다. 자원이 한계일 때
  새 손님을 계속 받는 것은 서비스 중인 손님까지 함께 죽이는 길이다(9.6).
- `ILoadLevelSource` 를 받으므로 메모리(`MemoryLoadLevelSource`)뿐 아니라 큐 깊이·지연·외부
  오케스트레이터 신호도 같은 자리에 꽂힌다. **열화 미들웨어와 같은 신호를 공유**하는 것이
  요점 — 두 방어가 다른 기준으로 움직이면 운영자가 상태를 하나로 설명할 수 없다.
- **⚠ 기본 임계가 `Critical` 인 것이 설계의 핵심 — 열화가 먼저, 수용 거부가 나중이다.**
  1단계 `Elevated`: 열화가 비필수 메시지를 버린다(문은 열려 있다).
  2단계 `Critical`: 그래도 부족하면 신규 수용을 끊는다.
  뒤집으면 조금만 밀려도 신규 사용자가 못 들어오고 **그 재시도가 accept 부하를 더한다.**
- `Normal` 임계는 평상시 전면 차단이 되므로 조립 시점에 거부한다.
- 테스트 9종(임계별 판정·설정 가능·회복·조립 검증·컴포지트 AND / **★ 단계적 반응**:
  Normal 통과 → Elevated 열화만 → Critical 수용 거부).

### ⚠⚠ GC 설정이 3개월간 적용되지 않았다 (`98d766d`, ADR-0031)

### 그래서 GC 를 켜면 빨라지는가 — A/B 측정 (512 커넥션 전체 활성, 서버 GC 모드만 변수)

| 구성 | RPS | p99 | 워킹셋 |

| ServerGC + DATAS 끔 | 165.1k | 7.3ms | **624MB** |

- **★ 처리량 차이가 전부 ±2% 안 — 실행 간 편차(2.2%)와 구분되지 않는다.**
  이것은 실패가 아니라 **설계 주장의 검증**이다. 프레임당 0바이트를 할당하면 GC 가 개입할
  지점이 거의 없다. **GC 튜닝이 안 먹히는 것이 무할당 설계가 작동한다는 증거다.**
- 명확한 신호는 두 부작용이다: **DATAS 가 p99 를 46~85% 악화**(힙 재조정 지터 — 클라우드

  GC 모드를 자기가 적용한다. 배너에 `Server=True`). LoadRunner 기반 종단 부하 4건만
  Workstation 이었고, 위 A/B 가 "처리량은 GC 둔감" 을 보였으므로 **A/B 결론은 전부 유지**,
  절대값 라벨만 정정했다.
- **프로덕션 기본값은 이 수치로 정하지 않았다.** 루프백 단일 머신은 서버 GC 스레드가
  생성기 코어를 직접 빼앗아 **ServerGC 에 구조적으로 불리**하다. 값은 CLAUDE.md 가 선언한
  의도(`true`) 그대로 두고, 전용 머신 재측정을 미완으로 남겼다.

## 결정 (이어서 2)

- **ADR-0031** — GC 설정은 선언이 아니라 runtimeconfig 로 검증한다. 프로퍼티 이름 정정 +
  검증 방법을 props 주석에 고정 + DATAS 는 기본값 유지(끄는 쪽이 p99 에 유리하지만 워킹셋
  10배는 프레임워크가 말없이 부과할 비용이 아니다 — 노브와 수치만 문서화).

## 측정 (이어서 2)

- `BENCHMARKS.md` — AOT vs JIT 절, **GC 모드 A/B 절** 신설. 측정 규칙에 "GC 모드는 선언이
  아니라 산출물로 확인하고 기록한다" 추가. 기준선 표와 LoadRunner 기록 4곳에 GC 라벨 부착.

## 배운 것 (이어서 2)

- **"고정했다" 는 선언은 검증이 아니다.** 문서가 서로를 인용하면 **틀린 것도 일관되게
  틀린다.** 사실의 근거는 생성된 산출물이거나 런타임 관측치여야 한다. 이 프로젝트가
  "측정 없는 최적화 금지" 를 규칙으로 뒀는데 **설정 자체는 그 규칙의 예외로 방치돼 있었다**
- **조용히 무시되는 것이 가장 위험하다.** 오타 난 MSBuild 프로퍼티, 오타 난 환경 변수,
  오타 난 editorconfig 키 — 전부 실패를 알리지 않는다. 이번 주에 같은 부류를 두 번 만났다
  (증분 빌드가 분석기 위반을 감춘 건, 그리고 이것)
- **튜닝이 안 먹히면 그것도 결과다.** GC 모드가 처리량을 못 바꾼다는 것은 실망이 아니라
  무할당 설계가 실제로 작동한다는 가장 직접적인 증거였다
