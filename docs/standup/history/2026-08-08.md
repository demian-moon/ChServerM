### ① 로그 레벨 런타임 변경 — 프레임워크 코드 0

- MEL 어댑터(ADR-0030)를 얹은 순간 **이미 성립**했다: 어댑터가 `IsEnabled` 를 **호출마다**
  MEL 로 위임하고(값을 캐시하지 않는다), MEL 은 필터 옵션이 바뀌면 규칙을 재구성한다.
  따라서 호스트가 `LoggerFilterOptions` 를 바꾸면 프레임워크 로그가 즉시 따라온다.
- **가정하지 않고 실제 `LoggerFactory` 로 검증했다** — 이 항목의 산출물은 코드가 아니라
  **증거**다: 필터 변경 반영 / 어댑터가 캐시하지 않음(질의 3회 = 위임 3회) / 범주
  (`ChServerM`)로 프레임워크 로그만 선택적으로 열기. 테스트 3종.
- 테스트 전용으로 `Microsoft.Extensions.Logging`(구현) 참조 — 필터를 바꿔 보려면 필요하다.
  **프로덕션 어댑터는 여전히 `Abstractions` 만** 참조한다.

### ② `LoadLevelAdmissionControl` — 메모리 워터마크를 수용 축에 연결

- 부하가 임계 이상이면 신규 연결을 거부해 **이미 붙은 커넥션을 보호**한다. 자원이 한계일 때
  새 손님을 계속 받는 것은 서비스 중인 손님까지 함께 죽이는 길이다(9.6).
- `ILoadLevelSource` 를 받으므로 메모리(`MemoryLoadLevelSource`)뿐 아니라 큐 깊이·지연·외부
  오케스트레이터 신호도 같은 자리에 꽂힌다. **열화 미들웨어와 같은 신호를 공유**하는 것이
  요점 — 두 방어가 다른 기준으로 움직이면 운영자가 상태를 하나로 설명할 수 없다.
- **⚠ 기본 임계가 `Critical` 인 것이 설계의 핵심 — 열화가 먼저, 수용 거부가 나중이다.**
  1단계 `Elevated`: 열화가 비필수 메시지를 버린다(문은 열려 있다).
  2단계 `Critical`: 그래도 부족하면 신규 수용을 끊는다.
  뒤집으면 조금만 밀려도 신규 사용자가 못 들어오고 **그 재시도가 accept 부하를 더한다.**
- `Normal` 임계는 평상시 전면 차단이 되므로 조립 시점에 거부한다.
- 테스트 9종(임계별 판정·설정 가능·회복·조립 검증·컴포지트 AND / **★ 단계적 반응**:
  Normal 통과 → Elevated 열화만 → Critical 수용 거부).

### 런타임 진단 (`13b9694`) — **Phase 11 마지막 항목, 관측 9/9 완결**

- **메트릭과 겹치지 않는 근거가 설계의 출발점이다.** 메트릭은 카디널리티 규약상 커넥션 ID·
  주소를 태그로 쓰지 못한다(쓰면 시계열 폭발). 진단은 정확히 그 **여집합** — 주기적 시계열이
  아니라 **요청 시점의 고카디널리티 스냅샷**이다.
- Core `IDiagnosticsSource`/`IDiagnosticsWriter`(평평한 키-값 — 트리·표 타입을 만들지 않는다,
  출력은 `curl` 로 읽는 것이 1차 용도) + `DiagnosticsService`(**구역별 try/catch** — 진단은
  장애 중에 부르는 경로라 한 구역이 던져 아무것도 못 보면 진단이 장애를 키운다).
- **옵트인 배선**(ADR-0023 규율): 전송·실행 모델이 구현하면 자동 등록. 버퍼 풀 소스는
  Observability 에(Buffers 무의존 유지, ADR-0025 와 같은 근거).
- **⚠ 커넥션은 집계 + 상한 표본(20개, 가장 오래 조용한 순).** 전체 덤프를 안 한 이유 둘:
  ① 1만 접속이면 응답이 MB 급이라 진단 조회가 그 자체로 부하 ② 커넥션 목록은 곧 **클라이언트
  주소 목록**인데 admin 엔드포인트는 평문·무인증이다. HTTP 노출도 `DiagnosticsPath`
  **옵트인**(기본 미노출) — 프로브는 오케스트레이터가 반드시 필요로 하지만 진단은 사람이
  필요할 때 켜는 것이므로 기본값이 덜 노출하는 쪽이어야 한다.
- 파티션은 전수(상한 512 라 출력이 유계) — 커넥션과 달리 표본을 뽑을 이유가 없다.
- 테스트 8종. 게이트에서 RS0017(생성자 시그니처 변경으로 옛 줄 잔존) → 승인 파일에서 제거.

### 플래키 제거 (`1388e1b`) — 게이트가 잡아낸 내 결함

- `State_is_bounded_by_slot_count...`(2026-08-07 증분 7)가 전체 스위트에서 간헐 실패했다.
  단독 실행은 통과 — 전형적인 부하 의존 플래키.
- **원인은 측정 도구였다**: `GC.GetTotalMemory` 는 **프로세스 전역**이라 병렬로 도는 다른
  테스트의 할당이 그대로 섞인다. `GetAllocatedBytesForCurrentThread` 로 바꾸니 병렬에
  영향받지 않고, "엔트리당 할당이 없다" 는 설계 주장을 **더 정확히** 검증한다(메모리 델타는
  GC 타이밍에도 흔들렸다). 전체 솔루션 3회 반복 무경합 확인.

### Phase 12 착수 (`c406106`) — 할당 회귀 게이트 + 성능 기준선

- **할당 고정이 코덱 수준에만 있었다.** 정작 미들웨어가 쌓이는 **조립된 파이프라인**은
  무방비였다 — 미들웨어 하나가 async 상태 머신을 만들거나 클로저를 잡으면 프레임당 할당이
  조용히 생긴다. 추적 fast-path·열화 fast-path·열화 **거부 경로**(과부하일수록 뜨거워지는
  경로라 여기서 할당하면 정반대 효과)·속도 제한·**셋을 합성한 실제 조립 형태**를 전부 0 으로 고정.
- **★★ 게이트가 고의 회귀를 실제로 잡는지까지 테스트로 고정했다** — 프레임당 할당하는
  미들웨어를 넣으면 측정이 0 이 아니어야 한다. 게이트가 무엇이든 통과시키면 게이트가 아니다.
  Phase 12 게이트 조건("의도적 성능 퇴화를 실제로 잡을 때") 그 자체다.
- **할당을 첫 게이트로 고른 이유**: 시간 기반은 개발 머신에서 본질적으로 노이즈가 크지만
  할당은 결정적이다. 바로 위 플래키 사건이 그 신뢰성 차이를 실증했다.
- `BENCHMARKS.md` 의 "목표 수치(가설, 미검증)" 표를 **실측 기준선으로 대체** — 169,180 RPS ·
  1만 접속 · 커넥션당 ~8KB · 프레임당 0B · 라우팅 0.69ns · 코어 확장 14.67×(91.7%) ·
  관측 오버헤드. 각 항목에 환경 ID 와 근거 기록을 붙였다. **회귀 방어 상태 표**도 함께 —
  할당은 상시 게이트(✅), 처리량·확장성은 미구현(❌)임을 정직히 명시.

## 배운 것 (이어서)

- **기본값은 덜 노출하는 쪽이어야 한다** — 진단 HTTP 경로를 옵트인(기본 미노출)으로 뒀다.
  프로브는 오케스트레이터가 반드시 쓰지만 진단은 사람이 필요할 때 켜는 것이고, 그 안에는
  클라이언트 주소가 들어간다. **켜는 실수보다 안 켜는 실수가 덜 나쁘다**
- **측정 도구의 범위를 확인한다** — `GC.GetTotalMemory` 는 프로세스 전역, `GetAllocatedBytes
  ForCurrentThread` 는 스레드 지역이다. 병렬 테스트 안에서 전자는 남의 할당을 센다.
  **무엇을 재는 도구인지가 테스트의 신뢰성을 정한다**
- **게이트는 스스로 증명해야 한다** — "회귀를 잡는다" 는 주장도 테스트가 필요하다. 고의 회귀를
  넣어 게이트가 실패하는 것까지 고정해야 게이트가 게이트다. 통과만 보는 테스트는 언제
  무력해졌는지 알 수 없다
