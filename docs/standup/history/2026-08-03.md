# 2026-08-03

Phase 1 계획(승인된 6단계)을 전부 소화했다. **Core 추상화 → 프레이밍 구현 → 인메모리 전송
→ TCP 전송 → 실행 모델 → 빌더·샘플**까지, 그리고 그 과정에서 실제 결함 세 건을 잡았다.

## 한 일

### Stage 1 — Core 기본 계약 (`53811bf`)

| 영역 | 내용 |
|---|---|
| `Identity/` | `PartitionKey`(피보나치 해싱 + 나눗셈 없는 인덱싱), `ObjectId`(Snowflake 41/10/12, 노드 성분 필수), `ConnectionId`(slot+generation), `MessageId`, `SessionId`/`JobId`/`NodeId` |
| `Time/` | `IClock`을 만들지 않고 BCL `TimeProvider` 채택. `MonotonicTimestamp`로 벽시계와 타입 분리 |
| `Diagnostics/` | `LogLevel`(레거시엔 레벨 개념 자체가 없었다), `EventId`, `IServerLogger`, `ErrorCode`, 메트릭 이름 상수 |
| `Features/` | `IFeatureCollection` — 전송별 선택 기능의 확장점 |

`JobId`는 **소유자 범위**다. 레거시 `HashM`이 오브젝트 스코프 키를 전역 작업 ID로 그대로 써서
두 오브젝트가 같은 키를 쓰면 두 번째부터 만료가 조용히 죽었다.

### Stage 2 — 네트워크 축 인터페이스 (`a21cd44`)

`Connections/` `Transports/` `Framing/` `Serialization/` `Dispatch/` `Execution/`.
공개 표면 **44 타입 / 16 인터페이스** — 축마다 하나씩이라 줄일 중복이 없음을 확인했다.

- `IServerTransport`가 **3단 종료**(Bind → Unbind → Stop). Unbind와 Stop 사이가 무중단 배포의 창이다
- `IFrameDecoder`가 `FrameDecodeResult` 구조체를 반환한다. `out` 4개보다, 호출자가
  `Consumed`/`Examined`를 빠뜨려 파이프를 교착시키기 어렵다
- `MessageContext`는 커넥션당 1개 재사용. `EndFrame()`이 페이로드 참조를 **실제로 끊는다**

### 주석 규약 (`b302070`)

`CLAUDE.md` 8.1 신설. 모든 주석은 한글, 모듈(파일 최상단 타입) 주석에
**존재 이유 / 스레드 규약 / 수명·소유권 규약 / 막고 있는 레거시 결함 / 성능 근거**를 담는다.

### Stage 3 — `ChServerM.Framing` (`eb3b744`)

- `FrameHeaderCodec` — 와이어 레이아웃을 아는 유일한 지점. `MemoryMarshal`이 아니라 `BinaryPrimitives`
- `FixedHeaderFrameDecoder` — **무상태**라 인스턴스 하나를 모든 커넥션이 공유한다.
  세그먼트를 넘는 헤더는 16B `stackalloc`
- 길이 필드를 `uint`인 채로 비교한다. `int` 캐스팅 후 비교하면 2GB 이상이 음수가 된다
- **모르는 플래그 비트를 거부한다.** 무시하면 압축된 페이로드를 원본으로 착각해 핸들러에 넘긴다

### Stage 4 — 인메모리 전송 + 디스패처 (`04310a0`)

`ChServerM.Hosting`(Core만 참조) + `ChServerM.Transport.InMemory`.

- `FramedConnectionHandler` — **`AdvanceTo`는 그 읽기에서 나온 모든 프레임의 디스패치가 끝난 뒤에만**
  부른다. 프레임 단위로 부르면 핸들러가 해제된 메모리를 본다
- **미들웨어가 라우팅보다 앞에 있다.** 반대면 모르는 ID를 보내는 것만으로 인증을 우회할 수 있다
- Core 계약 2건 변경 — `MessageDelegate`/`IServerMiddleware`가 `ValueTask<DispatchStatus>`를 반환.
  결과를 가변 필드에 적는 방식이면 아무도 안 적고 지나가 거부된 메시지가 정상 처리로 집계된다

### Stage 5 — TCP 전송 (`a4a1221`)

raw `Socket` + Pipelines. `TcpClient`/`NetworkStream`을 쓰지 않는다.

- 소켓 작업에 `CancellationToken`을 넘기지 않는다. 중단은 `Socket.Dispose()` — Kestrel과 같은 방식
- **0바이트 수신으로 대기**(`WaitForDataBeforeAllocating`). 1만 유휴 접속 × 4KB = 40MB 절감.
  레거시는 커넥션당 64KB를 상수로 붙들었다(= 640MB)
- 부분 전송 처리. `SendAsync`가 전부 보낸다는 보장이 없고, 놓치면 조용히 잘린 프레임이 나간다
- 수락 루프가 일시적 오류와 치명적 오류를 구분한다. 구분하지 않으면 조용히 수용을 멈추거나 CPU를 태운다
- `IOControlCode.KeepAliveValues`를 쓰지 않는다 — Windows 전용, 레거시의 크로스 플랫폼 차단 요인

### Stage 6 — 실행 모델 + 빌더 + 샘플 (`6f43927`)

- `ChServerM.Concurrency` — 파티션당 전용 스레드 + 단일 FIFO 채널
- `ServerBuilder`/`ClientBuilder`/`ChServerMServer`/`ChServerMClient`
- `PartitionedConnectionHandler` — 읽기 루프를 파티션에 고정 → **프레임당 큐 비용 0**
- `Samples/ChServerM.Samples.EchoServer` — Native AOT **1.9MB** 바이너리 정상 동작

- **ADR-0007 신규** — 최대 프레임은 전송 버퍼 한계 안에 들어가야 한다 (아래 참조)

## 잡은 결함 3건

### 1. `SocketConnection.Abort`가 송신 펌프를 깨우지 않음

소켓만 닫아서는 부족하다. 송신 펌프는 소켓이 아니라 **파이프**에서 대기하고 있어서,
`Abort`된 커넥션의 `DisposeAsync`가 영구 교착했다. `CancelPendingPipeReads()` 추가 +
`WaitForPumpsAsync`에 제한 시간.

### 2. 최대 프레임 > 전송 버퍼 = 영구 교착 (ADR-0007)

축 두 개의 성질이 충돌한다. 디코더는 완전한 프레임 전에 아무것도 소비할 수 없고(경계를 잃으므로),
전송 버퍼는 미소비 바이트가 임계값에 닿으면 쓰기를 멈춘다.

| 임계값 | 페이로드 | 결과 |
|---|---|---|
| 64 KiB | 200 KB | **교착** |
| 64 KiB | 40 KB | 정상 |
| 512 KiB | 200 KB | 정상 |

**TCP가 통과한 건 커널 버퍼가 흡수한 우연이었다.** 그리고 **기본값 조합(프레이밍 1MiB /
전송 64KiB)부터 이미 깨져 있었다.**

→ Core에 `ITransportBufferLimits`, 빌더의 `CompositionGuard`가 `Build()`에서 검사해
**조용한 교착을 시작 시점 예외로** 전환. 기본값은 일부러 맞추지 않았다 — 전송을 1MiB로 올리면
1만 접속에 20GB이고, 프레이밍을 64KiB로 낮추면 정당한 워크로드를 막는다.

### 3. 테스트가 대기 중인 `ManualResetEventSlim`을 `Dispose`

대기자가 있는 상태의 `Dispose`는 동작이 정의되지 않는다. 테스트 코드 쪽 결함이었다.

두 건(1·2)은 **`dotnet test`가 "테스트 호스트 프로세스 작동이 중단됨"으로 죽어서** 발견됐다.
72개 테스트가 전부 통과한 뒤 종료 시점에 걸렸고, 클래스 → 메서드 순으로 좁혀
독립 재현 프로그램을 만들어야 원인이 드러났다.
