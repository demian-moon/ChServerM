### 증분 1 — 파티션 백프레셔 관측 배선 (`5c9059b`, Phase 10 후속)

- **조사로 확정한 것**: "백프레셔 생산 배선"에 이름은 같지만 성숙도가 다른 셋이 섞여 있었다.
  `PartitionWorkRejected`·`PartitionQueueDepth`(신호는 `_rejectedCount`·`PendingExternalWork`
  로 이미 셈, 방출만 없음) / `RejectedByBackpressure`(DispatchStatus — **자연 생산자 없음**) /
  `BackpressureDuration`(Wait 모드 경로 없음, 별개).
- **핵심 발견**: `RejectedByBackpressure`(DispatchStatus)는 설계상 생산자가 없다 — 디스패치
  주 경로(`TryEnqueueExclusive`)는 커넥션당 in-flight 1건의 **자연 백프레셔**라 넘칠 수 없다
  (ADR-0008). 억지 생산자는 그 설계와 충돌. 사용자 승인(옵션 1): 파티션 메트릭만 배선 +
  DispatchStatus 문서 명확화.
- **구현**: `ExecutionPartition` 에 `IMetricsSink` 주입(로거와 대칭, 기본 Null). `TryPost`
  포화 거부 → `PartitionWorkRejected` 카운터, 게시/완료 → `PartitionQueueDepth` 게이지(대칭).
  파티션 태그는 생성 시 1회(게시당 할당 0). `RejectedByBackpressure` XML 을 "큐잉 디스패치
  모델용 예약" 으로 명확화. 스테일 TODO 2곳 갱신.
- 테스트 +2(거부 카운터 == 실제 거부 수 + 파티션 태그 / 게이지 게시 시 상승·드레인 후 0·피크).

### 증분 2 — 분산 트레이싱 디스패치 span + fast-path (`05a5ca6`, Phase 11, ADR-0022)

- **갈림길 2개 사용자 승인**: (1) `ActivitySource` Hosting 직접 방출(Core `ITraceSink` 탈락) —
  추적의 교체 지점은 방출자가 아니라 구독자(ActivityListener)라 대안 구현이 없고, Core 중립
  인터페이스는 프레임당 span 핸들 할당 비용만 남긴다. (2) 디스패치 span 만(커넥션 span 연기).
- **구현**: `TracingMiddleware` — 프레임마다 `ActivityNames.Dispatch` span, `message_id`·
  `connection_id` 태그(고카디널리티는 span 속성 전용, `TagNames.ConnectionId` 신설), 비-Handled
  → Error 상태. `ServerBuilder.UseTracing()`(싱크 인자 없음). `ActivitySource` 는 공유
  프레임워크라 Core 무의존 유지.
- **fast-path**: `HasListeners()` 가 false 면 `next` 를 async 래퍼 없이 그대로 반환 —
  2026-08-06 관측 벤치가 남긴 "데코레이터 async 비용(6→43ns)"의 실측된 해법.
- 테스트 +3(span 태그·상태 / 거부 Error / 리스너 없음 span 미생성). 전체 게이트 통과.

## 한 일 (이어서) — 증분 4: 헬스 체크 축 liveness/readiness (`a1c581d`, Phase 11, ADR-0023)

- **Core 최소 계약(무의존)**: `IHealthCheck`(CheckAsync) + `HealthStatus`(Unhealthy=0=최악=기본값)
  + `HealthCheckResult` + `HealthReport`. `Microsoft.Extensions.Diagnostics.HealthChecks`(패키지)
  대신 직접 — Core 무의존.
- **Hosting**: `HealthCheckService`(프로브 필터 + 항목별 try/catch + 최악 우선 집계) +

- **내장 readiness = 생명주기**: `ServerLifecycleState`(Created→Accepting→Draining→Stopped)를
  서버가 갱신, `AcceptanceReadinessCheck` 가 읽음. `UnbindAsync` 즉시 Draining → 무중단 배포 시
  LB 디레지스터 신호. 생명주기와 readiness 가 한 진실 공유.
- **내장 liveness = 실행 모델이 IHealthCheck 구현**: `PartitionedExecutionModel` 이 파티션
  스레드 생존 보고(`ExecutionPartition.IsThreadAlive`). 호스팅은 `_executionModel is IHealthCheck`
  면 자동 등록 — Core 실행 모델 계약 오염 없이·Concurrency 미참조로 배선.
- **이번 증분은 프로그래밍 API 까지**. HTTP 노출(/healthz·/readyz)은 별개 축(HTTP 호스팅)이라 후속.
- 테스트 +9(집계 최악 우선·빈 집계 Healthy·프로브 필터·예외 격리 / 생명주기 readiness 전이·
  실행 모델 liveness·미실행모델 빈 liveness·커스텀 등록). 전체 게이트 통과.

## 한 일 (이어서) — 증분 6: 바이트 카운터 + 풀 카운터 pull 배선 (`5a89ed6`, Phase 11, ADR-0025)

- **조사가 결정을 갈랐다**: 남은 메트릭 셋의 성격이 전혀 달랐다. 바이트는 **전송이 정확한 값을
  안다**(소켓 반환값, 옵션에 싱크 이미 배선) / 풀은 **이미 세어지고 있는데**(`BufferPoolDiagnostics`)
  `IMetricsSink` 가 push 전용이고 `Buffers` 는 **"Core 조차 참조하지 않는다"가 의도된 결정**
  (csproj 명시) / `FramesSent` 는 `FrameWriter` 가 static 확장이라 주입 지점이 없다.
- **바이트 = 전송이 push**: `SocketConnection` 이 소켓 경계에서 `BytesReceived`(수신 반환값)·
  `BytesSent`(전송 성공분, `finally` 뒤라 실패분 제외)를 센다. 계측이 **소켓 연산당 1회**라
  (프레임당이 아니다 — 한 read 가 여러 프레임을 실어온다) syscall 비용에 묻힌다. 시그니처 변경 0.
- **회선 없는 전송은 내지 않는다**: 인메모리는 파이프 직접 전달이라 wire 바이트가 존재하지 않는다.
  PipeReader/Writer 래핑으로 억지로 만드는 대신(핫패스 가상 호출) 계약(`MetricNames.BytesReceived`)에
  명시했다 — 그 조립에서 0인 것이 정상.
- **풀 = pull**: `IMetricsSink.ObserveCounter(name, Func<long>, tags)` 를 **기본 무동작 default
  메서드**로 추가(기존 구현체 안 깨짐). 대여·반납마다 push 하면 가장 뜨거운 경로에 메트릭 호출이
  붙는데, 값은 이미 세어지고 있으므로 수집 주기에 한 번 읽어가면 **핫패스 비용 0**. 어댑터는 BCL
  `Meter.CreateObservableCounter` 로 위임 — pull 의미가 그대로 성립(중간 저장·타이머 불필요).
- **풀 배선은 관측 어셈블리가(사용자 승인)**: `Observability → Buffers` 참조 +
  `BufferPoolMetrics.Register(sink)`. **Buffers 무의존 결정을 깨지 않는다.** 이름 3종 신설 —
  `pool.buffers.rented`/`returned`/`leaked`(**leaked != 0 이면 버그, 경보 대상**).
- 테스트 +5(TCP 양방향 바이트·싱크 없어도 동작 / 풀 3종 발행·**등록 후 대여가 다음 수집에 반영**
  (pull 의 핵심)·미지원 싱크 무시). 전체 게이트 통과.

## 결정 (이어서)

- **ADR-0025** — 바이트는 전송이 push, 풀은 pull(`ObserveCounter`), 배선은 관측 어셈블리가.
  탈락: 커넥션 데코레이터로 바이트(핫패스 가상 호출·SequencePosition 산술) / 디스패치

  `Buffers → Core`(명시된 의존 0 결정을 깸) / 앱이 직접 배선(자동 아님) / 별도 인터페이스(캐스팅).

  (측정 대상이 되는 추가 비용이 핫패스에 없다).

## 배운 것 (이어서)

- **"이미 세어지고 있는 값"은 push 가 아니라 pull 이다** — 풀 카운터를 push 로 내보내려면
  가장 뜨거운 경로(대여·반납)에 메트릭 호출이 붙는다. 값이 이미 있으면 수집 주기에 읽어가는
  것이 옳고, BCL ObservableCounter 가 정확히 그 계약이다. 앞으로 세션 수·캐시 항목 등도 같은 길
- **없는 개념을 억지로 만들지 않는다** — 인메모리 전송에는 "회선을 건넌 바이트"가 없다.

  적는 것이 더 정직하다(RejectedByBackpressure 를 예약으로 남긴 것과 같은 규율)
- **의존 방향은 배선의 위치를 정한다** — Buffers 가 Core 를 안 보므로 풀은 자기 카운터를
  메트릭으로 못 낸다. 그 제약을 깨는 대신(superseding ADR) **관측 배선을 관측 어셈블리가
  가져가는** 쪽이 기존 결정을 지키면서 자동 배선을 얻는다

### 증분 7 — 주소별 연결 속도 제한 (ADR-0026, T-14·T-16)

- ADR-0021 이 "상태·정리 정책이 필요한 별도 구현" 으로 미뤄둔 항목. `IAdmissionControl` 의
  **두 번째 구현**이라 Core 계약·전송 배선·컴포지트를 그대로 재사용했다(새 축이 아니다).
- **해결한 문제**: 전역 제한만으로는 악성 IP 하나가 전역 예산을 빨아들여 **정상 사용자가 함께
  거부**된다 — 정확히 공격자가 원하는 결과다.
- **설계의 핵심 — 방어 장치가 스스로 공격 표면이 되지 않게**: 주소→버킷을 `Dictionary` 에
  담으면 공격자가 소스 주소를 바꾸는 것만으로 맵이 무한히 자라 **OOM** 이 된다. 그래서 시작 시
  **고정 슬롯 배열(구조체)** 을 한 번 할당하고 절대 늘리지 않는다 — 축출 메커니즘·스윕 타이머·
  항목당 할당이 **아예 없다**(9.6 무제한 금지의 같은 원리). 테스트로 고정(주소 2만 개에도 증가 <1MB).
- 대가인 **해시 충돌은 수용**하고 타입 문서에 명시. **표적 충돌 공격**(피해자와 같은 슬롯을
  계산해 고갈)은 `HashCode` 의 **프로세스별 랜덤 시드**가 막는다.
- **IPv6 는 /64 프리픽스로 집계** — /128 단위 제한은 공격자에게 2^64 우회로를 주므로 방어가
  성립하지 않는다. **IPv4 매핑 IPv6 는 IPv4 로 환원**(듀얼스택 소켓이 그 형태로 넘김 — 환원하지
  않으면 같은 클라이언트가 두 주체로 갈려 제한이 두 배로 느슨해진다).
- 테스트 +13. 한계: NAT 뒤 다수 사용자는 한 주체(문서에 경고), 거부 태그는 전역과 동일(`admission`).

### 증분 8 — 파티션 정지 감지 (ADR-0027)

- **서킷 브레이커는 만들지 않았다 — 대상이 없다.** ROADMAP 정의는 "외부 의존(DB/Redis) 장애
  격리" 인데 조사 결과 **아웃바운드 호출 지점이 0**(Persistence 어셈블리·ISessionStore 계약 모두
  없음). 지금 만들면 구현 0·호출 지점 0 인 추상화가 되고 실물이 올 때 계약이 틀린다. 보류 근거를
  ADR·ROADMAP 에 기록하고 **Phase 13/15 로 미뤘다.**
- **대신 Bulkhead 항목이 가리키는 실재 위험을 막았다**: `ExecutionPartition` 은 배타 작업 완료를
  **무기한** 기다린다(그 대기가 ADR-0008 배타성 보장의 실체). 따라서 완료하지 않는 핸들러 하나가
  전용 스레드를 영구 정지시키고 **그 파티션의 모든 커넥션이 함께 멈추는데, 스레드는 살아 있어
  생존 신호로는 안 잡힌다** — 정확한 사각지대.
- 구현: 진행 중 항목의 시작 시각 기록(`TickCount64`, 유휴 `-1`) + `CountStalledPartitions(threshold)`.
  **9.3 대로 쓰기·읽기 모두 `Volatile`**, **표식 해제는 `finally`**(9.2 — 빠뜨리면 예외 하나로
  영원히 "정지 중" 오보, 테스트로 고정). 프레임당 long 쓰기 2회·**할당 0**.
- **심각도는 Degraded 이지 Unhealthy 가 아니다** — 정상적으로 오래 걸리는 작업도 임계를 넘을 수
  있어 liveness 를 실패시키면 **일시적 지연이 재시작 루프로 승격**된다. 스레드 사망만 Unhealthy.
- **별도 워치독 스레드를 만들지 않았다**(9.5) — 헬스 프로브 폴링이 곧 워치독이고 `/healthz` 로 노출된다.
- 테스트 +7. 한계: **감지일 뿐 강제가 아니다**(정지한 파티션의 커넥션은 여전히 멈춰 있다).

### 증분 9 — 크래시 처리 (`79e640f`, ADR-0028)

- **조사에서 실재 결함 발견.** 프레임워크 경계는 대부분 잘 닫혀 있었지만(핸들러 예외 격리·
  항목별 try/catch·`async void` 0), **수락 루프에 구멍**이 있었다: `AcceptLoopAsync` 는 소켓 계열
  예외만 잡는데 `StartConnection` 은 **사용자 공급 `IAdmissionControl.TryAdmit`** 을 부른다.
  던지면 ① 루프가 죽고 ② `_acceptLoop` 는 `Unbind` 에서야 await 돼 런타임에 신호가 없고
  ③ **readiness 는 계속 "수용 중"** 을 보고하며 ④ 예외는 종료 시점에야 튀어나온다 — 조용한 죽음.
- 수정: 최종 catch-all + 고장을 상태로(`_acceptFault`, 9.3 Volatile 양쪽) + `TcpServerTransport` 가
  `IHealthCheck` 구현 → 호스팅이 **readiness** 에 자동 등록(실행 모델과 같은 옵트인 규율, ADR-0023).
  기존 "수락 소켓 사망" 경로도 같은 표시로 통일(그쪽도 로그만 남기고 헬스는 수용 중이었다).
- **자동 재시작 안 함**: 원인이 지속적이면 무한 예외 루프로 코어를 태운다.
- 항목의 나머지: 전역 훅은 **opt-in 헬퍼**(`ProcessFaultHandlers`, 프로세스는 호스트의 것),
  덤프·재시작은 **코드가 아니라 운영 설정**임을 문서화(환경변수·오케스트레이터).
- 테스트 +5.

### 증분 10 — 우아한 열화 (`b88267b`, ADR-0029)

- 조사에서 **세 조각이 다 없음**을 확인: ① 부하 신호(`PendingExternalWork` 는 호출자가 없어 항상
  0, 메모리 신호 전무) ② 우선순위 표현 ③ 구분되는 거부. **①은 별개 ROADMAP 항목(메모리 워터마크)
  과 같은 것**이라 함께 채웠다.
- **무엇이 비필수인지는 프레임워크가 모른다** — 메커니즘만 주고 순서는 앱이 `ShedAbove` 로 선언.
  **미등록 = 필수**(설정 누락이 부하 시에만 재현되는 기능 상실이 되지 않게 — 실수의 방향을 안전한 쪽으로).
- 새 상태 `RejectedByLoadShedding` + `ErrorCode.LoadShed`(5000번대 실행·백프레셔, 6000 보안 아님).
  **무-종료** — `RejectedByPolicy` 재사용은 `CloseOnPolicyRejection` 에 걸려 부하 시 커넥션을
  무더기로 끊고 재접속이 부하를 키운다(열화가 붕괴를 앞당김). `RejectedByRateLimit` 와도 구분:
  클라이언트 과다 vs **서버 과부하** — 조치가 반대(학대자 차단 vs 증설).
- `MemoryLoadLevelSource`: `MemoryLoadBytes/HighMemoryLoadThresholdBytes` 비율이라
  **컨테이너 메모리 제한을 자동 추종**(절대 바이트는 환경이 바뀌면 틀림). 1초 캐시(`Current` 는 핫패스).
- **ADR-0021 이 워터마크를 미룬 이유(GC 시점 의존 → 테스트 결정성)를 축 분리로 해소** — 정책은
  가짜 소스로 결정적 검증. 테스트 +10.

### 증분 11 — 장애 주입 테스트 (`56c16d3`)

- **생산 코드 변경 0.** 적대 조건은 기존 API 로 만들어지므로 주입 설비를 추상화하지 않았다.
  **무작위 카오스도 안 씀** — 재현 안 되는 실패는 테스트를 끄게 만든다.

  (퍼즈는 코덱 수준만) · **잘린 프레임 후 절단**.
- **★ 복합 시나리오** — 게이트는 "과부하에서 거부하며 살아남는다" 를 주장하는데 세 기구가
  따로만 검증됐다. 동시에 걸고 200프레임 폭주 → 거부하되 **커넥션 유지**(무-종료 불변)·

## 한 일 (이어서) — 증분 12: MEL 로깅 어댑터 (`9ad167b`, Phase 11, ADR-0030)

  1. **`IServerLogger.Log<TState>` 가 `ILogger.Log<TState>` 와 인자 구성이 동일**하고

     패스스루**이고, 그 하나로 **ZLogger·Serilog·콘솔·Seq·App Insights 전체**가 프로바이더로 열린다.
  2. **"무할당" 은 이미 충족돼 있었다.** 로그 지점 **29곳을 전수 확인**하니 전부 오류·희소

     그런 설계를 애초에 하지 않았다.
  3. **ZLogger 직접 참조를 탈락시킨 결정적 이유**: 그 무할당 방출 경로를 쓰려면 상태 타입이

  선택은 호스트 몫). 범주는 `ChServerM` 로 `ActivitySourceName`·`MeterName` 과 통일 —
  메트릭·추적·로그를 한 이름으로 필터링.
- 테스트 +11. 게이트에서 **NU1109 다운그레이드 오류**: 새 패키지를 10.0.0 으로 잡았더니 기존

## 한 일 (이어서) — 증분 13: 실제 코어 제한 확장성 재측정 (`3b8c238`, Phase 8)

- **2026-08-03 곡선의 한계 1번을 해소했다.** 그 기록은 파티션 수 스윕이라 OS 가 여전히 모든
  코어를 쓸 수 있었다("코어 수를 바꾸는 것의 **근사**"). 프로세스 어피니티로 진짜 코어를 줄여
  다시 그렸다 — ADR-0005 에 붙은 검증 조건을 **근사가 아닌 실측**으로 방어한 것이다.
- **측정(ENV-B, 파티션 수 = 코어 수)**: 1코어 354.8ms → 2코어 1.96×(98.2%) → 4코어 3.90×(97.6%)
  → 8코어 7.63×(95.3%) → **16코어 14.67×(91.7%)**. 같은 머신의 순수 ALU 천장이 14.81×(93%)이므로
  프레임워크는 **그 99.0%** 를 낸다 — 남은 손실은 실행 모델이 아니라 하드웨어·OS 의 몫이다.
- **⚠ 선행 발견 — 기존 어피니티 안내가 틀렸다.** `Program.cs` 는 `start /affinity F` 를 4코어로
  안내했지만 **SMT 형제가 인접 쌍**이라 `0xF`(CPU 0~3)는 물리 2코어다. 그대로 썼으면 모든 숫자가
  2배 틀렸다. 물리 N 코어는 한 칸씩 건너뛴 마스크(`0x1`/`0x5`/`0x55`/`0x5555`/`0x55555555`).
- **내 첫 프로브도 틀린 답을 줬다.** 단일 의존 체인(`acc += i ^ (acc >> 3)`)으로 재니 SMT 형제도
  1.96× 가 나왔다 — IPC 가 낮은 코드는 SMT 가 거의 2배를 내므로 형제와 별개 코어를 **구분할 수
  없다**. 독립 누산기 8개(고 ILP)로 바꾸자 판정이 섰다: CPU 0+1 = **1.08×**(형제),
  CPU 0+16 = **1.93×**(별개 코어).
- **어피니티 적용 검증(대조군)**: 1코어 행이 파티션 24 까지 **완전 평탄**(354.2~354.8ms).
  코어가 하나면 파티션을 늘려도 빨라질 수 없으므로, 제한이 안 걸렸다면 불가능한 결과다.
- **부수 발견**: 초과 구독은 비율이 고르지 않을 때 더 나쁘다 — 8코어에서 12파티션(61.7ms)이
  24파티션(46.8ms)보다 느리다(1.5:1 은 불균형, 3:1 은 고르다). → **파티션 수는 코어 수의 배수로.**
- `PartitionScalingBenchmarks` 에 16 파라미터 추가 + 스윕만으로는 코어 확장을 증명하지 못한다는
  한계를 타입 문서에 명시. `Program.cs` 안내 정정. BENCHMARKS.md 2026-08-07 절.

## 배운 것 (이어서)

- **측정 도구가 틀렸는지 먼저 의심한다** — 어피니티 마스크가 물리 코어를 고르는지 확인하지 않았다면
  확장성 숫자가 통째로 2배 틀렸을 것이고, 그 숫자로 ADR 을 "검증했다" 고 적었을 것이다.
  **측정 전에 측정 도구를 측정한다.**
- **프로브의 워크로드가 답을 바꾼다** — 같은 질문(SMT 형제인가)에 의존 체인 워크로드는 1.96×,
  고-ILP 워크로드는 1.08× 를 줬다. 두 번째가 맞다. **무엇을 재는지가 어떻게 재는지에 달려 있다.**
- **대조군을 설계에 넣는다** — "1코어에서는 파티션을 늘려도 평탄해야 한다" 는 예측이 어피니티가
  실제로 걸렸음을 증명한다. 측정값만 있고 대조군이 없으면 "제한이 걸렸는가" 를 답할 수 없다
