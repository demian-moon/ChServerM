### 증분 1 — 파티션 백프레셔 관측 배선 (`5c9059b`, Phase 10 후속)

- **조사로 확정한 것**: "백프레셔 생산 배선"에 이름은 같지만 성숙도가 다른 셋이 섞여 있었다.
  `PartitionWorkRejected`·`PartitionQueueDepth`(신호는 `_rejectedCount`·`PendingExternalWork`
  로 이미 셈, 방출만 없음) / `RejectedByBackpressure`(DispatchStatus — **자연 생산자 없음**) /
  `BackpressureDuration`(Wait 모드 경로 없음, 별개).
- **핵심 발견**: `RejectedByBackpressure`(DispatchStatus)는 설계상 생산자가 없다 — 디스패치
  주 경로(`TryEnqueueExclusive`)는 커넥션당 in-flight 1건의 **자연 백프레셔**라 넘칠 수 없다
  (ADR-0008). 억지 생산자는 그 설계와 충돌. 사용자 승인(옵션 1): 파티션 메트릭만 배선 +
  DispatchStatus 문서 명확화.
- **구현**: `ExecutionPartition` 에 `IMetricsSink` 주입(로거와 대칭, 기본 Null). `TryPost`
  포화 거부 → `PartitionWorkRejected` 카운터, 게시/완료 → `PartitionQueueDepth` 게이지(대칭).
  파티션 태그는 생성 시 1회(게시당 할당 0). `RejectedByBackpressure` XML 을 "큐잉 디스패치
  모델용 예약" 으로 명확화. 스테일 TODO 2곳 갱신.
- 테스트 +2(거부 카운터 == 실제 거부 수 + 파티션 태그 / 게이지 게시 시 상승·드레인 후 0·피크).

### 증분 2 — 분산 트레이싱 디스패치 span + fast-path (`05a5ca6`, Phase 11, ADR-0022)

- **갈림길 2개 사용자 승인**: (1) `ActivitySource` Hosting 직접 방출(Core `ITraceSink` 탈락) —
  추적의 교체 지점은 방출자가 아니라 구독자(ActivityListener)라 대안 구현이 없고, Core 중립
  인터페이스는 프레임당 span 핸들 할당 비용만 남긴다. (2) 디스패치 span 만(커넥션 span 연기).
- **구현**: `TracingMiddleware` — 프레임마다 `ActivityNames.Dispatch` span, `message_id`·
  `connection_id` 태그(고카디널리티는 span 속성 전용, `TagNames.ConnectionId` 신설), 비-Handled
  → Error 상태. `ServerBuilder.UseTracing()`(싱크 인자 없음). `ActivitySource` 는 공유
  프레임워크라 Core 무의존 유지.
- **fast-path**: `HasListeners()` 가 false 면 `next` 를 async 래퍼 없이 그대로 반환 —
  2026-08-06 관측 벤치가 남긴 "데코레이터 async 비용(6→43ns)"의 실측된 해법.
- 테스트 +3(span 태그·상태 / 거부 Error / 리스너 없음 span 미생성). 전체 게이트 통과.

## 한 일 (이어서) — 증분 3: 커넥션 span + 크로스 스레드 부모 전파 (`1417941`, Phase 11, ADR-0022 후속)

- **완성한 것**: 증분 2에서 "연기" 로 남긴 커넥션 span·부모-자식 트리를 닫았다 —
  분산 트레이싱 항목(correlation ID 전파)이 실질 완료.
- **메커니즘**: `TracingConnectionHandler`(가장 바깥 데코레이터)가 커넥션 전 생애
  `ActivityNames.Connection` span 을 열고, 그 `ActivityContext` 를 `ConnectionTraceFeature`
  로 커넥션 기능에 1회 Set. `TracingMiddleware` 는 파티션 스레드에서 이 컨텍스트를 읽어
  디스패치 span 의 **명시적 부모**로 넘긴다 — `Activity.Current`(AsyncLocal)가 채널
  핸드오프를 넘지 못하는 문제를 이렇게 우회. `ServerTracing` 으로 단일 `ActivitySource`
  홀더 추출(커넥션·디스패치가 같은 원본).
- **결정(사용자 승인)**: 전 생애 부모 span — 커넥션 span 하나가 모든 디스패치 span 의 부모.
  트레이드오프(장수명 커넥션 = 큰 trace·늦은 export)는 head 샘플링으로 조절. 탈락: 짧은
  커넥션 span+공유 컨텍스트(시간 역전) / 현재 유지+인바운드 W3C traceparent(프로토콜 변경).
- **fast-path 보존**: 부모 조회(커넥션 기능 Get)는 `HasListeners()` 게이트 뒤에서만 —
  리스너 없는 핫패스는 여전히 8ns/0B.
- 테스트 +2 e2e(**실행 모델 껴서** 파티션 스레드 검증: 디스패치 span 이 커넥션 span 의
  자식·같은 TraceId / UseTracing 미호출 시 span 0). 전역 `ActivityListener` 격리 위해 두
  추적 테스트 클래스를 병렬 비활성 컬렉션으로 묶음. 전 타입 internal — public 표면 변경 0.

## 결정 (이어서)

- **ADR-0022 후속 절** — 커넥션 span + 크로스 스레드 부모 전파 완료. 전 생애 부모 span 채택
  근거·트레이드오프·탈락안 기록.

## 측정 (이어서)

- 새 벤치 없음 — 부모 조회는 `HasListeners` 게이트 뒤 feature Get 하나로, 기존 추적 벤치
  (리스너 있음 170ns/560B)에 이미 포함(벤치의 빈 기능 모음이 Get→null 경로를 이미 탐).

## 배운 것 (이어서)

- **크로스 스레드 컨텍스트는 명시적으로 나른다** — `Activity.Current`(AsyncLocal)는 편하지만
  스레드 경계(채널·파티션)를 못 넘는다. 파티션 실행 모델에서 부모-자식을 얻으려면 컨텍스트를
  값으로 실어야 한다. 기능 모음의 "수립 시 Set·그 뒤 읽기만" 규약이 락 없이 이걸 가능케 한다
- **전역 상태를 다루는 테스트는 컬렉션으로 순차화한다** — `ActivityListener` 는 프로세스
  전역이라 두 추적 테스트 클래스가 병렬로 돌면 "리스너 없음" 관측이 오염된다. 단독은 통과·
  묶으면 실패가 그 신호. `[Collection]` + 병렬 비활성으로 격리
- **실행 모델을 껴야 크로스 스레드를 실제로 잡는다** — 인라인 디스패치(실행 모델 없음)로
  테스트하면 정작 풀려던 파티션 스레드 문제를 건드리지 못한다. e2e 에 `PartitionedExecutionModel` 필수
