### 증분 1 — 파티션 백프레셔 관측 배선 (`5c9059b`, Phase 10 후속)

- **조사로 확정한 것**: "백프레셔 생산 배선"에 이름은 같지만 성숙도가 다른 셋이 섞여 있었다.
  `PartitionWorkRejected`·`PartitionQueueDepth`(신호는 `_rejectedCount`·`PendingExternalWork`
  로 이미 셈, 방출만 없음) / `RejectedByBackpressure`(DispatchStatus — **자연 생산자 없음**) /
  `BackpressureDuration`(Wait 모드 경로 없음, 별개).
- **핵심 발견**: `RejectedByBackpressure`(DispatchStatus)는 설계상 생산자가 없다 — 디스패치
  주 경로(`TryEnqueueExclusive`)는 커넥션당 in-flight 1건의 **자연 백프레셔**라 넘칠 수 없다
  (ADR-0008). 억지 생산자는 그 설계와 충돌. 사용자 승인(옵션 1): 파티션 메트릭만 배선 +
  DispatchStatus 문서 명확화.
- **구현**: `ExecutionPartition` 에 `IMetricsSink` 주입(로거와 대칭, 기본 Null). `TryPost`
  포화 거부 → `PartitionWorkRejected` 카운터, 게시/완료 → `PartitionQueueDepth` 게이지(대칭).
  파티션 태그는 생성 시 1회(게시당 할당 0). `RejectedByBackpressure` XML 을 "큐잉 디스패치
  모델용 예약" 으로 명확화. 스테일 TODO 2곳 갱신.
- 테스트 +2(거부 카운터 == 실제 거부 수 + 파티션 태그 / 게이지 게시 시 상승·드레인 후 0·피크).

### 증분 2 — 분산 트레이싱 디스패치 span + fast-path (`05a5ca6`, Phase 11, ADR-0022)

- **갈림길 2개 사용자 승인**: (1) `ActivitySource` Hosting 직접 방출(Core `ITraceSink` 탈락) —
  추적의 교체 지점은 방출자가 아니라 구독자(ActivityListener)라 대안 구현이 없고, Core 중립
  인터페이스는 프레임당 span 핸들 할당 비용만 남긴다. (2) 디스패치 span 만(커넥션 span 연기).
- **구현**: `TracingMiddleware` — 프레임마다 `ActivityNames.Dispatch` span, `message_id`·
  `connection_id` 태그(고카디널리티는 span 속성 전용, `TagNames.ConnectionId` 신설), 비-Handled
  → Error 상태. `ServerBuilder.UseTracing()`(싱크 인자 없음). `ActivitySource` 는 공유
  프레임워크라 Core 무의존 유지.
- **fast-path**: `HasListeners()` 가 false 면 `next` 를 async 래퍼 없이 그대로 반환 —
  2026-08-06 관측 벤치가 남긴 "데코레이터 async 비용(6→43ns)"의 실측된 해법.
- 테스트 +3(span 태그·상태 / 거부 Error / 리스너 없음 span 미생성). 전체 게이트 통과.

## 한 일 (이어서) — 증분 4: 헬스 체크 축 liveness/readiness (`a1c581d`, Phase 11, ADR-0023)

- **Core 최소 계약(무의존)**: `IHealthCheck`(CheckAsync) + `HealthStatus`(Unhealthy=0=최악=기본값)
  + `HealthCheckResult` + `HealthReport`. `Microsoft.Extensions.Diagnostics.HealthChecks`(패키지)
  대신 직접 — Core 무의존.
- **Hosting**: `HealthCheckService`(프로브 필터 + 항목별 try/catch + 최악 우선 집계) +

- **내장 readiness = 생명주기**: `ServerLifecycleState`(Created→Accepting→Draining→Stopped)를
  서버가 갱신, `AcceptanceReadinessCheck` 가 읽음. `UnbindAsync` 즉시 Draining → 무중단 배포 시
  LB 디레지스터 신호. 생명주기와 readiness 가 한 진실 공유.
- **내장 liveness = 실행 모델이 IHealthCheck 구현**: `PartitionedExecutionModel` 이 파티션
  스레드 생존 보고(`ExecutionPartition.IsThreadAlive`). 호스팅은 `_executionModel is IHealthCheck`
  면 자동 등록 — Core 실행 모델 계약 오염 없이·Concurrency 미참조로 배선.
- **이번 증분은 프로그래밍 API 까지**. HTTP 노출(/healthz·/readyz)은 별개 축(HTTP 호스팅)이라 후속.
- 테스트 +9(집계 최악 우선·빈 집계 Healthy·프로브 필터·예외 격리 / 생명주기 readiness 전이·
  실행 모델 liveness·미실행모델 빈 liveness·커스텀 등록). 전체 게이트 통과.

  검증 없이는 게이트 통과가 "위반 없음"을 뜻하지 않는다 — 증분-vs-클린 교훈의 3번째 사례
- **어댑터는 델리게이트로 소스를 받아 계층을 지킨다** — HTTP 헬스 어댑터가
  HealthCheckService(Hosting) 대신 프로브 델리게이트(Core 타입)를 받으니, "Server 어셈블리 →
  Hosting" 첫 사례를 만들지 않고 일방 의존을 유지했다. 값 타입(HealthProbe)을 Core 로 올리는
  작은 이동이 그것을 가능케 했다

## 한 일 (이어서) — 증분 6: 바이트 카운터 + 풀 카운터 pull 배선 (`5a89ed6`, Phase 11, ADR-0025)

- **조사가 결정을 갈랐다**: 남은 메트릭 셋의 성격이 전혀 달랐다. 바이트는 **전송이 정확한 값을
  안다**(소켓 반환값, 옵션에 싱크 이미 배선) / 풀은 **이미 세어지고 있는데**(`BufferPoolDiagnostics`)
  `IMetricsSink` 가 push 전용이고 `Buffers` 는 **"Core 조차 참조하지 않는다"가 의도된 결정**
  (csproj 명시) / `FramesSent` 는 `FrameWriter` 가 static 확장이라 주입 지점이 없다.
- **바이트 = 전송이 push**: `SocketConnection` 이 소켓 경계에서 `BytesReceived`(수신 반환값)·
  `BytesSent`(전송 성공분, `finally` 뒤라 실패분 제외)를 센다. 계측이 **소켓 연산당 1회**라
  (프레임당이 아니다 — 한 read 가 여러 프레임을 실어온다) syscall 비용에 묻힌다. 시그니처 변경 0.
- **회선 없는 전송은 내지 않는다**: 인메모리는 파이프 직접 전달이라 wire 바이트가 존재하지 않는다.
  PipeReader/Writer 래핑으로 억지로 만드는 대신(핫패스 가상 호출) 계약(`MetricNames.BytesReceived`)에
  명시했다 — 그 조립에서 0인 것이 정상.
- **풀 = pull**: `IMetricsSink.ObserveCounter(name, Func<long>, tags)` 를 **기본 무동작 default
  메서드**로 추가(기존 구현체 안 깨짐). 대여·반납마다 push 하면 가장 뜨거운 경로에 메트릭 호출이
  붙는데, 값은 이미 세어지고 있으므로 수집 주기에 한 번 읽어가면 **핫패스 비용 0**. 어댑터는 BCL
  `Meter.CreateObservableCounter` 로 위임 — pull 의미가 그대로 성립(중간 저장·타이머 불필요).
- **풀 배선은 관측 어셈블리가(사용자 승인)**: `Observability → Buffers` 참조 +
  `BufferPoolMetrics.Register(sink)`. **Buffers 무의존 결정을 깨지 않는다.** 이름 3종 신설 —
  `pool.buffers.rented`/`returned`/`leaked`(**leaked != 0 이면 버그, 경보 대상**).
- 테스트 +5(TCP 양방향 바이트·싱크 없어도 동작 / 풀 3종 발행·**등록 후 대여가 다음 수집에 반영**
  (pull 의 핵심)·미지원 싱크 무시). 전체 게이트 통과.

## 결정 (이어서)

- **ADR-0025** — 바이트는 전송이 push, 풀은 pull(`ObserveCounter`), 배선은 관측 어셈블리가.
  탈락: 커넥션 데코레이터로 바이트(핫패스 가상 호출·SequencePosition 산술) / 디스패치
  미들웨어에서 바이트(페이로드는 회선이 아니고 송신은 못 봄) / 풀 push(가장 뜨거운 경로) /
  `Buffers → Core`(명시된 의존 0 결정을 깸) / 앱이 직접 배선(자동 아님) / 별도 인터페이스(캐스팅).

## 측정 (이어서)

- 없음 — 바이트 계측은 소켓 연산당 1회라 syscall 에 묻히고, 풀은 pull 이라 핫패스 비용이 0이다
  (측정 대상이 되는 추가 비용이 핫패스에 없다).

## 배운 것 (이어서)

- **"이미 세어지고 있는 값"은 push 가 아니라 pull 이다** — 풀 카운터를 push 로 내보내려면
  가장 뜨거운 경로(대여·반납)에 메트릭 호출이 붙는다. 값이 이미 있으면 수집 주기에 읽어가는
  것이 옳고, BCL ObservableCounter 가 정확히 그 계약이다. 앞으로 세션 수·캐시 항목 등도 같은 길
- **없는 개념을 억지로 만들지 않는다** — 인메모리 전송에는 "회선을 건넌 바이트"가 없다.
  전송 간 대칭을 위해 PipeReader/Writer 를 래핑하면 핫패스 비용만 는다. 0이 정상임을 계약에
  적는 것이 더 정직하다(RejectedByBackpressure 를 예약으로 남긴 것과 같은 규율)
- **의존 방향은 배선의 위치를 정한다** — Buffers 가 Core 를 안 보므로 풀은 자기 카운터를
  메트릭으로 못 낸다. 그 제약을 깨는 대신(superseding ADR) **관측 배선을 관측 어셈블리가
  가져가는** 쪽이 기존 결정을 지키면서 자동 배선을 얻는다
