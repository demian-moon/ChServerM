## 한 일 — **Phase 12 완결 (10/10), Part III 종료**

측정을 **회귀 방어 장치로 승격**시키는 단계를 닫았다. 네 커밋 모두 Phase 12.

### ① 성능 회귀 게이트 (`dbcaaed`) — 비율 기준(CI) + 확장성(수동)

- **ROADMAP 원안("기준선 대비 N% 퇴화 시 빌드 실패")은 그대로 만들면 동작하지 않는다.**
  CI 는 GitHub 공용 러너라 절대 시간이 20~30% 흔들린다 — 임계가 좁으면 플래키하고
  넓으면 아무것도 못 잡는다. 대신 **같은 실행 안 두 팔의 비율**을 고정했다(노이즈가
  분자·분모에 함께 실려 상쇄된다). `eng/bench-gate.ps1` + `bench-gate.json`, 설계 주장 6종.
- 실패 시 **무너진 주장**을 출력한다 — 사람이 알아야 할 것은 "느려졌다" 가 아니다.
- **확장성 게이트는 CI 에 넣지 않는 것이 결정 사항**이다. 공용 러너는 2~4 vCPU 라 곡선이
  2점뿐이고 물리 코어와 SMT 형제를 구분할 수도 없다 — 거기서 도는 게이트는 의미 없는
  통과를 반복해 **게이트를 장식으로 만든다.** 하한은 ADR-0005 가 스스로 단 무효 조건
  (효율 70%)과 일치시켜, 실패가 "느려졌다" 가 아니라 "샤딩 전제가 무효다" 를 뜻하게 했다.
  전체 곡선 실측 1/2/4/8/16 코어 = 1.00 / 1.95 / 3.89 / 7.61 / **14.79×** (기준선 재현 ±0.7%).
- **★★ 고의 회귀 검증에서 게이트가 처음엔 놓쳤다.** 추적 fast-path 를 통째로 제거했는데
  비율이 0.049 → 0.126 에 그쳐 임계 0.15 를 통과했다. 원인: 리스너가 없으면
  `StartActivity` 가 null 을 돌려주므로 제거의 대가는 span 생성이 아니라 async 상태
  머신뿐(2.6배)이고, **내가 노이즈 여유로 준 3배가 실제 회귀보다 컸다.** 임계를
  **회귀 실측에서 역산**(0.09)하도록 고쳐 재검증 — 회귀 FAIL, 복원 PASS.
- 부수 수정 둘: `--filter` 를 반복해 넘기면 BDN 이 **아무것도 매칭하지 않고 exit 0 으로
  조용히** 끝난다(게이트가 "성공적으로 아무것도 측정하지 않는" 상태였다). `BenchConfig`
  이중 적용으로 exporter 중복 경고가 상시 떠서 제거 — **상시 경고는 게이트를 무력화한다.**

### ② 스파이크 시나리오 (`5ca8441`) — 종단 부하

- **ADR-0009 를 재검토했고 결론은 유지.** 커스텀 프레이밍이라 NBomber 를 넣어도 클라이언트
  코드는 그대로 써야 하고, **실제 공백은 도구가 아니라 시나리오 모양**이었다 — 램프업·지속은
  이미 있었고 **스파이크가 없었다.** 스파이크는 Phase 9/10 방어를 종단에서 검증할 유일한
  시나리오다(나머지는 과부하를 만들지 않는다).
- 설계 핵심은 **기준 무리와 폭주 무리의 분리**다. 합치면 폭주의 실패가 기준의 실패와 섞여
  아무것도 판정할 수 없다. 판정도 "빨랐는가" 가 아니라 ① 기준 무리 오류 0 ② 회복 p99 ≈
  기준 p99 ③ 폭주 거부는 실패가 아님.
- 실측: **수용 제어가 기존 손님의 p99 를 41% 지킨다**(27.20 → 16.00ms, 거부 1,975).
  p50 은 오히려 방어 쪽이 나쁘다(1.54 → 2.01ms) — **방어는 평균이 아니라 꼬리를 지킨다.**
  토큰 버킷 계산(1.1s 에 ~1,050)과 실측 수용 1,025 가 일치.
- **★ 측정 설계 결함 둘을 발견해 고쳤다.** ⓐ **TCP 연결 성공은 수용이 아니다** — 거부는
  accept **이후**라 커널이 핸드셰이크를 끝내 클라이언트 `ConnectAsync` 는 성공한다.
  왕복 기반 판정 전까지 방어를 켜고도 "거부 0" 이었다. ⓑ **워밍업이 없으면 기준 구간이
  티어드 JIT 승격 중에 측정**되어 스파이크가 30% *빠르게* 나온다.

### ③ 프로파일링 워크플로 (`c3a8372`) — `docs/PROFILING.md`

- **모든 절차와 수치를 실제로 실행해 얻었다.** 실행해 보지 않고 쓴 프로파일링 문서는
  반드시 틀린다. 밟은 함정을 그대로 기록: `cpu-sampling` 은 **Linux 전용**(Windows 는
  `dotnet-sampled-thread-time`) / 스택 리프가 의사 프레임이라 그대로 세면 "68%·32%" 두 줄만
  나온다 / 기동 직후 수집은 JIT 을 프로파일한 것 / 셸 백그라운드 PID ≠ 대상 PID.
- **★ 워크드 예제가 문서의 핵심**: 프로파일 1위 `ExecutionPartition.WaitForWork()` **25.32%**
  를 A/B 해보니 **없애면 RPS −4.7%·p99 +8%** 로 나빠져 **기각**했다. 그 25% 는 낭비가 아니라
  커널 전이를 피해 깨우기 지연을 줄이는 대가였다. **프로파일은 가설을 만들 뿐 결론을 만들지
  않는다** — "측정 없는 최적화 금지" 는 프로파일 결과에도 적용된다.
- GC 카운터도 기록: 할당 37.3MB/s(≈240B/요청) · gen0 5/s · **gen1·gen2 0**.
  240B 는 "프레임당 할당 0" 과 모순이 아니다(그 주장은 프레임워크가 얹는 몫에 대한 것이고
  이 벤치 핸들러는 `async` 다). **누수 신호는 할당량이 아니라 승격이다.**

### ④ 프레임워크 세금 (`aee51e0`) — raw Kestrel 바닥선, **Phase 12 완결**

- 지금까지 측정은 전부 ChServerM 안에서의 상대 비교였다 — "우리끼리 어느 쪽이 빠른가"
  밖에 답할 수 없었다. `RawKestrelEchoServer` 는 **같은 소켓 엔진 위에서 프레임워크를
  전부 걷어낸 것**이고, 그 차이가 조립 가능성·순서 보장·관측성의 가격표다.
- **비교를 의도적으로 바닥선에 유리하게 기울였다**(바이트 그대로 되쓰기·검증 하나·운영
  기능 없음) — 그래야 나온 값이 세금의 **상한**이 된다. 바닥선을 우리에게 유리하게 만들면
  비교가 자기 위안이 된다.

| 시나리오 | raw Kestrel | ChServerM | 차이 |
|---|---:|---:|---:|
| 16 활성 RPS / p99 | 168,022 / 133µs | 145,329 / 183µs | −13.5% / +37.6% |
| 512 활성 p99 | 15.30ms | 13.15ms | **−14.1%** |
| 10k+256 RPS / p99 | 164,192 / 5.75ms | 158,831 / 3.78ms | −3.3% / **−34.3%** |

- **세금은 단일 숫자가 아니다.** 저부하 지연 바닥에서 가장 크고(p50 차 11µs 는 CPU 가
  아니라 **파티션 인계 지연**이다) 부하가 오르면 인계가 파이프라인되어 1~3% 로 줄어든다.
- **★ 고동시성에서는 ChServerM 의 p99 가 34% 더 좋다**(2회 재현). raw 는 커넥션마다
  스레드풀에 올려 스케줄링 편차가 꼬리에 실리고, ChServerM 은 키별 전용 스레드+유계 큐라
  꼬리가 안정된다 — **ADR-0005 파티션 모델이 처리량이 아니라 꼬리 지연에서 값을 낸다는
  첫 증거**이며 지금까지 측정되지 않았던 이득이다.

## 배운 것

- **게이트의 임계는 노이즈 여유가 아니라 회귀 실측에서 역산한다.** 여유를 넉넉히 준다는
  선의가 게이트를 통과 전용 장식으로 만들 뻔했다. 고의 회귀 검증이 없었으면 그대로 배포됐다
- **프로파일은 가설을 만들 뿐 결론을 만들지 않는다.** CPU 1위 항목(25%)을 없애면 오히려
  나빠졌다. "고치지 않기로 한 결정" 도 기록해야 다음 사람이 같은 시간을 쓰지 않는다
- **비교는 상대에게 유리하게 기울여야 쓸모가 있다.** 바닥선을 우리에게 유리하게 만들면
  숫자가 아니라 자기 위안이 나온다
- **성공처럼 보이는 실패가 가장 위험하다.** 이번 주에 세 번 만났다 — MSBuild 오타(ADR-0031),
  `--filter` 반복 시 BDN 의 조용한 exit 0, 그리고 TCP 연결 성공을 수용으로 오독한 것
