## 한 일 — **Phase 13 세션 축 (7/12)**, 그리고 **서킷 브레이커 보류 해제**

다섯 커밋. 축 하나를 규율대로 끝까지 밀었다: **Core 계약 → 참조 구현 → 벤치마크 →

### ① `ISessionStore` 계약 + 인메모리 참조 구현 (`031eb13`, ADR-0033)

- **⚠ ROADMAP 이 Core 계약 항목을 빠뜨리고 있었다.** Phase 13 목록은 어댑터부터 시작하는데
  축 추가 순서는 Core 인터페이스가 먼저다. 누락된 선행 항목을 추가하고 그것부터 했다.
  `SessionId` 는 Core 에 있었지만 아무 데도 안 쓰이고 있었다 — 계약이 여기서 처음 생긴다.
- **값은 바이트다 — 결정적인 이유는 성능이 아니라 의미의 일치다.** `ISessionStore<TState>`
  로 객체를 주고받으면 인메모리는 **살아 있는 참조**를, Redis 는 **역직렬화된 사본**을
  돌려준다. 반환 객체를 고쳤을 때 한쪽은 저장소가 바뀌고 한쪽은 무시된다 —
  **같은 핸들러 코드가 저장소마다 다르게 동작**하므로 ADR-0004 가 깨진다.
- **버전(CAS)과 만료(TTL)를 v1 에 넣었다.** `PublicAPI.Shipped` 로 굳은 뒤엔 못 넣는다.
  **ABA 를 계약으로 막았다** — 버전은 같은 키에 재사용되지 않는다(만료·삭제 후 재생성 포함).
- **지연 만료만으로는 새는 것을 막지 못한다** — 다시 조회되지 않는 세션이 정확히 끊긴
  클라이언트의 상태다. 지연 판정 + 주기적 청소를 함께 쓴다(타이머는 저장소당 하나, 9.5).

### ② 벤치마크 + perf (`dd9165d`) — **벤치마크가 내 결함 2건을 잡았다**

| 항목 | before | after |
|---|---:|---:|
| CAS 충돌 64B | 50.53ns · 88B | 43.24ns · **0B** |
| CAS 충돌 1024B | 115.54ns · 1,048B | **43.74ns · 0B** |
| TryRenew | 54~56ns · 40B | 43.9ns · **0B** |

- **거부 경로가 상태를 복사하고 있었다** — `state.ToArray()` 를 버전 검사 **전에** 해서
  거부되는 호출도 상태 전체를 복사한 뒤 버렸다. **경합이 심할수록 충돌이 늘어나므로 정확히
  부하가 높을 때 GC 압력이 커진다.** 고치니 **거부 비용이 상태 크기와 무관**해졌다(43.24 vs
  43.74ns) — 그 크기 독립성이 실제 성질이다.
- **`TryRenew` 가 항목을 새로 만들고 있었다** — 만료를 미루자고 객체를 만드는 것은 이
  메서드의 존재 이유(상태를 다시 안 보내려고 만들었다)와 모순이다.
- **둘 다 테스트로 고정했다.** 벤치마크만으로는 다음에 다시 샌다.
- 부수: **벤치마크 자체에 결함**이 있었다 — 충돌 팔의 기대 버전 1 이 셋업의 실제 버전과
  같아져 **거부 경로 벤치마크가 조용히 성공 경로를 재고 있었다**.

### ③ Redis 어댑터 + ⭐ 적합성 스위트 (`c3ce160`, ADR-0034) — **축이 가설을 벗어났다**

- **버전을 값 안에** 넣는다(`[8B 버전][상태]`). 별도 키면 상태와 버전이 원자적으로 함께
  안 바뀌어 그 사이 읽은 쪽이 "새 버전 + 옛 상태" 를 본다.
- **CAS 는 Lua**. `WATCH/MULTI/EXEC` 는 커넥션에 묶이는데 멀티플렉서는 다중화한다.
  버전 발급도 서버가 `INCR` — 클라이언트가 만들면 다중 노드에서 충돌한다.
- 만료는 `SET PX`/`PEXPIRE` 로 **서버가 회수**. 인메모리는 직접 청소했다 —
  **같은 계약을 각자의 네이티브 수단으로 만족시키는 것**이 축의 요점이다.
- **⭐ 적합성 스위트**: 계약 단언 21종을 추상 클래스에 두고 각 어댑터가 **상속만 한다**.
  어댑터마다 자기 테스트를 쓰면 각자 자기 구현대로 단언하게 되어 **축 교체 시 동작 차이를
  아무도 못 잡는다.** 시간만 추상화하고(인메모리=가짜 시계 / Redis=실제 대기) 단언은 동일.
  **Redis 가 첫 실행에 21종 전부 통과** = 계약이 구현에 기대지 않고 그어졌다는 증거.
- Docker 부재는 **건너뛰되 사유를 남긴다**(`Xunit.SkippableFact`). 실패로 두면 CI 의
  windows-latest 가 깨지고, 조용히 통과시키면 "검증됐다" 는 착각을 준다.
- 사용자 승인 후 Docker Desktop 을 켜서 **실제 컨테이너로 검증**했다.

### ④ 서킷 브레이커 (`cd3c2b7`, ADR-0035) — **ADR-0027 의 보류 해제**

- **보류가 옳았다는 것이 드러났다.** 실물 없이 만들었다면 아래 분류를 근거 없이 정했을
  것이고, **CAS 충돌이라는 개념 자체가 세션 계약 전에는 존재하지 않았다.**
- **⚠⚠ 설계의 본체는 상태 기계가 아니라 "무엇을 실패로 세지 <i>않는가</i>" 다.**
  CAS 충돌·NotFound 는 저장소가 정상적으로 '아니오' 라고 답한 것이므로 실패가 아니다 —
  세면 **경합이 곧 차단**이 되어 부하를 견디라고 만든 장치가 부하 때문에 서비스를 끊는다.
  호출자 버그(`ArgumentException`)·취소도 아니다 — **잘못된 코드 한 줄이 저장소를 차단**시킨다.
- **실제 StackExchange.Redis 예외가 인프라 장애로 분류되는지 테스트로 고정**했다.
  스텁만으로는 증명 불가 — 분류가 틀리면 장애 때 알게 된다. 죽은 종단으로 검증하므로
  Docker 없이 항상 돈다.
- 열림 시 **예외를 던진다**(핫패스 예외 금지의 의도적 예외). `NotFound` 로 접으면 호출자가
  새 세션을 만들어 **사용자 상태 유실**이 된다.
- 계약을 3조각(`TryEnter`/`RecordSuccess`/`RecordFailure`)으로 나눈 대가는 **보고 누락 시
  회로가 영원히 안 닫히는 것** — 레거시 `ExecutableTaskDispatcherM` 과 같은 부류(9.2).
  계약 문서·데코레이터 `finally`·**자리 반납 테스트** 셋으로 막았다.
- Polly 탈락: 실행 래퍼 중심이라 호출당 할당이 있고, 필요한 표면은 메서드 3개뿐이다.

### ⑤ 세션 복구·재접속 (`4ffbf02`, ADR-0036) — **Phase 13 의 ⚠ 항목**

- **재개 자격은 서버 발급 토큰**이다. `SessionId` 는 로그·진단에 등장하고 열거 가능하므로
  자격으로 쓰면 **ID 를 아는 사람이 곧 주인**이 된다. 보안 규약 4종을 테스트로 고정:
  저장소엔 **해시만** / **쓸 때마다 회전**(탈취 토큰은 1회용, 늦게 온 쪽이 실패하므로
  **탈취가 드러난다**) / **실패 사유 미구분**(구분하면 실재 SessionId 열거 가능) /
  상수 시간 비교.
- **⭐ 좀비 차단을 CAS 에 얹어 새 개념이 0.** 재개가 토큰 회전이라는 쓰기를 유발해 버전이
  올라가고 옛 커넥션 버전이 자동 무효화된다 — **ADR-0033 이 CAS 를 v1 에 넣은 이유가 이
  경로다.** 능동 종료는 역방향 색인이 필요하고 **다중 노드에서 옛 커넥션에 닿지 않는다.**
- 저장 값은 `[1B 형식][32B 해시][앱 상태]` 봉투 — 키를 둘로 나누면 회전과 상태 갱신이
  원자적으로 함께 일어나지 않는다.
- **⚠ 토큰 타입을 Core 에 뒀다가 `CoreDependencyTests` 가 잡았다.** 암호 연산을 수행하므로
  추상화가 아니고, Core 계약 중 이것을 받는 것도 없다 → Hosting 으로 이동. **가드가 옳았다.**

## 배운 것

- **계약을 그을 때 가장 비싼 실수는 "의미가 갈리는 것" 이다.** 제네릭 타입 계약은 편하지만
  인메모리=참조 / 원격=사본 으로 **같은 코드가 저장소마다 다르게 동작**한다. 성능보다 이것이
  결정적이었다
- **적합성 스위트가 축을 진짜로 만든다.** 어댑터마다 자기 테스트를 쓰면 각자 자기 구현대로
  단언하게 된다 — 두 구현이 **같은** 테스트를 통과해야 교체 가능성이 증명된다
- **보류가 옳았음은 나중에만 알 수 있다.** 서킷 브레이커를 Phase 10 에서 만들었다면
  "CAS 충돌은 실패가 아니다" 를 알 수 없었다 — 그 개념이 존재하지 않았기 때문이다
- **가드는 내가 틀렸을 때 증명된다.** `CoreDependencyTests` 가 내 Core 오염을 잡았고,
  벤치마크가 내 할당 결함 2건을 잡았고, 벤치마크 자체의 결함도 드러났다

## 한 일 (이어서) — 세션 재개 **와이어 프로토콜**과 빌더 배선

앞 절에서 "세션 재개는 메커니즘까지다" 라고 남긴 것을 채웠다. **체크박스는 움직이지
않았다** — 이미 체크된 항목(세션 복구/재접속)을 깊게 만든 작업이라 후속으로 기록했다.

### ⑥ 와이어 프로토콜 (`680d539`)

- Core: 예약 ID 40007~40009 + **영구 동결** 코덱 `SessionHandshakeCodec` +
  `ISessionFeature`(커넥션↔세션 바인딩 + 마지막 관측 버전).
  `VersionHandshakeCodec` 의 선례를 따랐다 — 프레임워크가 정의하는 프로토콜은 Core 에 동결.
- Hosting: `SessionResumeDispatch` — 예약 메시지를 `SessionResumeService` 에 잇는다.
- **⚠ 재개는 프레임워크가, 수립은 앱이 한다.** 재개는 "제시된 토큰이 저장된 해시와
  맞는가" 라는 **기계적 판정**뿐이라 정책이 없다. 수립은 "이 사람에게 세션을 줘도 되는가"
  라는 **정책**이라 앱의 몫이다. 이 경계를 흐리면 인증 정책이 프레임워크로 새어
  ADR-0004 가 깨진다.
- **⚠ 코덱이 토큰 타입 대신 raw 스팬을 다룬다.** 토큰 타입은 암호 연산 때문에 Core 에 둘
  수 없지만(ADR-0036), **와이어 형식은 바이트를 옮기는 일**이라 암호가 필요 없다.
  이 분리 덕분에 앞으로 만들 클라이언트도 Core 만 참조해 프로토콜을 말할 수 있다.
- 보안 성질을 테스트로 고정: **성공과 실패의 응답 바이트가 완전히 동일**(길이 차이도 부수
  채널이다) / "세션 없음" 과 "토큰 불일치" 의 와이어 응답이 **바이트 단위로 같음** /
  실패 시 **바인딩을 만들지 않음**(만들면 그 커넥션이 남의 세션을 쓴다) /
  형식 오류도 **응답함**(끊기만 하면 "거부" 와 "네트워크 장애" 를 구분 못 한다).
- 동결 상수(크기·예약 ID)를 테스트가 못 박아, 조용히 바뀌면 배포 중이 아니라 빌드에서 난다.
- 테스트 16종.

### ⑦ 빌더 배선 (`6967c9d`)

- `ServerBuilder.UseSessions(resumeService)` — 앱이 예약 ID 40007 을 알 필요가 없다.
  서버가 `Sessions`/`SessionDispatch` 표면을 노출한다.
- **⚠ 서비스를 받고 만들지는 않는다.** 저장소가 인메모리인지 Redis 인지, 만료를 얼마로
  할지, 서킷 브레이커를 씌울지는 앱이 정해야 **축 교체 가능성이 유지된다**. 빌더의 몫은
  예약 메시지 배선과 표면 노출이다.
- 실제 서버·실제 소켓 종단 테스트 3종 — **앱 코드가 ID 40007 을 한 번도 언급하지 않고**
  재개가 왕복하는 것을 확인했다.

### ⚠ 정정 — `IAuthenticator` 는 **이미 배선돼 있었다**

앞 절과 커밋 메시지에 "`IAuthenticator` 가 배선되지 않았다" 고 여러 번 적었는데
**사실이 아니다.** `Dispatch/AuthenticationMiddleware` 로 완전히 배선돼 있고
`MessageDispatcherBuilder` 가 미들웨어 순서(상태 필터 → 인증 → 인가)까지 강제한다.
`Hosting/*.cs` **최상위만 grep 하고 `Dispatch/` 하위를 놓친** 내 실수다.
이 기록을 남기는 이유: 같은 방식으로 "없다" 고 단정하는 실수가 반복될 수 있다 —
**하위 디렉터리를 포함해 확인한 뒤에 없다고 말한다.**

### ⑧ 일관성 모델 (`c440012`, `docs/CONSISTENCY.md`)

- **"여기 적히지 않은 것은 보장되지 않는다"** 를 원칙으로 보장/미보장을 한 표에 모았다.

  만료는 판정 즉시·회수 지연 / 좀비 차단은 **다중 노드에서도 성립**(단일 키 CAS 위에
  세웠으므로) / 서킷 브레이커·인메모리·속도 제한은 **노드 로컬**.
- 앱 규율: **충돌 후 반드시 다시 읽는다** — 옛 값 위의 재시도는 남의 변경을 덮는다.

  문서에만 있으면 어댑터를 쓰는 사람이 못 본다.

### ⑨ PostgreSQL 어댑터 (`c45e6aa`, ADR-0037) — 사용자 지시로 MongoDB 대체

- **적합성 21종을 첫 실행에 전부 통과.** 인메모리(참조)·Redis(원격 KV)·PostgreSQL(관계형)
  **세 구현이 같은 스위트**를 통과하는 것이 교체 가능성의 가장 강한 증거다.
- **CAS 는 조건부 `UPDATE`** — Redis 가 Lua 로 묶어야 했던 것을 관계형은 공짜로 준다.
  버전은 전역 `SEQUENCE`(행별이면 삭제 시 사라져 ABA).
- **네이티브 TTL 이 없어** 지연 판정 + 주기적 청소 → 결과적으로 인메모리와 같은 모양.
  **청소에 배치 상한**(만료 행 수백만에서 무제한 `DELETE` 는 긴 잠금으로 서비스를 막는다 —
  **청소가 장애를 만드는 것이 가장 나쁜 결말**).
- 시간 기준은 **DB 서버 `now()`**(앱 시계면 노드마다 다른 답) · **스키마 자동 생성 안 함**
  (운영자가 DDL 시점을 통제해야 한다) · 식별자는 **화이트리스트로 거부**(SQL 에 직접
  삽입되므로 이스케이프보다 거부가 안전).
- **⚠ 문서 정정 범위를 판단했다.** 계획 문서(ROADMAP·STANDUP·CONSISTENCY·CLAUDE.md)만
  PostgreSQL 로 바꾸고 **`docs/legacy/` 는 고치지 않았다** — 레거시가 *실제로* MongoDB 를
  쓴다는 사실 기록이고 유출 자격증명도 실제 `mongodb://` 문자열이라, 바꾸면 **기록이
  거짓이 되고 보안 사실이 왜곡된다.** 레거시 문서에서 바꾼 것은 "어댑터 후보" 라는
  **미래 판정 한 줄**뿐이다. `history/` 도 추가 전용이라 그대로 뒀다.
- "MongoDB 어댑터 = 채택 안 함" 을 **미완료 체크박스로 두지 않았다** — 하지 않기로 한 일은
  영원히 미완료로 남아 진행률을 왜곡한다. 주석 줄로 남겼다.

  - CI 는 `dotnet-version` 을 적지 않고 `global.json` 을 읽으므로 별도 조치 없음

- **강타입 접근자 소스 제너레이터** (`8f2610c`, ADR-0043)
  - ⭐ **서수는 문자열 키를 고치다 만든 함정이다** — 열을 가운데에 하나 끼워 넣으면
    뒤따르는 모든 `GetInt32(row, 3)` 이 조용히 다른 열을 읽는다. 컴파일도 되고 예외도
    안 나고 **밸런스 값만 틀린다**(문자열 키는 "없는 열" 이면 터지기라도 했다)
  - ⭐ **진단으로 잡을 수 없으므로 스키마와 접근자를 같은 선언에서 함께 생성** —
    열 순서와 서수가 같은 입력에서 나와 어긋날 경로가 존재하지 않는다
  - 뷰는 스키마 **참조 동일성** 확인. 참조 대상은 `typeof(RowType)`(오타가 컴파일 오류).
    범위 "설정 안 함" 은 **명명 인자의 부재**로 판단(센티넬을 두면 "설정한 0" 과 섞인다)
  - `IEquatable` 을 생성 쪽에서 붙인다 — 생성기가 만든 타입의 비용(CA1815)을
    **사용자 파일이 치르게 하지 않는다**
  - 진단 CHSM2001~2010(**2009 는 결번** — 어트리뷰트가 DataTable 에 있어 "미참조"
    분기는 도달 불가). 테스트 39종(드라이버 20 + 종단 19), 읽기 경로 할당 0

- **콘텐츠 지문 게이트** (`ea8a262`, ADR-0044)
  - ⚠ **Core 는 이 값이 무엇의 지문인지 모른다** — 선택 축이라 타입이
    `ContentFingerprint` 이지 `TableVersion` 이 아니다. **일반화가 취향이 아니라
    하드 룰의 결과**이고, `StaticTableFingerprint → ContentFingerprint` 변환 한 줄이
    **앱의 몫**으로 남는다(그 어색함이 두 축이 분리돼 있다는 증거)
  - ⭐ `ClientHello` 는 영구 동결이라 필드를 못 더한다(R-2) → **새 메시지 ID**
    (40010·40011). `ClientHello` 와 **같은 플러시**에 실어 **왕복은 늘지 않는다**
  - 불일치에 **새 응답 형식을 만들지 않는다** — 기존 `ConnectionRejected` 의 사유
    코드만 늘렸다(형식을 늘리면 그것을 모르는 클라가 사유를 잃는다, R-3)
  - 예외 타입은 나눴다 — **조치가 다르기 때문**(실행 파일 갱신 vs 데이터 갱신)
  - ⚠ **파일이 아니라 파싱 결과**를 해싱한다. 주석·개행에 반응하면 `git autocrlf`
    하나로 전 클라가 거부된다. `XxHash128`(`string.GetHashCode` 는 프로세스마다 시드가
    달라 쓸 수 없다) — 이 축의 **첫 서드파티 의존**
  - 테스트 48종. THREAT-MODEL 7절에 **"인증이 아니다"** 로 분류

- **표 스냅샷** (`6052fef`, ADR-0045)
  - ⭐ **스키마는 와이어에 싣되 읽을 때는 로컬 것을 쓴다.** 실린 것은 대조용 —
    값이 열 우선이라 스키마가 한 칸만 어긋나도 **전부 엉뚱한 열로 조용히 해석**된다
  - 로컬 인스턴스를 쓰는 결정적 이유는 **생성된 접근자와의 호환**(뷰가 참조 동일성으로
    서수를 보장하므로 와이어 스키마로 세우면 받은 표가 거부된다). 대가는 **클라가
    스키마를 컴파일 타임에 가져야** 한다는 것
  - **합격 기준은 지문 보존** — 필드 비교보다 강하고 열 종류가 늘어도 유효하다
  - 참조 해결 결과는 싣지 않고 **다시 푼다**(값에서 유도되는 것이라 어긋날 수 있다)
  - 잘린 입력은 예외가 아니라 `false`. **문자열 길이를 믿고 배열을 먼저 잡지 않는다**
    (손상된 스냅샷의 큰 길이가 곧 OOM)
  - 전송 배선은 넣지 않았다 — 앱의 정책이다(파일 감시기를 넣지 않은 것과 같은 선).
    테스트 25종

## 배운 것 (이어서 5)

- **⭐ 한 문제를 고치면 그 해법이 다음 함정을 만든다.** 문자열 키를 서수로 바꿔
  조회 비용을 없앴더니 **서수 관리**가 새 위험이 됐다. 그리고 그 위험은 문자열 키보다
  **더 조용하다** — 없는 열은 터지지만 밀린 서수는 값만 틀린다. 개선의 대가를
  같이 적어 두지 않으면 다음 사람이 그 함정을 밟는다
- **⭐ 진단으로 못 잡는 문제는 자료구조로 없앤다.** 서수 밀림은 스키마도 사람이 적는
  한 검사할 기준이 없다. 답은 더 똑똑한 검사기가 아니라 **둘을 같은 입력에서 뽑는 것**
  이었다. 핫 리로드에서 "불변을 먼저 정한 것" 이 값을 치른 것과 같은 종류의 이득이다
- **⚠ 하드 룰이 이름을 정한다.** "Core 는 데이터 테이블을 모른다" 가 `TableVersion` 을
  `ContentFingerprint` 로 만들었고, 그 결과 변환 한 줄이 앱에 남았다. **그 어색함을
  없애려 하면 규칙이 깨진다** — 어색함이 경계가 살아 있다는 신호일 때가 있다
- **⚠ "경고 0" 은 또 한 번 증분 빌드가 숨겼다.** 증분에서 0 이었는데 `-t:Rebuild` 에서
  RS0016 이 **39개** 나왔다. 어제 배운 것을 오늘 또 밟았다 — 습관이 될 때까지
  `-t:Rebuild` 없이 0을 주장하지 않는다
- **⚠ 테스트가 최선 노력 경로에 의존하고 있었다.** 전 스위트 병렬 실행 중 한 번 깨진
  것을 "가끔 그런다" 로 넘기지 않고 원인을 봤더니, **설계가 의도적으로 보장하지 않는
  것**을 테스트가 단언하고 있었다. 제품을 고치면 설계 결정이 뒤집히므로 **테스트를
  고쳤고**, 전송 타이밍이 없는 InMemory 로 계약을 결정적으로 고정했다
- **커밋을 손으로 나눴으면 중간 커밋이 빌드되는지 확인한다.** worktree 하나로
  `8f2610c` 를 단독 빌드해 bisect 가 깨지지 않음을 확인했다

# 2026-08-10 (이어서 8) — 피어 링크 미검증 넷 해소: 셋이 결함이었다

## 한 일

로드맵 순서(리밸런싱)보다 **ADR-0050 이 스스로 남긴 부채**를 먼저 골랐다 — 리밸런싱이
그 링크 위에 올라가므로 밑을 먼저 굳히는 것이 순서라고 판단했고, 결과적으로 옳았다.

**미검증 넷 중 셋이 결함이었다** (미커밋, ADR-0051)

- ⭐⭐ **재연결은 "미검증" 이 아니라 동작하지 않았다.** `PipeWriter.FlushAsync` 는 상대가
  파이프를 닫아도 **예외를 던지지 않고** `IsCompleted` 만 세운 채 성공한 듯 반환한다.
  `ClusterPeerSet.WriteAsync` 가 그 `FlushResult` 를 버렸으므로 링크는 살아 있는 척하며
  **이후 모든 프레임을 조용히 삼켰고 재연결이 영원히 트리거되지 않았다**.
  고의 회귀로 확인: 피어 재기동 후 **20번을 보내도 0장 도착**
- ADR-0050 이 `TryWrite` 의 `false` 를 반드시 본다고 적어 놓고 **바로 다음 줄의
  `FlushAsync` 반환값은 버리고 있었다**
- `Drop()` 이 커넥션을 해제하지 않아 **재연결마다 소켓 누수**
- `ClientSession.Completion`(읽기 루프)을 버려 예외 미관측 + 가장 이른 사망 신호 상실
- `GetOrAdd` 팩토리 중복 호출로 고아 링크(채널 + 소비자 태스크)
- `QueueFull` 과 버퍼 반납은 **동작이 정상**이었고 이제 검증된다

**검증 (테스트 13 → 18종)**

- 큐 포화: **연결 수립을 붙잡는 게이트 전송**으로 결정적으로 재현(지연으로 흉내 내지 않았다)
- 버퍼 반납: 세는 `ArrayPool` 을 주입해 정상·거절·종료·실패 경로 전부에서 대여=반납
- 재연결: 피어 정지 → 같은 주소로 재기동 → 실제 도착
- **half-close 감지**: `FlushResult` 검사를 **홀로** 증명하는 테스트
- 재연결 시 커넥션 누수 없음
- **고의 회귀 3종 전부 확인**

**측정 2건 (BENCHMARKS)**

- 피어 링크 처리량: 피어 1개 **~2.0~2.5 M 프레임/s**, 할당 0
- 전용 풀 A/B: 깊은 큐에서 `Shared` 514.0 ns/274 B → 전용 **342.9 ns/0 B**

**공개 API +1**: `ArrayPool<byte>` 를 받는 생성자 (승인 파일 갱신)

## 배운 것

- **⭐⭐ "미검증" 이라고 정직하게 적는 것과 그것이 결함을 감추지 않는 것은 별개다.**
  ADR-0050 은 넷을 정직하게 미검증으로 적었고 그것은 옳은 일이었지만, **셋이 결함이라는
  사실은 실제로 돌려 보기 전까지 몰랐다.** 정직한 라벨이 안전을 주지는 않는다
- **⭐⭐ 반환값을 버리는 실수는 한 곳을 막는다고 끝나지 않는다.** 레거시의 `TryWrite`
  유실을 그토록 경계해 놓고 같은 파일 안에서 `FlushAsync` 를 버렸다.
  **"이 API 는 실패를 반환값으로 알리는가" 를 API 마다 물어야 한다** — 예외가 오지
  않는 것이 이 결함의 본질이었다
- **⭐ 한 테스트가 두 장치를 함께 통과시키면 둘 중 하나는 죽은 코드일 수 있다.**
  재연결 테스트만으로는 `FlushResult` 검사를 지워도 초록이었다(읽기 루프 완료가 먼저
  잡는다). half-close 테스트를 따로 붙여야 그 검사가 홀로 증명된다.
  **고의 회귀를 장치마다 돌려 본 것이 이것을 드러냈다**
- **⚠ 관측과 기다림은 다르다.** 읽기 루프를 `await` 하자 고의 회귀에서 **무한 정지**가
  재현됐다 — 커넥션 해제는 기다려도 되지만(우리 자원) 남의 태스크는 관측만 한다.
  인메모리 전송이 종료 드레인에 상한을 둔 것(감사 H3)과 같은 판단이다
- **⚠ 회귀 테스트가 정지가 아니라 실패로 끝나게 만든다.** 첫 고의 회귀는 240초 타임아웃까지
  매달렸다. 그 정지 자체가 설계 결함의 신호였고, 고치자 3초 만에 깨끗이 실패했다
- **⭐⭐ 헤드라인 지표가 조건부일 수 있다.** "프레임당 힙 할당 0" 이 **큐 깊이에
  조건부**였다. 같은 코드가 in-flight 1,000 에서 0 B, 10,000 에서 27~308 B.
  지금까지의 무할당 측정은 **전부 in-flight 가 얕은 조건**이었다
- **⭐ 판별 기준을 잘못 잡을 뻔했다.** 처음에는 "큐를 쓰는 경로" 를 찾으려 했는데,
  진짜 기준은 **미처리 대여물이 무엇에 비례하는가** 다 — 동시성이면 안전,
  **설정 용량**(큐 깊이·최대 커넥션 수)이면 함정. 그래야 `PooledBufferWriter`
  (커넥션당 하나, 커넥션 수명 내내 보유)가 걸린다
- **⚠ 문서가 권장하는 사용법이 함정의 모양일 수 있다.** `PooledBufferWriter` 는
  "커넥션당 하나를 만들어 재사용" 을 의도된 사용법으로 적어 두었는데, 그것이 정확히
  1만 커넥션에서 1만 개 대여를 붙드는 모양이다
- **⚠ 대가가 할당만이 아니었다.** 전용 풀은 0 B 를 회복했을 뿐 아니라 **33% 빨랐다**.
  "조금 더 할당된다" 로 읽었으면 이 크기를 놓쳤다
- **⭐ 조립 가드가 내 실수를 잡았다.** 벤치에서 프레임 상한(64 KiB)을 전송 버퍼(64 KiB)와
  같게 잡자 `CompositionGuard` 가 조용한 교착 대신 명시적 오류로 실패시켰다
