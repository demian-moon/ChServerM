# ChServerM 위협 모델

**작성**: 2026-08-05 (Phase 9 첫 산출물)
**지위**: 살아 있는 문서. 새 축·새 공격 표면이 생기면 갱신한다. 위협 항목은 삭제하지 않고
상태만 바꾼다(완화책이 구현되면 근거를 채운다).
**출발점**: [legacy/07-security.md](legacy/07-security.md#새-코드에-절대-옮기면-안-되는-것)의
결함 목록과 [legacy/05-client.md](legacy/05-client.md#-인증-핸드셰이크-전체-흐름-양쪽-코드로-확정)의
핸드셰이크 분석. 레거시가 실제로 뚫려 있던 지점이 이 문서의 위협 목록을 만들었다.

## 0. 이 문서를 읽는 법

- **위협(T-nn)** 은 STRIDE 로 분류하고, 각 위협에 **완화책과 상태**를 매핑한다.
  Phase 9 게이트 조건은 "모든 위협에 완화책이 매핑되어 있는가"다 — 전부 구현이 아니라
  전부 **매핑**이다. 미구현 완화책은 담당 Phase 를 명시한다.
- **레거시 근거**가 있는 위협은 그 결함이 재발하지 않음을 증명하는 것이 완화책의 합격 기준이다.
  "새 기능"이 아니라 "확인된 사고의 재발 방지"로 읽는다.
- 상태 표기: ✅ 구현·테스트됨(근거 병기) / 🔶 부분(남은 범위 병기) / ⬜ Phase N 예정

## 1. 보호 자산

| # | 자산 | 침해 결과 |
|---|---|---|
| A-1 | 사용자 자격증명(비밀번호·토큰) | 계정 탈취. 레거시는 미인증 키 교환으로 사실상 노출 상태였다 |
| A-2 | 세션 상태·사용자 데이터 | 위변조·탈취. 상업 서비스의 신뢰 근간 |
| A-3 | 서버 가용성(메모리·CPU·커넥션 슬롯·큐) | 서비스 정지. **거부가 붕괴보다 낫다**(CLAUDE.md 2절) |
| A-4 | 와이어 기밀성·무결성 | 도청·변조·리플레이 |
| A-5 | 키 자료(세션 키·인증서 개인키) | 하나가 새면 A-1·A-2·A-4 전부 무너진다 |
| A-6 | 운영 시크릿(저장소 자격증명 등) | 인프라 전체로 침해 확산 |

## 2. 신뢰 경계 (Trust Boundaries)

```
        비신뢰                              │ 신뢰 (프로세스 내부)
                                            │
 인터넷 ──▶ [TB-1 수신 소켓] ──▶ 프레이밍 디코더 ──▶ [TB-2 프레임 경계 확립]
                                            │              │
                                            │              ▼
                                            │        역직렬화 → 미들웨어 → [TB-3 인증 경계] → 핸들러
                                            │
 운영자 설정·시크릿 ──▶ [TB-5 설정 로딩]     │
                                            │
 외부 저장소(Redis 등) ◀── [TB-4 아웃바운드] ┘  (Phase 13에서 활성화)
```

| 경계 | 의미 | 경계를 넘을 때의 규칙 |
|---|---|---|
| TB-1 | 인터넷 ↔ 수신 소켓 | **모든 인바운드 바이트는 적대적이다.** 길이·버전·플래그를 버퍼 확보 **전에** 판정한다 |
| TB-2 | 프레이밍 ↔ 디스패치 | 프레임 **경계**만 신뢰가 확립된다. 페이로드 **내용**은 여전히 비신뢰 — 역직렬화·필드 검증이 남아 있다 |
| TB-3 | 인증 전 ↔ 인증 후 | 인증 전 주체는 익명이다. **기본 거부** — 화이트리스트에 없는 메시지는 도달하지 못한다 |
| TB-4 | 프로세스 ↔ 외부 저장소 | 저장소 응답도 검증 대상(Phase 13). 저장소 장애가 코어 경로를 마비시키지 않는다(Phase 10 Bulkhead) |
| TB-5 | 설정·시크릿 ↔ 프로세스 | 시크릿은 설정 파일에 두지 않는다. 잘못된 조합은 시작 시점에 실패(`CompositionGuard`, ADR-0007) |

## 3. 공격 표면 (Attack Surface)

| # | 표면 | 상태 | 비고 |
|---|---|---|---|
| AS-1 | TCP accept 경로 | 활성 | `MaxConnections` + 거부 통지 구현됨. SYN 폭주·accept 큐는 Phase 10 |
| AS-2 | 프레임 헤더 파싱 | 활성 | 퍼징 13만+ 회 통과, 불변식 4종 (Phase 4) |
| AS-3 | 조각 재조립 | 활성 | 연속성 계약 + 누적 상한 (ADR-0015) |
| AS-4 | 페이로드 역직렬화 | 활성 | 어댑터 3종. `TryDeserialize`(예외 없음), MemoryPack 엄격 소비 |
| AS-5 | 디스패치·핸들러 | 활성 | 미들웨어가 라우팅보다 앞(Phase 2). 인가는 Phase 9 |
| AS-6 | 핸드셰이크·키 교환 | **예정** | Phase 9 설계 대상. 레거시 최대 결함 지점 |
| AS-7 | 압축 해제(`IPayloadCodec`) | **예정** | Phase 9. 압축 폭탄·CRIME 류가 이 표면에 붙는다 |
| AS-8 | 세션·외부 저장소 | **예정** | Phase 13. 세션 복구 경로가 새 스푸핑 표면이 된다 |
| AS-9 | 운영·설정·시크릿 | 활성 | 시크릿 관리 정책은 Phase 9 |

새 축을 추가할 때 이 표에 행을 추가하고, 그 표면의 위협을 4절에 등록하는 것이
축 추가 절차의 일부다.

## 4. 위협 → 완화책 매핑

### 4.1 S — 스푸핑 (Spoofing)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-01 | **MITM 이 키 교환에 개입해 세션 키를 대체하고 자격증명을 복원** | 미인증 RSA 공개키 평문 교환 — MITM 이 키를 바꿔치기하면 비밀번호가 복원된다 ([05-client](legacy/05-client.md), 자격증명 실질 노출) | **TLS 1.3(`SslStream`) + 서버 인증서** — 자체 프로토콜을 만들지 않는다 (**ADR-0017 로 확정**) | ⬜ Phase 9 구현 (설계 ✅ ADR-0017) |
| T-02 | **다운그레이드 공격** — 협상 과정을 조작해 낮은 버전·약한 암호로 유도 | (신규 — 버전 협상 도입이 만드는 위협) | 협상을 **TLS 채널 안에서** 수행 — TLS 1.3 Finished 의 transcript 검증이 담당하므로 앱 계층 재검증이 필요 없다 (ADR-0017 결정 3) | ⬜ Phase 9 구현 (설계 ✅ ADR-0017) |
| T-03 | **세션 탈취·재접속 위장** — 끊긴 세션을 타인이 이어받음 | 레거시는 세션 복구 자체가 없음 | 재접속 토큰은 예측 불가 난수 + 만료 + 1회용. 세션 복구 설계(Phase 13)의 선결 조건으로 여기 예약 | ⬜ Phase 13 |

### 4.2 T — 변조 (Tampering)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-04 | **와이어 변조 미탐지** | 체크섬 함수 본문이 `return true`(가짜) + 인증 없는 CBC — 패딩 오라클로 복호까지 가능 ([07-security](legacy/07-security.md) 결함 #3) | 무결성은 **AEAD 태그 단일 수단**(AES-GCM/ChaCha20-Poly1305). 별도 체크섬을 두지 않는다 — Phase 4 에서 이미 체크섬 필드를 헤더에서 제거했다 | ⬜ Phase 9. 🔶 헤더에 가짜 무결성 장치가 없음은 확정(Phase 4) |
| T-05 | **리플레이** — 유효했던 패킷 재전송(결제·아이템 지급 등) | 레거시 `pid`(패킷 아이디) 개념만 존재, 검증 없음 | 커넥션 내 리플레이·재정렬은 TLS 레코드 계층이 차단 — 앱 시퀀스를 중복 구현하지 않는다(ADR-0017 결정 4, 레거시 `pid` 승계 안 함). 크로스 커넥션 토큰 재사용은 인증 계층(1회용·만료 토큰). 보안 축 "없음" 조립은 무보호임을 계약 문서에 명시 | ✅ 2026-08-06 — `ITokenReplayGuard`(검증→클레임 순서 계약: 역순은 가드 포화 로그인 DoS) + 유계·TTL 인메모리 구현(`9a7297d`). "같은 토큰 두 번째 커넥션 거부"가 2전송 테스트로 고정. 분산(다중 노드) 등록부는 Phase 13+ 어댑터 |
| T-06 | **프레이밍 desync** — 오류 프레임 이후 어긋난 경계로 계속 파싱 | 레거시는 예외를 잡고 루프 계속 → 상태 머신이 어긋난 채 진행 ([02-packet-framing](legacy/02-packet-framing.md)) | 오류 프레임 = 커넥션 종료, **재동기화 시도 금지**. 디코더 무상태화로 어긋날 상태 자체를 제거 | ✅ Phase 4 — 퍼징 불변식 4종, 위반 8경로 통합 테스트(ADR-0015) |

### 4.3 R — 부인 / 무관측 (Repudiation)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-07 | **보안 이벤트가 관측되지 않음** — 공격이 진행 중인데 아무도 모른다 | 압축·체크섬·백프레셔 등 6개 장치가 무동작인데 **아무도 몰랐다** ([09-observability](legacy/09-observability.md)) | 조용한 실패 지점마다 카운터 + 0 아니면 경보: 인증 실패·버전 거부·프레임 오류·리플레이 탐지·풀 누수(`LeakedBuffers` 는 이미 있음). `ErrorCode`/`EventId` 체계는 Core 에 확정됨 | 🔶 계약(Core)·풀 누수 카운터는 있음. 메트릭 파이프라인은 ⬜ Phase 11 |

### 4.4 I — 정보 노출 (Information Disclosure)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-08 | **도청** — 트래픽이 사실상 평문 | 서버→클라 XOR 32B 반복 키: 고정 헤더 = 알려진 평문으로 키 전체 복원 (결함 #4) | 양방향 AEAD. **방향별 알고리즘 차등 금지** — 레거시의 근본 오류는 "클라→서버만 중요하다"는 비대칭 가정이었다 | ⬜ Phase 9 |
| T-09 | **암호문 패턴 노출** — 같은 평문 접두사 = 같은 암호문 접두사 | 세션 전체 IV 고정 + CBC (결함 #2). 고정 구조 헤더라 즉시 관찰 가능했다 | nonce 관리를 TLS 1.3 레코드 계층에 위임 — 직접 관리하지 않는 것이 완화책이다(ADR-0017 결정 1) | ⬜ Phase 9 구현 (설계 ✅ ADR-0017) |
| T-10 | **키 자료 메모리 상주·노출** | RSA 개인키가 `public string` 프로퍼티, 프로세스 수명 내내 XML 평문 (결함 #5) | 키 자료는 `Span<byte>` + 사용 후 `CryptographicOperations.ZeroMemory`. **키를 담는 타입을 public API 표면에 노출하지 않는다**(승인 파일 게이트가 diff 로 잡는다) | ⬜ Phase 9 |
| T-11 | **압축-암호화 상호작용(CRIME 류)** — 압축률 관찰로 비밀 복원 | 레거시는 압축이 무동작이라 우연히 면제(결함 #1) — 새 코드가 압축을 "고치면" 위협이 생긴다 | **압축 → 암호화 순서 고정** + 비밀(토큰 등)과 공격자 제어 데이터가 같은 압축 문맥에 섞이는 메시지는 무압축. `IPayloadCodec` 계약 문서에 명시 | ✅ 2026-08-06 — 순서는 구조가 보장(압축 = 페이로드 수준, TLS = 그 바깥 스트림 수준 — 뒤집힐 방법이 없다, ADR-0019). 비밀 문맥 제외는 `PayloadCompressionOptions.DoNotCompress`(제외 목록이 코덱 호출 자체를 막음을 계수 테스트로 고정, `b9bd2d0`) |

### 4.5 D — 서비스 거부 (Denial of Service)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-12 | **와이어 값 기반 무제한 할당** | `Decompress` 가 와이어의 `originalLength` 로 `new byte[]` — 공격자 제어 할당 (결함 #6). 최대 프레임 크기 자체가 없었다 | 길이를 **버퍼 확보 전에** 판정: `MaxPayloadLength` + 절대 상한 64MiB, `uint` 인 채 비교(int 캐스팅 금지) | ✅ Phase 4 — 퍼징 길이 극단값 포함. 압축 해제 상한도 ✅ 2026-08-06 (T-18, ADR-0019) |
| T-13 | **조각 재조립 메모리 고갈** — 미완성 조각을 무한 누적 | (레거시는 조각화 자체가 없음 — 신규 표면) | 누적 상한 `MaxAssembledMessageLength`(기본 1MiB, 0=거부) + 연속성 계약 + 미완성 방치는 idle timeout 이 종료 | ✅ ADR-0015 — 위반 8경로 테스트 |
| T-14 | **커넥션 폭주·슬롯 고갈** | 레거시는 상한 없음 | `MaxConnections` + 거부 사유 통지(`ConnectionRejected` 40004, 최선 노력 동기 send — 거부 경로의 비동기 대기는 그 자체가 표면). 동적 판정은 `IAdmissionControl` | 🔶 정적 상한·거부 통지 ✅(Phase 5). SYN 폭주·accept 큐·동적 제어 ⬜ Phase 10 |
| T-15 | **슬로우로리스·유휴 점유** — 바이트를 흘리며 자원만 점유 | 레거시는 감지 수단 없음 | `IdleTimeout`(전송당 스윕 타이머 1개) + `WaitForDataBeforeAllocating`(유휴 커넥션 버퍼 0). 커넥션당 실측 ~8KB | ✅ Phase 5 — 1만 접속 실측 82MB |
| T-16 | **핸드셰이크 비대칭 CPU 소진** | 커넥션마다 **양쪽이 RSA 2048 키쌍 생성** — 연결 폭주 = CPU 고갈 ([05-client](legacy/05-client.md) 결함 #4) | 설계 제약으로 고정: 서버 측 비대칭 연산은 커넥션당 ECDHE 1회 수준으로 최소화, 인증서 키는 재사용. 핸드셰이크 타임아웃 + 인증 전 커넥션의 자원 상한 | ⬜ Phase 9 (설계 제약) + Phase 10 (타임아웃·상한) |
| T-17 | **큐 팽창 OOM** — 느린 소비자 뒤로 무한 적재 | 레거시: 무제한 큐 + `TryWrite` 조용한 유실 ([04-concurrency](legacy/04-concurrency.md)) | 유계 채널 + 백프레셔(9.6). 최대 프레임 ≤ 전송 버퍼 조립 시점 검사(ADR-0007) — 어기면 무예외 교착이었다 | ✅ Phase 5·8 — 데드락 테스트로 고정 |
| T-18 | **압축 폭탄** — 작은 입력이 거대한 출력으로 팽창 | T-12 와 동근(와이어 값 신뢰) | 압축 해제 출력 상한 = `MaxPayloadLength` 와 연동, 초과 시 커넥션 종료. `IPayloadCodec` 계약에 상한 인자를 포함시켜 구현체가 생략할 수 없게 | ✅ 2026-08-06 — `TryDecode(maxDecodedLength)` 필수 인자(생략 불가) + 블롭 자기서술로 **버퍼를 잡기 전에** 선언 길이 검증(ADR-0019, `c04644b`). 상한 = `MaxDecompressedMessageLength`(기본 1MiB). 16B 프레임의 1GiB 선언 폭탄 = 할당 없이 종료 + 서버 생존이 종단 테스트로 고정 |

### 4.6 E — 권한 상승 (Elevation of Privilege)

| ID | 위협 | 레거시 근거 | 완화책 | 상태 |
|---|---|---|---|---|
| T-19 | **인증 전에 인증 후 메시지 처리** | `AllowedPkState` 기본값이 `A_SC_ANY_STATE`(전부 허용) — 존재하지 않는 세션이 가장 관대한 권한 ([06-session-user](legacy/06-session-user.md)) | 상태별 패킷 화이트리스트 + **기본 거부**. 미들웨어가 라우팅보다 앞(Phase 2 — 모르는 ID 로 인증 우회 불가), `MessageId.None` 센티넬 등록 거부는 이미 있음 | ✅ 2026-08-05 — `MessageStateFilterMiddleware`(기본 거부는 옵션이 아님, FrozenDictionary+비트마스크). 인증 전 특권 메시지 차단·미등록 기본 거부·상태 전이가 2전송 테스트로 고정(`StateFilterTests`, `1b3fc20`) |
| T-20 | **인증 결과 무시** — 검증은 하는데 결과를 버림 | `DoPkLogin` 이 `WRONG_PW` 의 `return` 을 주석 처리 — 올바른 PBKDF2 해싱이 완전 무의미 ([07-security](legacy/07-security.md) AuthM #1) | 구조로 봉쇄: 미들웨어는 `ValueTask<DispatchStatus>` **반환을 강제** — 결과를 가변 필드에 적는 설계였다면 안 적고 지나가도 정상 집계된다(Phase 1 에서 이 이유로 반환형 채택). 인증 실패 = 즉시 종료를 인증 미들웨어 계약에 명시 | ✅ 2026-08-06 — `AuthenticationMiddleware`(`9a7297d`): 실패 = `next` 미호출 + **옵션 무관** 6000 종료(전용 `RejectedByAuthentication` — `RejectedByPolicy` 재사용 시 옵션 하나로 통과하는 구멍을 막음). 성공 = 상태 대체 전이(T-19 필터와 한 몸). 해싱 위임은 ADR-0018(`f47967b`, 레거시 해시 형식 호환). 오답 = 응답 없이 종료가 2전송 테스트로 고정 |
| T-21 | **메시지별 인가 누락** — 인증됐지만 권한 밖 행위 | 레거시는 인가 개념 자체가 없음 | 인가 미들웨어(`IAuthorizationPolicy`) — 핸들러 도달 전 판정 | ✅ 2026-08-06 — 2단 구조(`83a8d76`): 메시지 수준은 T-19 필터 + 인증 `GrantedStates` 가 기본 거부로 담당(관리자 전용 = 상태 비트), 자원 수준(소유자 검사 등 페이로드 의존)은 `AuthorizationMiddleware` 보호 목록 + `IAuthorizationPolicy`. 조립 순서(필터→인증→인가)는 `Build()` 검증. 거부는 옵션 게이트(6001) — 인증과 의도적 비대칭(정당한 세션의 정상 흐름일 수 있다). 소유자 검사 2전송 테스트 고정 |
| T-22 | **역직렬화를 통한 계약 위반** — 페이로드가 파서 상태를 오염 | 와이어 값 신뢰가 레거시의 반복 패턴 | `TryDeserialize`(예외 없는 실패), MemoryPack 엄격 소비(잔여 바이트 거부)·null 거부, FlatSharp Greedy 전용(반환 객체의 버퍼 참조 탈출 차단), 필드 범위 검증은 입력 검증 항목으로 | 🔶 어댑터 계약 ✅(Phase 6). 페이로드 필드 범위 검증·퍼징 확대 ⬜ Phase 9 |

## 5. ⚠ 프로토콜 버전 협상 — 요구사항과 설계 방향

**문제(2026-08-04 감사)**: 현행 유일 정책은 "프레임 버전 불일치 → `VersionMismatch` → 종료"다
(`FramingOptions.ProtocolVersion`, 수용 버전 정확히 1개). 무중단 롤링 배포(Phase 15) 중에는
서버·클라 버전 불일치가 **정상 상태**이므로 이 정책과 구조적으로 충돌한다 — 배포할 때마다
구버전 클라이언트가 전부 끊긴다면 "무중단"이 아니다.

### 요구사항 (핸드셰이크 ADR 이 충족해야 할 것)

| # | 요구사항 | 근거 |
|---|---|---|
| R-1 | **협상은 핸드셰이크에서 1회** — 프레임마다 버전 분기를 두지 않는다 | 핫패스 무분기. 프레임 헤더의 버전 필드는 "합의 위반 감지"용으로 유지 |
| R-2 | **부트스트랩 최소 서브셋** — 첫 메시지(ClientHello)는 모든 버전이 파싱할 수 있는 최저 공통 형식으로 고정 | 협상 이전에는 합의된 버전이 없다. 이 서브셋은 사실상 영구 동결이므로 최소로 |
| R-3 | **교집합 없으면 명시적 거부** — 지원 범위 불일치 시 사유(지원 범위 포함)를 보내고 종료 | 조용한 유실 금지. 기존 `ConnectionRejected`(40004) 경로 재사용 |
| R-4 | **다운그레이드 방지** — 협상 전사를 키 확립 후 AEAD 로 재검증 | T-02. 협상이 암호화 이전에 일어나므로 MITM 이 지원 목록을 조작할 수 있다 |
| R-5 | **거부·협상 결과를 카운터로 관측** — 버전별 접속 분포, 거부 수 | 롤링 배포 중 "구버전이 얼마나 남았나"가 배포 진행 판단 근거다 (T-07, Phase 11) |

### 설계 확정 — ADR-0017 (2026-08-05 채택)

- **클라이언트가 지원 범위 `[min, max]` 제시 → 서버가 교집합 최고 버전 선택·확정** 통보.
  이후 모든 프레임은 합의 버전을 사용하고, 불일치는 그때부터 종료 사유가 된다(현행 정책이
  "협상 후" 단계의 정책으로 자리를 옮기는 것 — 코드 폐기가 아니다).
- **협상은 TLS 채널 확립 후에 수행한다** — R-4(다운그레이드 방지)가 TLS Finished 의
  transcript 검증으로 구조적으로 충족되어, 앱 계층 재검증 장치가 필요 없다.
- **핸드셰이크 프레임은 헤더 v1 + 고정 바이너리 레이아웃으로 영구 동결**하고 직렬화 축에
  의존하지 않는다(R-2) — 교체 가능한 축 위에 부트스트랩을 얹으면 축 교체가 와이어
  호환성을 깬다.
- **와이어 프레이밍 버전과 애플리케이션 스키마 버전을 분리**한다. 전자는 이 절의 협상 대상,
  후자는 직렬화 축의 스키마 진화가 담당(protobuf 모르는 필드 보존, MemoryPack `VersionTolerant`
  — ADR-0013 주의 계약). 하나의 버전 번호에 두 의미를 싣지 않는다.
- 기각된 대안(다중 버전 상시 병행 수용, TLS 밖 협상 + transcript 재검증 등)과 근거는
  ADR-0017 의 대안 표에 있다.

## 7. 범위 밖 (Out of Scope)

- **볼류메트릭 DDoS** (대역폭 포화) — 인프라 계층(LB·스크러빙)의 몫. 프레임워크는 자원 상한과
  거부로 프로세스 생존만 책임진다.
- **호스트·물리 보안, 커널 취약점** — 배포 환경의 몫.
- **타이밍 이외의 사이드채널** (전력 분석 등) — BCL 암호 구현(`AesGcm`, `SslStream`)에 위임.
  직접 암호 프리미티브를 구현하지 않는 것 자체가 완화책이다.
- **클라이언트 단말 침해** (메모리 치팅 등) — 서버는 클라이언트를 신뢰하지 않는 것으로 대응하며
  (TB-1), 단말 안티치트는 프레임워크 범위가 아니다.
